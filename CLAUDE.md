## 2. Стек

**Бэкенд:** Python 3.12, FastAPI + Uvicorn, Jinja2 (HTML-шаблоны), SQLAlchemy + SQLite, bcrypt + python-jose, httpx для внешних API.

**Фронтенд:** Ванильный JS + чистый CSS в шаблонах. Никакого React, Node.js, сборщиков. Это не SPA.

**Иконки:** Lucide через CDN (`https://unpkg.com/lucide@latest`). Эмодзи в UI-элементах запрещены — см. `design-system.md`, раздел 8.

**ИИ (через OpenRouter API).**

Приоритет источников, от слабого к сильному: **дефолт в коде → `fly.toml [env]` → секрет Fly**. Секрет перекрывает всё, и `flyctl secrets list` показывает только имена, не значения — поэтому фактическое значение проверяется на машине:

```bash
flyctl ssh console -a energydess-tools -C "python -c \"import os;print(os.getenv('LETTER_MODEL'))\""
```

| Переменная | Дефолт в коде | `fly.toml [env]` | Секрет | **Работает на проде** |
|---|---|---|---|---|
| `LETTER_MODEL` | `opus-4-5` | — | `opus-4-8` | **`opus-4-8`** |
| `ANALYZE_MODEL` | `sonnet-4-5` | — | — | **`sonnet-4-5`** |
| `PARSER_MODEL` | `sonnet-4-5` | — | — | **`sonnet-4-5`** |
| `MODEL` | `haiku-4-5` | `haiku-4-5` | — | **`haiku-4-5`** |

Назначение: `LETTER_MODEL` — генерация сопроводительных писем; `ANALYZE_MODEL` — анализ вакансии и оценка релевантности; `PARSER_MODEL` — парсинг резюме в досье; `MODEL` — лёгкие задачи (нутриция, простые классификации).

**Правило:** одну переменную задавать в ОДНОМ месте. `LETTER_MODEL` намеренно убран из `fly.toml`: там лежало `sonnet-4-5`, тогда как секрет давал `opus-4-8` — файл противоречил реальности, и любой, кто прочитал бы его, ошибся бы в выводах.

### 2.1. Потолки ответа: все с именем, все замерены

**Правило: числа `max_tokens` на месте вызова в проекте нет ни одного.** Каждый
потолок — именованная константа в шапке `main.py` с переопределением из
окружения. Число на месте невидимо: его нельзя грепнуть, нельзя сверить
с расходом и нельзя поднять без передеплоя. Ровно так `/api/analyze-vacancy`
жил с захардкоженными `700`, пока таблица здесь утверждала, что лимит поднят
до 2000.

| Константа | Потолок | Что генерирует | Фактический расход (замер 2026-08-11) | Запас |
|---|---:|---|---:|---:|
| `ANALYZE_MAX_TOKENS` | 2000 | анализ вакансии, JSON из 9 полей | 552–958 | **2,1×** |
| `LETTER_MAX_TOKENS` | 3000 | письмо, 200–450 слов | 793 (письмо 2049 симв.) | **3,8×** |
| `PARSER_MAX_TOKENS` | 4000 | резюме → досье, JSON со всем опытом | 402 | **10×** |
| `PROGRAM_MAX_TOKENS` | 6000 | программа тренировок, 3–6 дней | не замерен | — |
| `CHAT_MAX_TOKENS` | 1000 | реплика ассистента (дневник, тренер) | ~110 (270 симв. в базе) | **9×** |
| `VISION_MAX_TOKENS` | 800 | разбор фото еды, распознавание тренажёра | не замерен | — |
| `FOOD_MAX_TOKENS` | 300 | КБЖУ продукта, JSON из 5 чисел | не замерен | — |

Замеры сняты настоящими вызовами через локальное приложение. Отношение
русского текста к токенам **уточнено 2026-08-11 на четырнадцати письмах
с прода**: 2,37–2,53 символа на токен, среднее **2,45**. Прежняя цифра
2,58 стояла по одному замеру (2049 / 793) и завышала запас на 5%.
Считались настоящим вызовом: текст уходит промптом с `max_tokens=1`,
читается `prompt_tokens`.
По нему считается худший разрешённый промптом случай: письмо в 450 слов —
это ~3150 символов, то есть ~1220 токенов. **Прежний потолок письма был 1500**,
и в худшем случае оставалось 19% запаса — а при структурированном ответе
на вопросы работодателя (промпт это разрешает) его не оставалось вовсе.
Обрыв письма при этом не диагностировался никак: `finish_reason` там
не читался, оборванное на середине фразы письмо отдавалось пользователю
и уезжало в историю как готовое.

Четыре потолка помечены «не замерен» честно: живого вызова с полными
входными данными для них в этот заход не было. Строка расхода в логе
(ниже) закрывает это без отдельной работы — первый же вызов на проде
напечатает число.

**`finish_reason` разбирается во всех девяти точках вызова, через один
`_model_output`.** Он же печатает расход **всегда**, а не только при обрыве:

```
[letter] finish=stop токенов=793 из 3000
[analyze] finish=length токенов=60 из 60   ← обрыв, наружу уходит 502 с внятным текстом
[parser] finish=stop токенов=1900 из 2000  ← ЗАПАС КОНЧАЕТСЯ (порог 80%)
```

Это единственный способ узнать фактический расход на проде: `usage`
нигде не сохраняется, и без строки в логе запас у потолка проверяется
рассуждением, а не замером. Метки: `analyze`, `letter`, `parser`,
`program`, `nut-chat`, `wk-chat`, `vision`, `food`.

Отрицательный тест проведён, а не только положительный: приложение поднято
с `ANALYZE_MAX_TOKENS=60 LETTER_MAX_TOKENS=60`, оба эндпоинта вернули 502
с человеческим текстом, в логе `finish=length` и число. Разбор самого
`_model_output` — `tests/test_model_output.py`, 9 тестов.

**Анализ вакансии живёт в ДВУХ местах, и правка одного не доезжает до второго.** Внутри `/api/generate-letter` (первый этап генерации) и отдельным эндпоинтом `/api/analyze-vacancy` за кнопкой «Проверить совпадение с резюме». Задача 8 подняла лимит и завела разбор `finish_reason` только в первом; второй до 2026-08-11 ходил в `LETTER_MODEL` с захардкоженными `max_tokens: 700` — то есть таблица выше про него **врала**, а пользователь получал `Unterminated string at line 22 column 5`. Замер: ответ анализа на живой вакансии занимает 958 токенов, при 700 модель обрывается на середине строки. Лимит поднимать не пришлось — 2000 хватает вдвое, чинить надо было второе место.

Правило на будущее: **меняете параметр вызова модели — грепните имя переменной по всему `main.py`, а не правьте то место, куда привёл стектрейс.** Обе команды ниже обязаны давать пусто:

```bash
grep -nE '"max_tokens":\s*[0-9]' main.py          # число на месте вызова
grep -n 'json()\["choices"\]' main.py             # разбор ответа мимо _model_output
```

### 2.2. Статика: адрес называет содержимое, иначе кеш вечным не бывает

**Правило: подключать `.css` и `.js` только через `{{ st('имя') }}`.**
Помощник отдаёт `/static/имя?v=<8 знаков sha256 от содержимого>`. Прямая
строка `/static/style.css` в шаблоне — долг; тест
`tests/test_static_cache.py` его ловит.

Отказ, который это лечит, дороже самой ошибки: правка CSS выкачена, файл
на сервере новый, замер на сервере чистый — а браузер рисует страницу
старым файлом, консоль пуста. Пользователь сообщает о дефекте, которого
уже нет. Любая визуальная приёмка при этом становится недостоверной.

**Замер 2026-08-14, до правки.** `Cache-Control` не отдавался НИ ДЛЯ
ОДНОГО типа файлов — ни css, ни js, ни svg, ни png, ни jpg; были только
`etag` и `last-modified`. По RFC 9111 §4.2.2 браузер в этом случае берёт
эвристику — примерно десятую часть возраста файла — и до её истечения
на сервер не ходит вовсе.

Вторая половина замера объясняет, почему окно оказывалось таким большим:
**на проде `last-modified` равен времени сборки образа и одинаков у всех
файлов сразу** (`Thu, 13 Aug 2026 16:47:52 GMT` у `style.css`, `ui.js`
и `og.png`). То есть возраст считается не от правки файла, а от
предыдущего деплоя, и окно показа старого файла равно его десятой части:
две недели без выкаток дают почти полтора суток слепоты.

**Три случая заголовка, а не два** (`_кеш_статики` в `main.py`):

| Запрос | Заголовок | Почему |
|---|---|---|
| `?v=` совпал с текущим хешем | `max-age=31536000, immutable` | по этому адресу содержимое больше не изменится по построению |
| `.css`/`.js` без версии или с чужой | `no-cache` | страховка: файл, который забыли пометить, не должен замерзать на год. Тело остаётся в кеше — `etag` даёт 304, а не повторную выкачку |
| прочее (картинки, svg) | `max-age=86400` | их правят заменой файла; ревалидация 1746 картинок упражнений на каждой открытой странице дороже суток устаревания |

Средняя строка — самая важная. Ставить `immutable` на любой запрос
к `/static/` значило бы заморозить у пользователя на год ровно тот файл,
который забыли переименовать, — и починить это было бы нечем.

**HTML получил `no-cache` тем же заходом, и без этого версия дырявая.**
Замер: страницы уходили без `Cache-Control` и без единого валидатора —
ни `etag`, ни `last-modified`. Браузер, отдавший из кеша старую разметку,
взял бы из неё старый `?v=`, а тот помечен `immutable`, — то есть
починенный CSS не приехал бы вообще ни по какому пути. Именно `no-cache`,
а не `no-store`: страницу можно хранить, нельзя брать оттуда без вопроса,
и `no-store` заодно выключил бы восстановление из bfcache в Firefox.

**Проверено живым браузером** с постоянным профилем (не инкогнито),
счёт запросов — по журналу сервера, потому что Playwright сообщает
о запросе и тогда, когда файл взят из кеша:

| Шаг | Запросов к `style.css` |
|---|---:|
| первая загрузка | 1 |
| ещё три захода, CSS не менялся | **0** |
| после правки CSS, обычная навигация без очистки кеша | 1, маркер в браузере новый |

**Про bfcache честно: под автоматизацией он не воспроизводится.** Возврат
«назад» дал `persisted=false` при `type='back_forward'`. Контроль на проде,
где `Cache-Control` на HTML ещё нет, дал **тот же** `persisted=false`, —
значит его гасит подключённый CDP, а не наш заголовок. Что до самого
поведения: bfcache восстанавливает уже отрисованную страницу целиком
и сети не касается по построению — это тот же документ, который человек
только что смотрел, а не «правка не доехала». Любая обычная навигация
после этого забирает новую версию.

### 2.3. `--nut-u` — единственное осознанное исключение из шкалы отступов

**Правило: десктопная раскладка дневника питания (ширина ≥900px) считается
кратными `--nut-u`, а не ступенями `--space-*`. Это исключение названо,
и оно одно. Переводить его на системную шкалу нельзя.**

Что это. Одна величина, объявленная на `<body>` страницы `/nutrition`
тремя ступенями:

```css
body { --nut-u: 1rem; }
@media (min-width: 1600px) { body { --nut-u: 1.1rem; } }
@media (min-width: 2200px) { body { --nut-u: 1.25rem; } }
```

От неё считаются ширина содержимого, кегли, кольцо калорий, высота
графика, отступы и высоты карточек — около сотни мест в
`static/nutrition.css` внутри `@media (min-width: 900px)`.

**Почему остаётся.** Шкала `--space-*` задана в пикселях и по построению
не растёт с шириной окна; корневой кегль растёт, но слабо — 16px на 1440
против 19px на 2560, шесть процентов при росте ширины на 78%. Раздел
на широком мониторе обязан расти целиком и в одной пропорции: ширина,
кегль, кольцо и отступы вместе. Разложить это по ступеням `--space-*`
значит зафиксировать отступы в пикселях при растущем вокруг них тексте —
то есть вернуть ровно ту болезнь, которую лечила задача 80 («не крупнее,
а реже»). Разбор и таблица замеров по трём ширинам —
`design-system.md` §10.7.

**Границы исключения — их три, и они проверяемые:**

| Граница | Что это значит |
|---|---|
| только внутри `@media (min-width: 900px)` | мобильная и базовая раскладка на `--space-*`, как весь остальной проект |
| только раскладка страницы | системные компоненты внутри — `.card`, `.chip`, `.input`, `.field-label`, `.segmented-btn` — сохраняют свои размеры. Страница растит **вокруг** них, а не их самих |
| токен не объявляется в `:root` | иначе страница, которая его задаёт, стала бы находкой проверки 2. Та же причина, что у `--app-aside`, `--undo-window` и `--meter-h` |

**Одно исключение, названное и объяснённое, лучше формально единой
системы с лишним слоем.** Обратный ход — завести в `:root` вторую,
масштабируемую шкалу отступов рядом с `--space-*` — дал бы две шкалы
на весь проект ради одной страницы, и следующий выбирал бы между ними
наугад.

**Деплой:** Fly.io, автодеплой через GitHub Actions на push в `main`.

(`hh.css`, `landing.css`, `nutrition.css`, `profile.css`, `workout.css`). Новую страницу
оформлять так же, а не наращивать `style.css` и не оставлять inline
`<style>` в шаблоне.

**Заводите новый страничный CSS — впишите его в переменную `pages` §6.0.2**
(так туда попал `workout_profile.css` 2026-08-06).
Проверки 1, 2 и 3 ходят по списку файлов, и файл, которого в списке нет, молча
выпадает из-под контроля: проверка продолжает печатать «чисто», просто
уже не про всё. Это тот же класс отказа, что и «немой сбой» из §6.0.1,

## 4. Темы разделов

Каждый раздел объявляет класс темы **на `<body>`** — не на `<main>`
и не на обёртке контента. Тема объявляет **четыре** токена и больше
ничего: `--tool-accent`, `--tool-accent-dim`, `--tool-accent-hover`
и `--tool-accent-ink` (цвет надписи на акцентной заливке). Вся остальная
механика — лесенка поверхностей, типографика, отступы, состояния —
наследуется из `:root`.

Четыре, а не два, с 2026-08-09: `BACKLOG.md`, задача 43. Акцент
не объявляется в одиночку — разделить заливку и надпись значит получить
белый текст на янтаре, 2.15. По той же причине классы `.theme-*` и `.tool-*`
объявлены в `style.css` **одним правилом на пару**.

| Раздел | Класс темы | Акцент | Иконка Lucide | Mono-label | Применён |
|---|---|---|---|---|---|
| HH-ассистент | `.theme-hh` | electric blue #4F8FFF | `Briefcase` | `КАРЬЕРА` | да, `<body>` |
| Дневник питания | `.theme-nutrition` | emerald #10B981 | `Salad` | `ПИТАНИЕ` | да, `<body>`, с 2026-08-09 |
| Тренировки | `.theme-workout` | amber #F59E0B | `Dumbbell` | `ТРЕНИРОВКИ` | да, `<body>`, обе страницы |
| Enshrouded | `.theme-enshrouded` | copper #D97706 | `Shield` | `ИГРЫ · ENSHROUDED` | **нет**, свои хардкоды |

Последняя колонка — не украшение. Тема, объявленная в таблице и
не применённая в коде, читается как «акцент раздела работает», а он
не разрешается ни во что, и отказ немой: свойство просто не применяется,
консоль чистая. Замерено 2026-08-06 на живом дереве. Дневник переведён
2026-08-09 (замер по шестнадцати элементам, включая все двенадцать
модалок, тост и меню вложений — везде `#10B981`). Enshrouded остаётся:
`BACKLOG.md`, задача 38, вторая половина.

**Замер переменной ≠ замер пикселя.** Тот же заход показал, что
`--tool-accent` у `.site-header` разрешался с 2026-08-06, а фокус-кольцо
поля поиска всё это время оставалось синим: правило
`.header-search .input:focus` в `style.css` било компонент по специфичности.
Документ полтора месяца утверждал обратное, потому что вывод сделали
из замера переменной и не проверили. Подробности — `design-system.md` §7.7.

**Почему именно `<body>`, а не `<main>`:** переменные наследуются вниз
по дереву, и объявление на `<main>` обрезает акцент по границе главного
блока — всё, что лежит рядом (оверлеи, лайтбоксы, тултипы, тосты,
припаркованные в конце `<body>`), темы не видит. Подробнее и с замерами —
`design-system.md`, раздел 7.7.

### 5.0. Вакансия hh берётся из JSON, а не из разметки

**Правило:** `/api/fetch-url` сначала пробует `_extract_hh_vacancy` — разбор
`<template id="HH-Lux-InitialState">`, — и только при неудаче откатывается
на общий обход тегов `_extract_text`. Порядок не менять, обход тегов
для hh не восстанавливать.

Причина. hh.ru — React-приложение: описание вакансии в отдаваемой сервером
разметке **не рендерится вовсе**, оно приезжает полем `vacancyView.description`
в JSON начального состояния. Общий обход тегов давал заголовок, куки-баннер
дважды и плашки «Опыт работы 1–3 года» — ни требований, ни обязанностей.

Отказ был немой и **выглядел как успех**: страница загрузилась, текст
извлёкся, счётчик показал «5 748 символов», зелёная галочка. Письма при
этом выходили приемлемые — модель домысливала по названию должности, —
то есть инструмент работал вопреки входным данным, и заметить это можно
было только прочитав, что именно уехало в модель.

| Что | Где | Замер 2026-08-11 |
|---|---|---|
| описание в DOM | `data-qa="vacancy-description"` | **отсутствует** |
| описание в JSON | `vacancyView.description`, экранировано дважды | есть, 5035 символов |
| старый разбор на архивной вакансии | `_extract_text` | 960 символов, описания ноль |
| новый разбор там же | `_extract_hh_vacancy` | 1139 символов, описание на месте |

Проверено на восьми вакансиях hh и rabota.by — все восемь идут по ветке
JSON. Клоны (`rabota.by`, `belarus.hh.ru`) отличать не надо: структура
одна, разбор берёт их тем же кодом.

**Вторая половина правила — проверка того, что разобралось.**
`_vacancy_quality` возвращает причину, по которой текст не похож на
описание (короткий; нет ни требований, ни обязанностей, ни одного длинного
абзаца), и она показывается **до** генерации отдельной плашкой
`.alert-warn`. Без неё любой следующий отказ разбора снова стал бы
«вроде что-то загрузилось»: единственный способ поймать немой отказ —
сверять содержимое, а не длину. Тесты — `tests/test_vacancy_parse.py`.

Чего проверка не ловит намеренно: вакансию, написанную прозой без слов
«требования» и «обязанности», она пропускает по длине абзаца — служебные
плашки всегда короткие. Ложная тревога здесь дороже пропуска: человек
перестанет читать плашку на третий раз.

**Зарплата берётся из поля `compensation` дословно, и «от»/«до» — часть
значения.** Односторонняя вилка (в JSON только `to`) без слова «до»
читается как точный оклад: замер 2026-08-12 на `hh.ru/vacancy/135237472` —
hh рисует «до 75 000 ₽», наш разбор отдавал «75 000 ₽ на руки».
Починено, тест в `tests/test_letter_language.py`.

Расхождение шапки разбора с телом описания при этом **нормально
и не является нашей ошибкой**: работодатель заполняет поле одним числом,
а в тексте пишет другое (замер на живых вакансиях: 78 000 в поле против
«78 300 рублей» в тексте; вилка 250 000–300 000 в поле против «оплата
на старте 250 000» в тексте). Сводить их нельзя — оба числа настоящие.

**Текст вакансии — данные, а не инструкции.** Разобранное описание
попадает в промпт как сведения о позиции; исполнять указания изнутри
него модели прямо запрещено (блок в `generate_letter`), а язык письма
решается до неё — §5.0.2.

### 5.0.2. Язык письма решается ДО модели и приходит к ней параметром

**Правило:** `_letter_language(job_text)` возвращает `ru` или `en`
детерминированно, по одному признаку — слово про сопроводительное письмо
и слово про английский **в одном предложении**. Решение показывается
переключателем, ручной выбор человека сильнее автоопределения, и в промпт
уезжает уже принятое решение.

Почему не «пусть модель поймёт из текста»: именно так язык письма
однажды и продиктовала вакансия — в ней стояло «пришлите сопроводительное
на английском», модель выполнила, письмо ушло не на том языке, которого
ждал автор. Указание внутри данных не должно управлять системой.

Почему признак сужен до одного предложения: «English B2» и «свободный
английский» стоят в половине IT-вакансий и о языке ПИСЬМА не говорят
ничего. Ложное срабатывание здесь дороже пропуска — человек получит
английское письмо на русскую вакансию и заметит это последним.

### 5.0.1. Удаление письма — пометка, а не DELETE. Срок записан в двух местах

**Правило:** удаление письма из истории ставит `cover_letters.deleted_at`,
и с этой секунды запись не попадает **ни в одну** пользовательскую выдачу:
история, счётчик в заголовке, `/api/search`, переход `?letter=N`, `PATCH`.
Физически строка стирается через `LETTER_PURGE_DAYS` (30) в
`_purge_deleted_letters`, который зовётся из выдачи истории.

Почему не удалять сразу: у удаления есть отмена на пять секунд. Держать
эти пять секунд отложенный запрос в браузере значит получить письмо,
которое осталось живым после закрытия вкладки, при полной уверенности
человека, что он его удалил, — немой отказ из §6.0.1 в чистом виде.

**Срок 30 дней записан ДВАЖДЫ**, и оба места правятся вместе:

| Файл | Где именно |
|---|---|
| `main.py` | константа `LETTER_PURGE_DAYS` рядом с `_purge_deleted_letters` |
| `main.py` | `STATIC_PAGES["privacy"]`, таблица «Сколько мы храним данные», строка «Письма, удалённые вами из истории» |

Ровно та же ловушка, что с retention снимков тома (§10): поменять одно
и забыть про второе значит молча превратить политику в неправду.

**Что окном отмены НЕ является.** «Ушёл со страницы — вернуть нельзя»
держит интерфейс: id удалённых писем живут в памяти вкладки. Сервер окно
не сторожит намеренно — для этого понадобились бы часы клиента,
а разошедшееся время превращало бы «Вернуть» в необъяснимую ошибку.

### 5.0.3. Ассистент дневника не сообщает о записи, которой не видел

**Правило:** текст «записал в дневник» составляется ТОЛЬКО из строк,
перечитанных из базы после `commit`. Пути, на котором подтверждение
печатается раньше чтения записи, в коде быть не должно.

Причина замерена. Модель на сообщение с тремя блюдами присылает три
блока `###FOOD_JSON###`, а `_extract_food_block` брал `search()` — первый —
и `sub()` вырезал из текста все. Наружу уходило одно блюдо, два исчезали
бесследно. Дальше модель видела в истории собственную реплику
с описанием блюда, принимала её за сделанную работу и на вопрос про
второе отвечала, что уже добавила. Дневник при этом был пуст.

Три следствия, которые вместе и составляют правило:

| Что | Где |
|---|---|
| разбираются ВСЕ блоки | `_extract_food_blocks`, `finditer` |
| решение о записи принимает человек, а не модель | набор карточек в чате, правка и удаление до сохранения |
| подтверждение читается из базы | `/nutrition/api/ai-chat/log-foods`: `flush` → `commit` → `SELECT` по id → текст |

Не записанное называется поимённо. «Сохранено 2 из 3» без имён — тот же
немой отказ (§6.0.1), только с числом.

**Числа норм и съеденного модель не считает.** Они приходят в промпт
из `nut_goals` — той же функции, что питает `/nutrition/api/diary`,
чтобы кольцо на экране и реплика ассистента не могли разойтись.
На возражение пользователя с другим числом модель обязана назвать
данные, а не согласиться: замер 2026-08-13 показал, что до правки
она соглашалась мгновенно («Понял, значит, ваша норма — 95 г»
при 150 г в анкете), и согласилась бы точно так же, если бы ошибался
пользователь.

### 5.0.4. Вкладка на экране «Добавить» — это ОБЛАСТЬ поиска

**Правило:** запрос всегда исполняется внутри выбранной области, а сама
область названа вслух — подсветкой вкладки и подсказкой в поле. Областей
четыре: вся база, недавние, частые, мои рецепты. Адрес запроса берётся
из одной таблицы (`АДРЕС_ОБЛАСТИ` в `nutrition.html`), рядом с той же
вкладкой.

До 2026-08-14 вкладка задавала, ЧТО показано, и не задавала, где ищется:
человек стоял в «Частых», вводил запрос и получал находки из всего
справочника. Прежнее лечение — снимать подсветку с вкладок на время
показа находок — лечило признак: вкладка переставала врать тем, что
замолкала. Теперь она права и молчать не должна, поэтому **подсветка
на время поиска НЕ снимается**, и это сознательный откат прежнего
решения. Без неё «нашлось три штуки» не отвечает на вопрос «три штуки
где».

**Пусто в узкой области — не то же самое, что пусто везде, и подставлять
одно вместо другого запрещено.** Экран говорит оба факта и даёт перейти:

```
В недавних ничего не нашлось
Во всей базе — 20 продуктов        [ Искать по всей базе → ]
```

Число берётся НАСТОЯЩИМ запросом ко всей базе, а не оценивается: на него
нажмут. Переход область меняет, а запрос сохраняет — иначе кнопка
приводила бы на пустой экран, обещав обратное.

**Пустое поле в области «Вся база» показывает НЕДАВНЕЕ, а не приглашение.**
Это правка 2026-08-15 и откат прежнего решения («справочник ищут, а не
листают»). Плата за прежнее была названа верно и оказалась слишком
большой: экран встречал двумя заглушками сразу — «Начните вводить
название» слева и «Выберите продукт слева» в панели справа — и полутора
экранами пустоты.

Логику областей это не ломает, и вот почему: **область задаёт, где ищет
ЗАПРОС**, а запроса тут нет. Первый же введённый знак уходит
в `/nutrition/api/search`, то есть во всю базу, ровно как обещают
подсветка вкладки и подсказка в поле. Подменой области это было бы
только в одном случае — если бы поиск по введённому тексту пошёл
в недавние.

Заголовок над блоками обязателен («Недавнее — начните вводить, чтобы
искать по всей базе»). Недавние, показанные без подписи в области «Вся
база», читались бы как выдача справочника, и человек решил бы, что в базе
двенадцать продуктов. Недавних нет вовсе — тогда приглашение, и это НЕ то
же самое, что «поиск ничего не нашёл»: искать ещё нечего.

**Отбор по запросу делает сервер, и сравнение идёт в Python** —
`_нут_совпало`. `ilike` в SQLite не приводит кириллицу к нижнему
регистру, и «Творог» не нашёлся бы по «творог»: выдача вышла бы пустой
и выглядела бы как «у вас такого не было», а не как ошибка. Та же
причина, по которой так устроен `/nutrition/api/search`.

**«Недавние» раскладываются по приёмам пищи, «Частые» — нет.** Ключ
дедупликации в `by_meal` включает приём: одно блюдо, съеденное и на
завтрак, и на ужин, попадает в оба блока. Схлопнув их по имени, выдача
утверждала бы, что творог едят только на завтрак — там, где его съели
первым. Приём, в который ни разу ничего не вносили, не показывается
вовсе. «Частые» — единый топ по числу добавлений за всё время, и само
число видно в карточке: правило сортировки, которого не видно, читается
как случайный порядок.

Плоский список `results` у `/nutrition/api/recent-foods` остался рядом
с `by_meal` и не заменён им: его читает окно подбора ингредиента рецепта,
где приём пищи не значит ничего.

### 5.0.7. Бренд весит меньше названия, а дубли считаются по видимому

**Правило: запись, совпавшая с запросом ТОЛЬКО брендом, в основную выдачу
не попадает — она уезжает в подписанную сворачиваемую секцию под ней.
И две записи, у которых совпало всё, что видно в карточке, — это одна
карточка, чем бы они ни отличались внутри.**

Замер 2026-08-16, «молоко простоквашино»: восемнадцать находок, шесть
молок и двенадцать карточек остального ассортимента бренда. В ранжировании
стоял ключ `(-совпало, -в_названии)` — сколько слов совпало ХОТЬ ГДЕ
решало первым, то есть бренд весил столько же, сколько название.

| | было | стало |
|---|---:|---:|
| «молоко простоквашино» — в основной | 18 (+1 дубль) | **6** |
| то же — в секции бренда | — | 12 |
| «гречка увелка» — основная / секция | 20 / — | **7** / 13 |
| «сметана простоквашино» | 18 / — | **9** / 9 |
| «творог» (одно слово) | 21 / — | 21 / — |

**Брендовое слово опознаётся структурно, и порога по доле здесь НЕТ.**
Первая версия считала долю записей, у которых слово стоит в поле `brands`.
Замер по пятнадцати запросам показал, что доли не разделяются: бренды дают
0.21 («ламбер»), 0.50 («активиа»), 1.00 («простоквашино»), а НЕ бренды —
0.17 («шоколад»), 0.30 («йогурт»), 0.33 («творог»). Любой порог либо
пропускает «Ламбер», либо объявляет брендом «творог» — а последнее увело бы
в секцию бренда весь творог по запросу «творог» (у восьми записей из
двадцати четырёх поле `brands` буквально равно «творог», мусор справочника).

Признак вместо порога: слово брендовое, если оно **ни разу не встретилось
в названии, очищенном от собственного бренда записи**, но встретилось
в поле бренда. «Простоквашино» в «Сметана Простоквашино 15%» из счёта
вычитается — это бренд, напечатанный в названии; «творог» в «Творог 9%»
не вычитается (бренд там другой), поэтому брендовым словом не станет.

Цена названа: правило **молчит**, когда бренд встречается и в названиях без
поля `brands` («шоколад алёнка», «сыр ламбер», «йогурт активиа» секции
не дают). Это пропуск, а не ложь: секции просто нет, выдача прежняя,
из неё ничего не исчезает. Ошибка в обратную сторону дороже — она прячет
искомое.

Три ограничителя, без которых правило вредит:

| Ограничитель | Что было бы без него |
|---|---|
| единственное слово запроса брендовым не объявляется никогда | «творог» → основная пуста, «по названию ничего не нашлось» про запрос, по которому нашлось всё |
| хотя бы одно слово обязано остаться продуктовым | «домик деревне» → делить выдачу не на что |
| свой продукт пользователя в секцию не уезжает | спрятали бы под сворачиваемый заголовок ровно то, что человек завёл руками |

**Склейка дублей теперь ДВЕ, и это не дублирование.** `_склеить_дубли`
идёт по штрих-коду внутри `_off_search`; `_склеить_видимые` — по тому, что
написано в карточке, и уже на общем списке. Мимо первой проходил главный
случай: свой продукт человека собирается ПОСЛЕ `_off_search` и в склейку
по коду не попадает вовсе. Замер: аккаунт со своим «Молоко Простоквашино
2.5%» получал по этому запросу две одинаковые карточки — 19 против 18
после правки. Ключ повторяет `подписьПродукта` буквально, включая то, что
объём упаковки виден ТОЛЬКО у записи без бренда: две такие записи человек
различает, и склеивать их нельзя.

Переживает первая по порядку, недостающие поля добираются у близнецов —
то же правило, что у склейки по коду, и следствие полезно: свой продукт
в списке идёт раньше справочника, значит исчезает чужая запись, а не своя.

### 5.0.5. Налитая вода удаляется поштучно, и отказ отличим от успеха

**Правило:** `DELETE /nutrition/api/water/{id}` отвечает **404**, когда
удалять нечего, и возвращает дату записи вместе с новым итогом дня.

Прежний ответ был `{"ok": true}` на любой исход — и на удаление, и на
чужой id, и на несуществующий. Снаружи все три выглядели одинаково:
интерфейс рисовал успех, а в базе всё оставалось на месте. Чужая запись
даёт тот же 404, а не 403: отказ по правам подтвердил бы, что она
существует (§5.1).

Итог дня считает сервер и отдаёт в ответе. Вычитание на клиенте показало
бы новую сумму и тогда, когда запись не удалилась.

**Почему список порций, а не «отменить последнюю» и не правка итога.**
Порции льются по одной кнопке, за день их набирается десяток, и ошибочные
500 мл обнаруживаются вечером — отменять пришлось бы всё, что налито
после. Правка итога числом стирает историю: 1500 вместо 2000 не говорит,
какая порция была лишней.

**Времени у порции не показываем, и это решение.** `water_logs.created_at`
пишется в UTC, а человек живёт в своём поясе: «14:32» под порцией,
налитой в 17:32, — тихая неправда. Опознавать порцию по времени и не
нужно: у неё нет ничего, кроме объёма, и удаление любых «200 мл» из двух
даёт один и тот же итог.

### 5.0.6. «Сегодня» дневника — в поясе пользователя, и источник у него ОДИН

**Правило:** текущий день дневника считает сервер функцией `_сегодня(user)`
по `users.timezone`. Ни `datetime.now()` на месте вызова, ни `new Date()`
в браузере вторым мнением о дне быть не должны.

Отказ был двойной и весь молчащий. Сервер брал день через `datetime.now()`,
то есть в поясе процесса, а на Fly это UTC; браузер рисовал дату
в сайдбаре через `toLocaleDateString()`, то есть по часам устройства.
Воспроизведено живым прогоном 2026-08-15 в 00:57 по Москве:

| Место | Показывало | Откуда брало |
|---|---|---|
| сайдбар и шапка | «Сб, 15 Авг.» | часы браузера |
| полоска дней, «сегодня» | 14-е | `datetime.now()` сервера = UTC |
| подпись под полоской | «Сегодня, 14 августа» | оттуда же |
| 15-е в полоске | будущий день, пунктир | оттуда же |

То есть две даты на одном экране расходились на сутки, обе выглядели
настоящими, и записать еду в текущие по местным часам сутки можно было
только через «будущий» день, где кольцо говорит «запланировано».

Четыре следствия правки, каждое — отдельное решение:

| Что | Как | Почему не иначе |
|---|---|---|
| день считает сервер | `_сегодня(user)` | у клиента нет права решать, куда ляжет `log_date` |
| момент отделён от пояса | `_день_в_поясе(момент, зона)` | иначе граница суток не проверяется тестом: прогон в три часа дня о поведении в 00:30 не говорит ничего |
| `сегодня` — обязательный аргумент `_нут_дата` | не умолчание | умолчание вернуло бы UTC любому, кто забыл его передать, и починка держалась бы на внимательности каждого следующего вызова |
| день уезжает В РАЗМЕТКУ (`nut_today`) | а не только ответом `/diary-days` | до первого ответа экран уже нарисован, и правка «сегодня» задним числом означала бы мигание даты на глазах |

**Пояс, которого нет в профиле, определяется браузером ОДИН раз.** Замер
по боевой схеме: `users.timezone` заполнен у двух аккаунтов из десяти —
то есть без этого починка не доехала бы до восьмерых и выглядела бы
сделанной. Берётся `Intl…timeZone`, отправляется в `/api/timezone`
(та же проверка по списку, что у профиля) и только когда в профиле пусто.
Дальше главным остаётся сохранённое значение.

Отказ этого шага не проглатывается: зона не из нашего списка даёт 400,
и причина печатается в консоль. Принять её значило бы записать пояс,
которого нет в выпадающем списке профиля, — и профиль показывал бы
человеку не то, что записано.

**Чего правка НЕ закрывает.** Зоны вне `TIMEZONES` (список из ~40 имён):
`Europe/Amsterdam` определится, но принят не будет, и такой человек
останется на UTC до ручного выбора в профиле. Расширение списка —
решение продуктовое, а не техническое.

**Браузерных дат на странице не осталось — 2026-08-17.** Тут стояло
«`histDate` в истории по-прежнему считается браузером, история правится
отдельным заходом». Заход состоялся, и мест оказалось **два**, а не одно:

| Где | Что считало | Как это выглядело |
|---|---|---|
| вкладка «История», `S.histDate` | `new Date().toISOString()` — день по UTC | замер 2026-08-17, 00:34 MSK: сайдбар «Пн, 17 Авг.», история рядом «Вс, 16 Авг.» |
| загрузка фото прогресса, `uploadBodyPhotos` | то же | снимок, сделанный в час ночи, ложился во вчерашнюю дату |

Второе не искали — его нашла проверка, у которой сняли исключение:
тест `test_страница_дневника_отдаёт_серверное_сегодня` обрывал файл
на слове `histDate`, потому что там жило законное исключение. Исключение
закрыли, обрыв убрали, и проверка тут же назвала второе место. Это
и есть довод в пользу узких исключений с именем: пока оно записано,
за ним прячется всё, что стоит ниже по файлу.

**Своей даты у истории больше нет вовсе.** Не «считается правильно»,
а нет поля: вкладка показывает `S.date` — тот же выбранный день, что
дневник, подпись «запись пойдёт в…» и `POST /log-food`. Два поля означали
бы, что человек правит один день, а видит другой, и признака этого
не было бы никакого — оба экрана рисуют одинаково правдоподобно.

**Существующие записи правка не трогает.** `log_date` — текстовая колонка,
миграций по ней нет ни одной, отпечаток всех значений до и после правки
совпадает. Меняется только то, какой день считается сегодняшним.

### 5.0.8. Окно чтения дневника и окно записи — РАЗНЫЕ

**Правило: `/nutrition/api/diary` смотрит назад без предела
(`назад=None`), запись назад ограничена `NUT_EDIT_BACK` (365 дней),
вперёд обе — `NUT_DAY_RANGE` (7). Умолчания `_нут_дата` остались
прежними: вызов, не назвавший границы, ведёт себя ровно как до правки.**

До 2026-08-17 окно было одно, ±7, и это было верно ровно до тех пор,
пока история умела ходить теми же стрелками, что полоска дней. Календарь
месяца задал второй вопрос — «какой день можно ОТКРЫТЬ», — и ответ «семь»
на него неверен: дневник заводят, чтобы смотреть назад.

**Отказ был немой и показывал ЧУЖИЕ данные.** Замер до правки, восемь
нажатий «‹» подряд:

```
клик 6: histDate=2026-08-10  подпись='Пн, 10 Авг.'  ккал='3266'
клик 7: histDate=2026-08-09  подпись='Вс, 9 Авг.'   ккал='3266'   ← 400 от сервера
клик 8: histDate=2026-08-08  подпись='Сб, 8 Авг.'   ккал='3266'
```

Сервер отвечал 400, `loadHistory` этого не проверял, `data.totals`
падал `TypeError` (три ошибки в консоли), и на экране оставались числа
предыдущего дня. Подпись при этом менялась — она считалась на клиенте.
То есть экран УТВЕРЖДАЛ, что 9 августа съедено 3266 ккал, и это было
число 10-го.

Год для записи — не «сколько разрешено», а «дальше это заведомо
опечатка»: дата 1999 года в теле запроса — мусор, а не намерение.
И сообщение об отказе теперь называет сторону: «не дальше 7 дней вперёд»
против «в пределах 365 дней назад». Одинаковый текст на оба случая
заставлял бы искать не там — одно чинится календарём, другое не чинится
ничем.

### 5.1. Отдача чужих файлов: исключений для админа нет

`/avatar/{user_id}` и будущий `/media/{kind}/{token}` отдают файл **только
владельцу**. Ветки «а администратору можно» там нет и появляться не должна.

Причина не в паранойе, а в согласованности с документом: политика
конфиденциальности прямо говорит, что письма, дневники, измерения,
фотографии и переписка с ассистентами в служебном интерфейсе
не отображаются. Появится обход по `is_admin` — политика станет неверной
в ту же секунду и молча, потому что читать её никто заново не станет.

Проверка при code review одна: в обработчике отдачи медиа сравнивается
`запись.user_id == user.id`, и больше ничего. Не совпало — **404**, а не
403: отказ по правам подтверждает, что файл существует.

Понадобится служебный экран с чужими файлами — сначала правка политики,
потом код, а не наоборот.

### 5.2. Вход в Zepp Life — родная схема. Аккаунт Xiaomi удалён

Про умные весы, но правило общее для любых учётных данных третьей стороны.

#### СХЕМА ОДНА, И ЭТО НЕ ОСТОРОЖНОСТЬ, А УСЛОВИЕ РАЗБОРА

**Вход через аккаунт Xiaomi удалён 2026-08-14 целиком** — не отключён
флагом, не оставлен запасным, не выбирается автоматически. Осталась
родная схема Huami: почта и пароль аккаунта Zepp Life.

Почему удалён. Живой пользователь прошёл круг дважды: вход → «подтвердите
личность» → проверка по ссылке с кодом из почты → `{"code":404,"message":
"routes not found"}` → повторный вход → снова «подтвердите личность».
Второй круг пройден уже ПОСЛЕ починки постоянного `device_id`, то есть
объяснение «мы каждый раз предъявляли новое устройство» исчерпано.
Отметку «устройству доверяем» Xiaomi привязывает к сессии браузера,
в котором человек проходил проверку, и на наш сервер она не переносится:
поток рассчитан на собственные приложения Xiaomi.

Почему нельзя было оставить запасной веткой: **почта у пользователя
на аккаунте Xiaomi и на аккаунте Zepp Life одна и та же.** Выбрать схему
по адресу невозможно, а любой автовыбор вернул бы в тот же круг — и,
что важнее, сделал бы неотличимым «не та схема» от «что-то ещё». Это тот
же класс отказа, что `|| true` в §6.0.1: диагностика, которая не может
ошибиться в нашу пользу, потому что ответа не даёт вовсе.

#### ЧЕМ РОДНАЯ СХЕМА ОТЛИЧАЕТСЯ ПО УСТРОЙСТВУ

Браузер пользователя в обмене **не участвует**: два серверных POST через
httpx с `follow_redirects=False`, ответ читается из заголовка `Location`.
Проверки личности в схеме нет — ни капчи, ни кода из почты, ни страницы
Xiaomi.

| | схема Xiaomi (удалена) | родная схема Zepp Life |
|---|---|---|
| шагов | 4 (authorize → oauthLogin → serviceLoginAuth2 → 3 редиректа → client/login) | 2 (tokens → client/login) |
| браузер человека | ведёт его на страницу Xiaomi | не участвует |
| проверка личности | есть, и стороннему приложению недоступна | нет |
| `third_name` | `xiaomi-hm-mifit` | `huami` |
| формат ответа | `&&&START&&&` + JSON | 303 + параметры в `Location` |
| наш `redirect_uri` | **упирался в него браузер человека** — там 404 | эхо в заголовке, не открывается никем |

Последняя строка — про то, из-за чего вся история. 404 в конце проверки
отдавал НАШ же `redirect_uri` (`api-mifit-cn.huami.com/huami.health.
loginview.do`), адрес возврата в мобильное приложение Zepp, которого
у нас нет. В родной схеме `redirect_uri` тоже обязателен (без него 400,
проверено), но его никто не открывает: мы читаем заголовок и по адресу
не ходим. Проверено подстановкой своего адреса — ответ не изменился.

#### ЗАМЕРЫ ФОРМЫ ОТВЕТОВ (2026-08-14, живые запросы)

Учётных данных у разработчика нет, поэтому замеры сняты заведомо
несуществующим адресом — форму отказа это показывает полностью.

```
POST https://api-user.zepp.com/registrations/{почта}/tokens
  верные данные  → 303, Location …?access=<токен>&country_code=..&region=..
  неверные       → 303, Location …?error=401&state=REDIRECTION&region=eu-central-1
  кривой запрос  → 400, тело '"HuaMi Oauth / User Registration 2.0.2"'
POST https://account.zepp.com/v2/client/login
  негодный code  → 400, тело {"error_code":"0104"}
GET  https://api-mifit.zepp.com/users/{id}/members/-1/weightRecords
  негодный токен → 401, {"code":0,"message":"invalid token","data":{"code":"0102"}}
```

Отдельно проверено: `account.huami.com` маршрута `/registrations` не имеет
(404), домены `zepp.com` и `huami.com` в остальном отвечают одинаково,
`client_id=HuaMi` обязателен.

#### КЛАССЫ ОТКАЗА: ЧЕТЫРЕ, И НИ ОДИН НЕ ГОВОРИТ ЛИШНЕГО

| Класс | Когда | Что делать человеку |
|---|---|---|
| `ZeppAuthError` | шаг tokens вернул `error=401` | проверить почту и пароль |
| `ZeppStepError` | всё, что после полученного кода доступа | ничего: чинится правкой `zepp_client.py` |
| `ZeppProtocolError` | не 303, нет `Location`, ни `access`, ни `error`, **незнакомый код** | то же |
| `httpx.HTTPError` | сеть | попробовать позже |

`ZeppVerificationError` **удалён**: его порождала только схема Xiaomi.
Если родная схема однажды всё же пришлёт что-то похожее, это будет
`ZeppProtocolError` с настоящим кодом, а не наша догадка про капчу.

Два правила разбора пережили смену схемы целиком:

- **Незнакомый код не схлопывается в «неверный пароль».** Иначе следующая
  причина отказа стала бы неотличима от опечатки, и разбирать её было бы
  нечем.
- **Ниже принятого пароля ни одна ветка не говорит про пароль.** Код
  доступа получен — значит, пароль проверен и принят; всё, что сломалось
  дальше, к нему отношения не имеет.

#### ХОСТ ДАННЫХ ХРАНИТСЯ, ИНАЧЕ 401 ЧИТАЕТСЯ КАК «ПРОТУХ ТОКЕН»

Ответ шага входа несёт поле `domains` — где лежат данные ИМЕННО ЭТОГО
аккаунта. Оно сохраняется в `scale_connections.data_host`, и вот почему
колонка, а не константа: вход бывает **один раз**, пароль не хранится, —
не сохранив хост, мы потеряли бы его немедленно.

Замер показал, что снаружи регион не определяется ничем: `api-mifit.zepp.com`,
`api-mifit-de2.zepp.com`, `api-mifit-us2.zepp.com` и их пары на `huami.com`
отвечают на негодный токен побайтово одинаково. То есть проверить догадку
о хосте было бы нечем, а ошибка в ней дала бы 401 на ЖИВОМ токене — у нас
это означает «токен протух», то есть просьбу ввести пароль заново.
По кругу и без единого признака, что дело не в пароле (§6.0.1).

#### ХРАНЕНИЕ: ПАРОЛЬ ОДИН РАЗ И НИКОГДА В БАЗУ

**Пароль используется один раз — обменять на токен — и не сохраняется.**
До 2026-08-13 он лежал в `scale_connections.encrypted_password` (Fernet)
ради одного: автоматически перелогиниться, когда протух токен. Цена —
пароль от чужого аккаунта в нашей базе, у которого нет ни срока,
ни отзыва, тогда как у токена есть и то и другое. Плата за отказ известна
и принята: протух токен — статус `reauth` и просьба ввести пароль заново,
сами перелогиниться мы не можем.

Поля очищаются **сразу после отправки**, до ответа сервера, и `type`
возвращается в `password` — иначе открытый глазком пароль переживал бы
переключение вкладок. Почта остаётся: она не секрет, а стирать её значит
заставлять набирать адрес заново на каждой повторной попытке.

#### ЧТО ПОПАДЁТ В ЛОГ НА СЛЕДУЮЩЕЙ ПОПЫТКЕ

Форма ответа каждого шага — коды и **имена** непустых полей. Именно имена:
в ответах лежат `access`, `app_token`, `login_token` — ключи к чужому
аккаунту, и печатать их значит положить их в лог, который читают глазами
и пересылают. Значения от сервиса печатаются через `ascii()`: сервис
отвечает и по-китайски, а на консоли cp1251 обычный `!r` роняет `print`
и валит им весь вход (§6.0.1 наизнанку — диагностика ломает то, что
диагностирует).

```
[zepp] устройство …37:0a (постоянное для пользователя)
[zepp] tokens: HTTP 303 location=есть
[zepp] tokens: непустые поля (3): error, region, state | error='401' region='eu-central-1'
[zepp] domains в ответе (3): api-mifit=…, api-user=…; хост данных = …
[zepp] выборка с <хост>: страниц 1, записей получено 42, годных 40, отброшено …
```

#### СОСТАВ ТЕЛА: СПИСОК ПЕЧАТАЕТ ПЕРВАЯ ЖЕ УСПЕШНАЯ ВЫБОРКА

Живого ответа у нас нет — аккаунт весов только у владельца, — поэтому
список показателей брался из чужого репозитория и принимался на веру.
Теперь выборка печатает **три** строки, а не одну, и третья важнее всех:

```
[zepp] поля summary в ответе (N): bmi, bodyWaterRate, boneMass, fatRate, …
[zepp] из них мы НЕ разбираем (N): …
[zepp] мы ждём, а их нет (N): …
```

Разбираются девять величин: вес, ИМТ, процент жира, процент воды, процент
мышц, костная масса, висцеральный жир, основной обмен, «возраст тела»
(в API он называется `muscleAge`). **Идеального веса в ответе нет** — если
он понадобится, его придётся считать самим по росту, и это будет наше
число, а не показание весов.

#### ПУСТАЯ ИСТОРИЯ И СБОЙ РАЗЛИЧАЮТСЯ

`fetch_weight_records` возвращает словарь, а не список, и это не
косметика. Пустой список отвечал сразу на два разных вопроса — «измерений
в аккаунте нет» и «измерения есть, но ничего не разобралось», — а
в интерфейсе оба выглядели как «синхронизировано: 0».

| Случай | Что происходит | Что видит человек |
|---|---|---|
| история пуста | `total = 0`, статус `ok`, строка в лог «это НЕ сбой» | «измерений пока нет — встаньте на весы» |
| нет поля `items` вовсе | `ZeppProtocolError` | «сервис ответил не так, как мы ожидаем» |
| записи есть, все отброшены | видно в `dropped` и в логе | «новых измерений нет» |
| 401 на выборке | `ZeppApiError` → `reauth` | «сессия истекла, введите пароль» |

**Измерения, сделанные ДО привязки весов, подтягиваются** — сервис отдаёт
всю историю аккаунта, до 30 последних записей. Три вещи, которые на этом
и вылезли (все три — молчащие, замеры в `tests/test_scale_sync.py`):

- запись, заведённая в приложении руками, приходит с `summary: null`.
  `item.get("summary", {})` значение по умолчанию НЕ применяет, когда ключ
  есть и равен `null`, — прежний код падал на ней `AttributeError` и ронял
  синхронизацию целиком;
- два взвешивания за один день давали **две строки дневника на одну дату**:
  сессия открыта с `autoflush=False`, и добавленная через `db.add()` строка
  не видна собственному же запросу (замер: id 13 = 81.0 и id 14 = 79.0
  за одну дату);
- из этих двух в дневник попадало **самое старое**: сервис отдаёт записи
  новейшими вперёд, и последним применялось утреннее взвешивание.

Ручная запись пользователя за ту же дату не перетирается — это было
и осталось.

### 5.3. Гейт подтверждённой почты — ОДИН middleware, а не проверка в каждом

**Правило: непроверенный аккаунт не записывает ничего. Заслон стоит
в одном месте — `гейт_подтверждения_почты` в `main.py`, — и новый
эндпоинт получает его в момент появления, не делая ничего.**

Почему не зависимостью в каждом обработчике: зависимость, которую надо
не забыть дописать, — это гарантия, что следующий эндпоинт её не получит,
и **никто этого не заметит**. Отказа нет, ошибки нет, запись проходит.

Ровно так и было до 2026-08-18. `_verification_gate` стоял на четырёх
страницах инструментов — и **ни на одном из 59 эндпоинтов записи**. Дверь
заперта, окна открыты. Замер живыми запросами до правки: непроверенный
аккаунт записал воду, вес, свой продукт, анкету тренировок, досье HH,
часовой пояс и слот Enshrouded — семь запросов, семь ответов 200,
и вода после трёх прогонов накопилась до 600 мл.

| Что | Как |
|---|---|
| где стоит | `main.py`, `@app.middleware("http")`, до `log_request` |
| что закрывает | `POST`, `PUT`, `PATCH`, `DELETE` — `ГЕЙТ_МЕТОДЫ` |
| код отказа | **428** Precondition Required (`ГЕЙТ_КОД`) |
| исключения | `ГЕЙТ_ИСКЛЮЧЕНИЯ_ТОЧНО` и `ГЕЙТ_ИСКЛЮЧЕНИЯ_ПРЕФИКС`, с причиной у каждой строки |

**428, а не 401 и не 403, и это выбор, а не вкус.** 401 значит
«представьтесь» — человек представился, сессия рабочая, и он пойдёт
вводить пароль заново. 403 значит «вам нельзя» — читается как бан,
и человек пойдёт в поддержку вместо того, чтобы открыть почту. 428 значит
ровно происходящее: доступ откроется, как только выполнено названное
условие. Клиент при этом отличает случай по коду, не разбирая тело.

**Форма ответа зависит от `Accept`.** Браузерная форма (`text/html`)
получает 303 на `/verify-pending` — JSON в адресной строке человек
не прочитает; `fetch` получает 428 с `code: "email_not_verified"`.

**GET не закрывается намеренно.** Чтение непроверенному оставлено: он
должен видеть, куда попал и что подтвердить. Страницы инструментов и так
закрыты плашкой `_verification_gate`. Единственный пишущий GET —
`/verify/{token}`, само подтверждение, — в исключениях.

#### ПЕРВОЕ, ЧТО ЛОМАЕТСЯ У НЕАККУРАТНОГО ГЕЙТА, — ПУТЬ ПОДТВЕРЖДЕНИЯ

Закрой гейтом `/verify/{token}` или `/resend-verification` — и аккаунт
**заперт насмерть**: войти и увидеть плашку человек может, а подтвердить
почту ему нечем. Отказ при этом немой: ошибки нет, просто круг.

Поэтому список исключений — именно список **исключений с причинами**,
а не «всё, что не подошло», и на каждую строку в нём есть тест
(`tests/test_verify_gate.py`, 29 проверок).

**Список живёт в ОДНОМ месте.** `check_endpoints.py` спрашивает
`main._гейт_путь_исключён`, а не держит копию: две копии разошлись бы
молча, и опись начала бы утверждать, что эндпоинт закрыт, когда он
открыт, — то есть ровно ту ложь, ради поиска которой опись существует.
На это тоже есть тест.

#### ОПИСЬ ЭНДПОИНТОВ: `py check_endpoints.py`

Полная таблица маршрутов приложения — путь, метод, пишет или читает, чем
защищён, к какому разделу относится. **Обходом `app.routes`, а не грепом
по декораторам**, и разница не косметическая: греп видит 120 маршрутов,
приложение обслуживает 130. В разнице — пять настоящих эндпоинтов
(`@app.api_route` и роутер `agent_slots`) плюс пять служебных FastAPI.
Скрипт печатает оба числа и **раскладывает расхождение поимённо**:
выбрать меньшее молча значит потерять из виду то, что принимает запросы.

Код возврата: 0 — эндпоинтов записи без гейта нет, 1 — есть и названы.

## 6. Правила работы с кодом

- Разбивать работу по фазам, отчёт после каждой, всегда показывать реальный код (не summary).
- Перед добавлением UI-элемента — проверить, есть ли уже такой в `design-system.md`, раздел 2 «Компонентная база». Если есть — использовать существующий класс. Если нет — сначала обсудить, что за компонент, и добавить в дизайн-систему.
- CSS-переменные — только из `design-system.md`, раздел 13. Никаких новых токенов без обсуждения.
- Хардкод-цвета в HTML/CSS — запрещены. Всё через переменные.
- Хардкод-размеры шрифтов и отступов — запрещены. Всё через шкалу (`--text-*`, `--space-*`) или `clamp()`.
- Inline `<style>` в шаблонах Jinja2 — по возможности избегать. Общее — в `style.css`. Если нужен uniquely-page стиль — оформлять в отдельный `<style>`-блок в начале шаблона с комментарием «TODO: перенести в модульный CSS».

### 6.0. Кириллица ломает shell и jq. Латиница в машинном слое

**Правило:** всё, что читает не Python, — только ASCII. Имена переменных
bash, ключи JSON, которые разбирает `jq`, имена файлов в командах.
Комментарии и текст для человека остаются русскими.

Почему это отдельный раздел, а не строка в шапке workflow: там
предупреждение уже висело, и за одну сессию я наступил на те же грабли
**пять раз** — в тесте, в диагностике, в отпечатке справочника. Значит
место было выбрано неудачно. Здесь оно попадается при написании кода,
а не при чтении файла целиком.

| Где | Что ломается | Симптом |
|---|---|---|
| имя переменной bash | `вывод=$(...)` | `вывод=Connecting: command not found`, код 127 |
| ключ JSON под `jq` | `.хеш` | `jq: error: syntax error, unexpected INVALID_CHARACTER` |
| `jq` с кириллицей всё же нужен | — | только через `.["хеш"]`, но лучше переименовать |
| `bytes`-литерал в Python | `b"текст"` | `SyntaxError: bytes can only contain ASCII` |

Правило простое: **если строка попадёт в shell, `jq` или имя файла —
латиница.** Значения внутри могут быть любыми, ограничение только
на имена и ключи.

Живой пример разделения: `dump_exercises.py` печатает отпечаток
с ключами `total`, `with_video`, `hash` — его читает `jq` в workflow.
А внутри самого снимка ключи русские (`формат`, `упражнения`,
`счётчики`), потому что тот файл читает человек.

### 6.0.2. Страница не переопределяет систему. Девять проверок и один ручной пункт

**Правило:** страничный CSS не объявляет селекторы из компонентной базы,
не переопределяет токены и не выносит статические стили в атрибут `style=`.

Почему правилом, а не уборкой. Специфичность всплывала четыре раза, и один
раз мы уже чинили этот файл — коммит `d387c67` убрал хардкоды из медиазапроса
`nutrition`, но **причина осталась**: `.card` и `--border` там переопределены
до сих пор. Уборка без правила даёт возврат через полгода, потому что
архитектура переопределение разрешает: стили страницы грузятся после
`style.css` и выигрывают при равной специфичности, а `style=` бьёт вообще
любой файловый селектор.

| Что нельзя | Почему | Что вместо |
|---|---|---|
| `.card`, `.btn-primary`, `.input`… в шаблоне или в `hh.css`/`profile.css` | компонент ломается везде, где окажется на странице | системный компонент как есть — либо **новый вариант в системе** |
| `--border`, `--surface-1`… вне `:root` в `style.css` | меняет всю страницу молча; правка в `style.css` до неё не дойдёт | добавить вариант токена в систему |
| `style="margin-bottom:8px"` в разметке | бьёт любой селектор, в грепы по классам не попадает | класс в CSS |

**Префикс страницы (`.nut-card`) — не путь по умолчанию, а исключение.**
Если странице нужна карточка, отличная от системной, это почти всегда значит,
что в системе не хватает варианта: правильный ход — добавить его туда.
Префикс допустим только для того, чего в системе нет и быть не должно
(например, раскладка конкретного экрана). Иначе через полгода получим три
системы вместо одной: `.nut-card`, `.work-card`, `.hh-card`.

**Девять проверок** — шесть грепов и три скрипта. Скрипт там, где грепом
честно не выходит: у седьмой надо разбирать кодовые блоки документации,
у восьмой — сверять CSS с разметкой, у девятой — историю git со статусами
задач. Все три читаются по коду возврата.
Грепы ходят и по шаблонам, и по CSS-файлам (класс уже переехал
в `hh.css` и `profile.css`, поэтому смотреть только `templates/` мало):

Последний шаг — про `.tool-card .eyebrow` в `landing.css`. Правило красит
`.eyebrow`, а `.tool-card` там только контекст: карточку оно не трогает

честной строки вида «оформить своё внутри системной карточки». Проверка,
которая растёт от нормальной работы, перестаёт читаться на третий раз.

Уточнение: имя системного класса должно стоять последним в своей связке —
дальше допускаются только `:псевдокласс`, `.ещё-класс`, `[атрибут]`,
а потом сразу `,` или `{`. Пробел между именем и скобкой означает, что
субъект другой, и строка пропускается. Проверено на семи формах:

| Форма | Ожидание |
|---|---|
| `.card { }` | **поймать** |
| `main.container { }` | **поймать** — составной субъект |
| `.card.active { }`, `.card:hover { }` | **поймать** |
| `.card + .card { }` | **поймать** по второму вхождению |
| `.hero .btn-primary { }` | **поймать** — субъект системный |
| `:is(.card, .x) { }`, `.foo, .card { }` | **поймать** |
| `@media (…) { .card { } }` в одну строку | **поймать** |
| `.tool-card .eyebrow { }`, `.card > .foo { }` | пропустить — субъект свой |
| `closest('.card')` в скрипте | пропустить — за именем кавычка, а не `,` или `{` |

Прогнано на этих одиннадцати строках разом, а не по одной: правка
регулярки, проверенная на том единственном случае, который был перед
глазами, — это ровно та ошибка, из-за которой понадобилась ревизия
2026-08-04.

сработал на собственном авторе: `СТРАНИЦЫ="…"` — не присваивание, а команда,
которой не существует. Bash отвечает `command not found`, код 127, а `$pages`
дальше раскрывается в пустоту — то есть **все шесть проверок пошли бы

#### Проверка 7: документация — тоже поверхность отказа

Первые шесть ходят по коду. Ни одна не ходит по `design-system.md`

То есть проверка 7 закрывает **имена и значения, но не утверждения
о смысле**. Вторая половина ловится чтением, и повод для чтения теперь
не «когда-нибудь», а таблица-триггер в §6.2.

Шестой греп — про `<div class="auth-box" class="v-center">`. Браузер второй
атрибут **молча игнорирует**: ошибки нет, страница рисуется, класс просто
не применяется. Так на двух экранах подтверждения почты текст полгода шёл
слева вместо центра — `.v-center` и `.v-block` были написаны, подключены
и не работали ни разу.

Это шестое слепое пятно: дубль атрибута не ловят первые пять, потому что
он не переопределение и не инлайн — синтаксис разметки, а не стиль.
Автоматизируется без ложных срабатываний, поэтому и попал в список,
в отличие от ручного пункта ниже.

Три замечания по самому грепу:

| Что | Почему так |
|---|---|
| `-P`, а не `-E` | нужна обратная ссылка `\1` — «тот же атрибут второй раз». В POSIX ERE её нет |
| `[^>]*` между атрибутами | ограничивает поиск ОДНИМ тегом: без этого `<div class="a"><span class="b">` в одной строке считалось бы дублем |
| `-i` | в HTML имя атрибута регистронезависимо: `<img SRC="1" src="2">` — дубль. Без `-i` обратная ссылка требует совпадения регистра и такой тег проходит мимо |
| `-z` в 6b | тег, разорванный переносом, построчный греп пропускает. `-z` читает файл одной строкой, и `[^>]*` начинает захватывать переводы строки. Раньше это сверялось руками «на глаз»; теперь это команда |

#### Проверка 8: id весит больше класса, и первая проверка его не видит

Заведена 2026-08-11. Форма была названа накануне при разборе задачи 45
(`#resume-textarea` в `hh.css` менял компоненту кегль) и отложена
до замера масштаба. Замерили.

Проверка 1 ищет системный класс **субъектом**: `.hero .btn-primary { … }`.
Правило `#hero-cta { … }` на том же элементе она не видит вовсе — а весит
оно больше: id это (1,0,0), любой класс (0,1,0). **Форма и невидимая,
и более сильная разом.**

Отказ немой в обе стороны:

| Сторона | Что происходит |
|---|---|
| компонент рисуется не по системе | разметка верная, класс на месте, консоль чистая — по коду не увидеть |
| компонент чинят в `style.css` | до такого элемента правка не доедет: id выигрывает и у медиазапроса, и у нового варианта |

**Почему скрипт, а не восьмой греп.** Разницы между долгом и законной
строкой в самом правиле нет. `#job-input { min-height: 300px }` законно
(высота экземпляра), `#job-input { font-size: … }` — долг (кегль
принадлежит компоненту). Отличают их две вещи сразу: какие свойства
объявлены **и носит ли элемент с этим id системный класс**. Второе лежит
в разметке, а не в CSS.

Замер на живом дереве: правил по id в проекте **48**, на элементе
с системным классом — **3**. Греп без разбора разметки печатал бы
48 строк, из которых 45 чужие: 94% ложных. Проверка, которая врёт,
перестаёт читаться на третий раз — тот же довод, из-за которого
в проверку 4 пришлось внести `_admin_nav.html`.

**Список компонентов проверка не дублирует** — читает строку `names='…'`
отсюда же, из §6.0.2. Вторая копия разошлась бы с первой молча. Нет
строки — скрипт останавливается с кодом 2 и говорит об этом, а не
проходит с пустым списком: whitelist, который молча опустел, печатает
«чисто» про всё на свете.

Свойства делятся по тому же критерию, что первое число: раскладка
экземпляра (`width`, `height`, `min-*`, `flex`, `margin`, `position`…) —
законна и в код возврата не идёт; вид компонента (`font-*`, `color`,
`background`, `border`, `radius`, `padding`, `shadow`) — долг.

**Граница** — что проверка 8 не видит:

| Что проходит мимо | Почему не закрыто |
|---|---|
| класс, навешенный скриптом (`el.classList.add('card')`) | в разметке его нет, а исполнять скрипт проверка не может |
| id, собранный в рантайме (`id="row-" + n`) | такой строки не существует в исходнике |
| атрибут `style=` на том же элементе | это проверка 3, не эта |

Проверена отрицательным тестом, а не только положительным: в `hh.css`
временно возвращён `font-size` на `#job-input` — код 1, строка названа,

своим (субъект — класс), и это правильно — его ловит проверка 1.

#### Ревизия 2026-08-04: что проходило мимо и что теперь ловится

Поводом стали три попадания подряд. `--tool-accent` прошёл мимо проверки 2,
потому что список префиксов требовал имя сразу после `--`, а там стоит `tool`.
`.modal h3` прошёл мимо проверки 1, потому что это селектор потомка, а греп
искал имя в начале строки перед `{`, `,` или `:`. Мёртвый `.modal` в `style.css`
никакая проверка не искала вовсе. Причина у всех трёх одна: **регулярка
писалась под тот случай, который был перед глазами в момент написания.**

Поэтому проверки пересмотрены не вопросом «что она ловит», а вопросом
«какая форма нарушения проходит мимо». Ниже — что изменилось и что
осталось непокрытым **осознанно**.

**Проверка 1.** Было: `^\s*\.имя\s*[,{:]` — только имя в начале строки.
Проходили мимо: селектор потомка (`.modal h3`), соседа (`.card + .card`),
составной (`main.container`, `.card.active`), имя внутри
`:is()`/`:where()`/`:not()`, имя не первым в списке (`.foo, .card {`),
имя внутри `@media { .card {` на одной строке. Стало: имя класса **где угодно
на строке**, лишь бы на той же строке была `{`. Требование `{` — единственное,
что отделяет CSS-правило от прозы и от `closest('.card')` в скрипте;
без него проверка выдавала полтора десятка ложных срабатываний на
комментариях, где классы просто упомянуты.

Что это дало сразу: находок стало **16 вместо 1**. Пятнадцать новых —
не регресс, а долг, который проверка не показывала (`BACKLOG.md`, задача 37;
закрыта 2026-08-06, долговых строк не осталось).

**Правка 2026-08-06: «где угодно на строке» оказалось слишком широко.**
Под это попадал предок — `.tool-card .eyebrow` — где системный класс
вообще не оформляется, а только задаёт контекст своему. Такие строки
пишутся при нормальной работе, и число росло бы от неё же. Уточнение:
системный класс обязан быть **субъектом** селектора, то есть последним
в своей связке (дальше только `:псевдокласс`, `.класс`, `[атрибут]`,
потом сразу `,` или `{`). Пробел перед скобкой означает, что субъект
другой. Формы, на которых это проверено, — таблица выше.

Проверялась и обратная гипотеза: не ловит ли проверка сам `style.css`.
Не ловит и не может — его нет в `$pages` и не было ни разу. Если бы
был, дал бы 36 находок одной только системой, описывающей саму себя.
`main.container { max-width: 1600px }`, из-за которого вопрос и возник,
живёт в `static/hh.css:8` — то есть это страничный файл, меняющий
системный контейнер, и находка настоящая.

**Проверка 2.** Было: список префиксов имён. Список — это whitelist, и всё,
что в него не попало, невидимо: `--shadow-lg`, `--warning`, `--error`,
`--radius-xl`, `--ease-out`. `--tool-accent` был не единственной дырой,
а первой замеченной. (Здесь до 2026-08-06 стояло `--max-w` — токена
с таким именем в системе нет и не было, то есть пример был выдуман.
Нашла его проверка 7, см. ниже.) Стало: **список токенов берётся из самого `style.css`** прямо
перед прогоном — 63 имени на сегодня. Пятно закрыто не расширением списка,
а тем, что списка больше нет: имя, которого нет в системе, и не может быть
её переопределением, а любое системное имя проверяется по факту.
Плюс снят якорь `^\s*`, поэтому ловятся `.x { --border: red }` в одну строку
и `style="--border: red"` в разметке. Последнее важно: проверка 3 считает
инлайновый стиль из одних CSS-переменных **законным** и пропускает его —
через эту дверь системный токен переопределялся молча.

**Проверка 3.** Добавлены `static/*.js` в область (разметку собирает не только
Jinja) и отдельный проход 3a под `style='…'` в одинарных кавычках: HTML их
допускает, а прежний греп искал только двойные. Разбирать одинарные тем же
конвейером не стали — четыре звена исключений пришлось бы переписать
с экранированием кавычек внутри кавычек, а форм таких в проекте ноль;
дешевле называть их целиком и разбирать глазами, если появятся.

**Проверка 4.** Было: страница **упоминает** партиал шапки. Форма, проходившая
мимо: страница партиал подключила и **вдобавок** нарисовала свою шапку —
ровно то, чем была `<nav class="nav">`. Добавлена 4b: прямой поиск
`class="nav"` и `class="site-header"` в разметке страниц.

**Проверка 6.** Добавлены `-i` (в HTML имя атрибута регистронезависимо)
и поддержка одинарных кавычек; сверка многострочных тегов перестала быть
ручной — это 6b.

#### Признанные пробелы: что не ловится и проверяется глазами

Проверка с честно названной границей полезнее той, про которую думают,
что она видит всё. Ниже — формы, которые **остаются** непокрытыми, и почему
их не стали автоматизировать.

| Проверка | Что проходит мимо | Почему не закрыто |
|---|---|---|
| 1 | селектор, разорванный переносом: `.foo,`↵`.card`↵`{` — на строке с именем нет `{` | построчный греп такого не видит; вариант с `-z` даёт ложные срабатывания на каждом упоминании класса в комментарии, а комментариев в этих файлах много |
| 1 | имя класса, собранное в скрипте: `'.' + вид + '-card'` | не существует в исходнике как строка |
| 1 | **ложное** срабатывание: проза, где рядом стоят имя класса и `{` | лечится не грепом, а формулировкой комментария — см. `nutrition.css`, где пришлось убрать скобки из пояснения |
| 1 | системный класс как СУБЪЕКТ, но со свойством раскладки: `.save-bar .btn-primary { width: 100% }` | попадает в вывод, хотя законно: `width`, `flex`, `min-width` принадлежат родителю, а не компоненту. Отличить грепом нельзя — надо читать объявления. Поэтому первое число, как и пятое, разбирается по таблице в задаче 37, а не считается долгом целиком |
| 7 | утверждение о смысле: охват («на всех страницах»), потребитель, технология, строка интерфейса | буквального представления в коде нет — сверять не с чем. Полный список и разбор каждого — таблица «ГРАНИЦА» выше. Размер `36×36` сюда больше не входит: с 2026-08-09 его берёт проход C |
| 2 | токен, переопределённый анимацией или `@property` | форм в проекте нет; появятся — добавить звено |
| 3 | `элемент.style.свойство = …` в скрипте (146 мест) | подавляющее большинство законно рантаймовые; регулярка не отличит их от статики, а проверка, которая врёт в половине случаев, перестаёт читаться целиком |
| 3 | атрибут `style`, разорванный переносом строки | то же, что у проверки 1 |
| 3 | `style="{{ весь_стиль }}"` — атрибут целиком из переменной | попадает в вывод как долг, хотя может быть законным. Оставлено намеренно: ложная тревога здесь безопаснее пропуска |
| 4, 5 | партиал **упомянут в комментарии**, но не подключён; `include` под условием, которое никогда не истинно | греп проверяет наличие строки, а не факт вывода. Отличить может только рендер |
| 6 | дубль, разнесённый по веткам Jinja: `{% if %}class="a"{% else %}class="b"{% endif %}` | в файле это не дубль, а в выводе — дубль. Ловится только рендером |
| 6 | атрибут без кавычек: `<div class=a class=b>` | форм в проекте ноль; регулярка без кавычек цепляет слишком многое |
| 8 | класс, навешенный скриптом (`el.classList.add('card')`); id, собранный в рантайме | в разметке такой строки нет, а исполнять скрипт проверка не может |
| 8 | `!important` на правиле по КЛАССУ, бьющий систему тем же способом | другая форма: её видит проверка 1, если имя в `names`. Экземпляр в проекте один и он назван — `.spinner`, задача 45 |
| 7 | **возвращение** имени, объявленного удалённым: класс вернули в разметку, а документ по-прежнему пишет, что его нет | список исключений говорит «про это имя написано, что его нет», и на этом успокаивается. Найдено отрицательным контролем 2026-08-17: `.box-title` вернули в шаблон — проверка дала 0. Не закрыто по замеру: из 60 исключений сборщик считает «живыми» 40, потому что комментарии из CSS не вырезает; проверка с 40 ложными на 40 находок не читается вовсе |
| 9 | задача, у которой устарел не статус, а **содержание**: названы файлы, которых нет, план разошёлся с решением | буквального представления в коде нет. Лечится пунктом в §6.2 — сводка бэклога читается по коду, а не по заголовку |
| 9 | работа без номера задачи в теме коммита; «ЧАСТИЧНО», под которым сделано всё; «ВЫПОЛНЕНА» после отката | пропуски, а не ложь. Шесть из девяти расхождений сводки 2026-08-11 проверка бы не нашла — их закрывали походя |
| все | **самодельный компонент** — кнопка, поле, модалка, алерт под своим именем | ручной пункт ниже, автоматизировать нечем |

Четвёртый и пятый греп — про ту же болезнь, что первые три, только на этаж
выше: страница не переопределяет систему **и не пересобирает её заново**.
Своя `<nav class="nav">` на шести страницах входа была именно этим: копия
шапки, которая жила отдельной жизнью и молча расходилась с общей — на
`verify_required` она успела отрастить пару текстовых ссылок «Профиль /
Выйти», прямо запрещённых в `design-system.md`, разделе 4.

Обе проверки печатают **имена файлов**, а не строки, и молчание означает
«чисто». `grep -L` — это «файлы БЕЗ совпадения»; `grep -v '/_'` убирает
сами partials, у которых include самих себя быть и не должно. В четвёртом
грепе `_admin_nav.html` перечислен рядом с `_header.html` не для красоты:
админка подключает шапку через него, и без этого альтернатива дала бы
четыре ложных срабатывания подряд — а проверка, которая врёт, перестаёт
читаться на третий раз.

**Законные исключения на сегодня** — их видно в выводе пятого грепа, и это
не долг:

| Файл | Почему без хвоста |
|---|---|
| `demo_landing.html` | витрина тестового задания: с сайтом не связана ни одной ссылкой, своя вёрстка целиком |
| `demo_program.html` | вторая страница той же витрины |

Всё остальное в выводе — долг.

**Страницы, у которых хвост есть, а футера нет, в этот список
не попадают и попадать не должны** — их две, и обе объявляют это
флагом `footer_off` прямо в шаблоне, с причиной строкой рядом:

| Файл | Почему без футера |
|---|---|
| `verify_pending.html` | условия приняты шагом раньше, на регистрации |
| `verify_required.html` | то же: человек уже зарегистрирован и вошёл |

Разница между этими двумя таблицами — это разница между «решили»
и «забыли», и снаружи она видна только потому, что первое записано
флагом. Пропущенный include выглядит точно так же, как осознанный
отказ, и отличить их было бы нечем (§6.0.1).

#### Ручной пункт: компонентная база

Греп ловит переопределения и самодельные шапки, но не ловит **самодельные
кнопки, поля, модалки и алерты**: `<button class="verify-resend-btn">` —
это ни системный класс (значит, греп 1 молчит), ни инлайн (греп 3 молчит),
а просто новый компонент, которого в системе нет.

Поэтому пункт ручной и остаётся ручным: **кнопки, поля, модалки и алерты
на странице взяты из компонентной базы; каждое исключение названо вслух —
что это и почему не системный класс.** Автоматизировать его нечем. Регулярка
не отличит «кнопку с другим оформлением, потому что так надо» от «кнопку
с другим оформлением, потому что автор не посмотрел в дизайн-систему», и
проверка, которая врёт в половине случаев, перестаёт читаться целиком —
ровно как это случилось бы с грепом 4 без `_admin_nav.html`.

Третий греп написан именно так, потому что первая его версия имела слепое
пятно того самого класса, за которым мы гоняемся: она отсеивала строку
целиком, если в ней встречалось `{{`. То есть `style="width: {{ x }}%"`
пропускался законно, а `style="width: {{ x }}%; border: 1px solid red"` —
незаконно, и проверка рапортовала «чисто». Теперь исключается только то,
что законно **целиком**: смесь законного и статики ловится.

**Пятое звено — `${...}` — добавлено 2026-08-04.** Разметку у нас собирает
не только Jinja: в `nutrition.html` и `workout.html` куски HTML строит
скрипт шаблонными строками, и `style="height:${h}%"` — такое же рантаймовое
значение, как `{{ }}`, записать его в CSS точно так же нечем. Пока звена
не было, эти строки попадали в вывод как долг, которого нет. Форма у звена
намеренно та же, что у Jinja-звена: пропускается ОДНО свойство, значение
которого целиком выражение. Смесь выражения со статикой ловится по-прежнему.

Проверять изменения этого грепа надо на шести примерах сразу:

| Пример | Ожидание |
|---|---|
| `style="--n: 3"` | пропустить |
| `style="--n: 3; margin-top: 8px"` | **поймать** |
| `style="width: {{ x }}%"` | пропустить |
| `style="width: {{ x }}%; border: 1px solid red"` | **поймать** |
| `style="height:${h}%"` | пропустить |
| `style="height:${h}%; color: red"` | **поймать** |

#### Где инлайн допустим осознанно

| Случай | Пример | Почему |
|---|---|---|
| значение считается в рантайме | `style="width: {{ процент }}%"` | в CSS его записать нечем |
| переключатель видимости для JS | `style="display:none"` | начальное состояние элемента, которым управляет скрипт |
| CSS-переменная как параметр | `style="--задержка: .3s"` | это данные для стиля, а не сам стиль |

Всё остальное — необёрнутый CSS. `style="margin-bottom:8px"` и
`style="color:var(--text-2);font-size:0.95rem"` относятся ко второй
категории: токен внутри не делает инлайн законным.

### 6.0.1. Подавлять сбой нельзя. Список конструкций для ревью

**Правило:** нельзя подавлять вывод или код возврата у команды, которая
может сработать частично. Отказ, о котором никто не узнал, — дороже отказа:
он выглядит как успех и обнаруживается в тот единственный день, когда
на него положились.

За две сессии этот класс всплывал четыре раза, каждый раз в новом месте:
`except: pass` в анализе вакансии (письма молча выходили без разбора),
`|| true` в уведомлении о сбое бэкапа (полтора месяца немого 404),
`curl` без проверки ответа (404 считался успехом), `2>/dev/null` поверх
упавшего `git add` (в коммит уехала половина работы). Поэтому — не урок,
а список, по которому можно грепнуть.

| Конструкция | Чем плоха | Что вместо |
|---|---|---|
| `except:` без типа | ловит и `KeyboardInterrupt` с `SystemExit` | назвать конкретные исключения |
| `except X: pass` | сбой исчезает бесследно | `print(f"[метка] что не вышло: {e}")` или запись причины в поле |
| `except X: return []` / `return None` | вызывающий не отличит «пусто» от «сломалось» | вернуть признак ошибки либо залогировать |
| `\|\| true` в shell | шаг зеленеет при неудаче | `if ! cmd; then echo "::error::…"; exit 1; fi` |
| `2>/dev/null` | глушит и настоящую причину | убрать; если шумно — фильтровать конкретный текст |
| `curl` без `-f` и без чтения кода | HTTP 404 и 500 — «успех» | `-w '%{http_code}'` и явная проверка, как в `telegram.sh` |
| `set +e`, `continue-on-error: true` | отключает проверки оптом | точечная обработка нужной команды |
| `git add … 2>/dev/null` | частично применённая команда молчит | без подавления, потом `git status` |
| **проверка, чей результат читают глазами** | интерпретатора нет — заглушка печатает текст и «проходит» | читать **код возврата**, а не вывод |

#### Команда, которая проверяет код, сама проверяется по коду возврата

Последняя строка таблицы — не гипотеза. `python check_docs.py` (проверка 7
в §6.0.2) на этой машине **не запускалась ни разу**: `python` в `PATH` —
заглушка Microsoft Store из `WindowsApps`, она печатает
«Python was not found…» и возвращает 9009. Опорное число «проверка 7 — 0»
получено командой, которая не прочитала ни строки, и мы полгода считали
документацию сверенной. Обнаружено 2026-08-08, когда вывод показался
подозрительно коротким.

Родство с `curl` без `-f` прямое: **успехом объявлен ответ, который
успехом не является.** curl считает удачей HTTP 404, заглушка — ненайденный
интерпретатор. В обоих случаях сигнал есть и он верный (код 404, код 9009),
просто его никто не смотрит.

Правило: **у проверки читается код возврата.** Вывод — для человека, код —
для решения. Если проверка вызывается вручную, а не из workflow, кодом
надо интересоваться так же:

```bash
py check_docs.py;    echo "код=$?"     # 0 — сверено, не 0 — разбираться
py check_privacy.py; echo "код=$?"
```

Три признака, по которым такой отказ узнаётся, пока он не стоил полугода:

| Признак | Пример |
|---|---|
| вывод короче обычного и без чисел | вместо «0 расхождений» — одно слово `Python` |
| результат не меняется от правок в проверяемом | сколько ни ломай документ, всё те же «0» |
| код возврата не 0 при «успешном» на вид выводе | 9009 в PowerShell, 49 в Git Bash (те же 9009 по модулю 256) |

**Проверить грепом:**

```bash
grep -rn "except:" --include="*.py" .
grep -rn -A1 "except" --include="*.py" . | grep "pass$"
grep -rn "|| true\|2>/dev/null\|set +e\|continue-on-error" .github/
grep -rn "curl " .github/ | grep -v "http_code"
# локальный вызов python вместо py — заглушка Store молча ничего не сделает.
# Внутри flyctl ssh console python ЗАКОННЫЙ: там Linux и /usr/local/bin/python
grep -n "^\s*python[ 3]" CLAUDE.md *.md
```

#### Где подавление осознанно — и почему

Эти места **не** являются нарушением правила, у каждого своя причина.
Список нужен, чтобы правило не обходили «по аналогии»: аналогия
допустима только с той же причиной, а не с той же конструкцией.

| Место | Конструкция | Почему допустимо |
|---|---|---|
| `backup.yml`, шифрование | `shred \|\| rm` | `shred` может отсутствовать в образе; раннер эфемерный, пароль исчезнет с ним |
| `backup.yml`, уборка дампа | шаг не роняет прогон | идёт под `always()`; упав, перекрыл бы настоящую причину сбоя выше. Молчания при этом нет: `::warning::` плюс сообщение в Telegram |
| `database.py`, миграции | `except Exception: pass` | `ALTER TABLE` на уже применённой миграции обязан падать, это и есть признак «уже сделано» |
| `auth.py`, разбор токена | `return None` | битый токен — это «не авторизован», нормальный ход событий, а не сбой |
| `main.py`, Turnstile | `return False, False` | различает «не прошли» и «проверить не смогли»; решение fail-open принято осознанно, см. §8.1 |
| `make_backup.py`, счётчики | `счётчики[т] = None` | таблицы может не быть на старой базе; None и означает «не посчитано» |

### 6.0.3. Один снимок — не воспроизведение. Состояния перечислены поимённо

**Правило:** воспроизведение визуального дефекта считается проведённым
только если снято во **всех** интерактивных состояниях элемента: обычное,
наведение, фокус, нажатие, раскрытое/свёрнутое, — а на сенсорных ширинах
ещё и состояние **после касания**. Снимок в одном состоянии основанием
для вывода «дефекта нет» не является.

Почему правилом, а не внимательностью. Проверка в одном состоянии — это
`|| true` из §6.0.1, повёрнутый к глазу: **она отчитывается успехом,
не тронув то состояние, в котором дефект существует.** Отличить такой
зелёный от настоящего по отчёту нельзя, потому что в отчёте написано
«снято и сверено», и это правда.

**Случай, из-за которого правило появилось.** Задача 65 (2026-08-11)
разбирала «слипание блоков в карточке письма». Замер: три раскрытия сняты
побайтово одинаковыми, зазор 0 на всех проверках — дефект объявлен
несуществующим. Все три снимка при этом сделаны в **одном и том же**
состоянии: курсора над заголовком нет, фокуса на нём нет. Дефект живёт
ровно там, где не смотрели. Разбор 2026-08-12:

| Состояние | Фон шапки | Фон блока письма | Что видно |
|---|---|---|---|
| обычное | прозрачный (карточка `#141520`) | `#1E2030` | промежуток есть |
| **наведение** | **`#1E2030`** | `#1E2030` | **промежутка нет — цвета совпали** |
| после касания (390px) | `#1E2030`, залипает | `#1E2030` | то же, и не уходит само |

Геометрия при этом не менялась ни на пиксель — ни до правки, ни после:
расстояние между границами было 0 всегда, а видимый зазор давала
прозрачная подкладка шапки. **Побайтовое сравнение снимков такой дефект
не ловит по построению**, потому что дефект не в размерах, а в том, каким
цветом залита та же самая геометрия.

Отсюда два следствия, которые дороже самой правки:

- **Совпадение вычисленных значений — не доказательство отсутствия
  дефекта.** Доказательством может быть только снимок состояния,
  в котором на дефект жалуются.
- **Состояния перечисляются в отчёте поимённо.** «Проверено во всех
  состояниях» — та же непроверяемая фраза, что «каждое подтверждено
  чтением кода» из §6.2. Названо `hover` — значит, снят `hover`.

**Сенсорная ширина — отдельная строка списка, а не «то же самое, только уже».**
На телефоне `:hover` остаётся на последнем тронутом элементе до касания
в другом месте: состояния «мышь ушла» там не существует. Ловится только
эмуляцией с сенсорным вводом (`has_touch=True`) и тапом, а не изменением
ширины окна. Тем же заходом выяснилось, что подсветку давал именно
`:hover`, а не фокус, как выглядело: `:focus-visible` в момент залипания
возвращал `false`.

**Что это правило не обещает.** Оно перечисляет состояния одного элемента.
Дефект, который живёт в сочетании состояний двух элементов (открытая
модалка + фокус в поле под ней) или появляется только после
последовательности действий, из списка не выводится — его по-прежнему
находит воспроизведение по шагам из жалобы.

**Побочное правило про декоративные обещания.** Если элемент своим видом
обещает действие — «ручка» шторки, курсор-указатель, стрелка сворачивания, —
проверяется, что действие есть. Элемент, обещающий жест, которого нет,
это тот же немой отказ, только его видит пользователь, а не лог: замер
2026-08-12 показал, что смахивание модалки работало на одной странице
из всех, а «ручку» компонент рисовал на каждой.

#### У ПРОВЕРКИ ОБЯЗАН БЫТЬ ОТРИЦАТЕЛЬНЫЙ КОНТРОЛЬ

Заведено 2026-08-15, поводом — две собственные ошибки подряд, обе одного
вида: **проверка отчиталась, не потрогав то, что проверяет.**

| Случай | Что показала проверка | Чего стоило |
|---|---|---|
| задача 75 (2026-08-14) | «обработчика нет ни в разметке, ни в скриптах» — вывод сделан ЧТЕНИЕМ | загрузка фото работала с коммита `7600adf`; задача была выдумана целиком |
| залипающий `:hover` (2026-08-15) | тап + скролл на сенсорной ширине: «залипло 0» | тот же ноль получался и ДО правки — проверка не касалась состояния, в котором дефект живёт |

Второй случай важнее первого, потому что выглядел безупречно: снимки
сняты, ширина сенсорная, `has_touch=True`, число напечатано. Отличить
такой ноль от настоящего по отчёту нельзя.

**Правило: рядом с проверкой ставится случай, на котором она ОБЯЗАНА
сработать. Не сработала — проверка сломана, а не объект исправен.**

Как это выглядело на деле в тот же день:

- **Залипающий `:hover`.** Годная проверка — навязать `:hover` через CDP
  (`CSS.forcePseudoState`) и сверить вычисленные стили. Отрицательный
  контроль — прогон на коде ДО правки: 46 элементов из 74 меняют вид
  при `hover: none`. После правки 0, а на десктопе как было 47, так
  и осталось. Три числа вместо одного, и каждое опровергает свою версию
  «ничего не проверили».
- **Декоративные обещания (задача 71).** Проверка — нажать и сверить
  состояние страницы. Отрицательный контроль — нажать на превью,
  у которого действие ЕСТЬ: открылась модалка, значит проверка видит
  работающий элемент. Без этого контроля «ничего не изменилось» означало
  бы что угодно, включая «клик не дошёл».

**Отсутствие упоминания в коде основанием для вывода не является.**
Обработчик бывает делегатом на `document`, приходит из общего скрипта,
навешивается по атрибуту. Грепом это не видно, нажатием — видно всегда.

#### ПРОВЕРКУ НЕ ПЕРЕПИСЫВАЮТ В ТОМ ЖЕ ЗАХОДЕ, ГДЕ ЧИНЯТ ПРОВЕРЯЕМОЕ

Заведено 2026-08-18. Повод — пятая проверка: 2026-08-17 она ушла с 9 на 2
**вместе** с переформулировкой под `_page_end.html`. Там всё было честно,
и отрицательный контроль это показал (снятый из партиала футер дал
19 страниц разом). Но честность в этом месте держалась на добросовестности,
а не на правиле, — и следующий раз мог выйти другим.

Опасность конкретная: **число упало, и по выводу нельзя отличить
«починили» от «стали спрашивать другое».** Обе причины дают одинаково
приятный результат, обе объясняются одной строкой в отчёте, и проверить
задним числом нечем — прежняя формулировка уже не существует.

**Правило.** Заход, который чинит проверяемое, проверку не трогает.
Число меняется только от правки кода — тогда падение числа что-то значит.

**Если переписать всё же пришлось** — а это бывает: после правки прежняя
формулировка может стать бессмысленной, как «ищи `_footer.html`» после
переезда футера в хвост, — в отчёте обязательны **четыре** вещи:

| Что | Зачем |
|---|---|
| прежняя формулировка дословно | иначе сравнить не с чем |
| новая формулировка дословно | то же |
| причина, по которой прежняя стала негодной | «стало удобнее» причиной не является |
| отрицательный контроль **НА НОВОЙ** формулировке | старый контроль про новую проверку не говорит ничего |

Последняя строка — та, которую пропустить легче всего. Контроль, снятый
до переписывания, подтверждает работоспособность **прежней** проверки;
новая может не ловить вообще ничего, и вывод «чисто» будет её обычным
состоянием.

### 6.0.4. Контрольные числа печатаются командой, а не лежат в тексте

Заведено 2026-08-18, после того как одно и то же число протухло дважды
подряд.

**Что случилось.** Про правила `:hover` в `@media (hover: hover)` в этом
файле стояло сначала **112**, потом **131**. Замер не дал ни того ни
другого — и не мог дать, потому что у вопроса три разных ответа:

| Что считать | Сейчас |
|---|---:|
| блоков `@media (hover: hover)` | 123 |
| **правил** — селекторов с `:hover` внутри них | **129** |
| вхождений `:hover` (селекторы через запятую) | 134 |

То есть беда была двойная: число устарело **и** не говорило, что именно
оно считает. Число без способа счёта не значит ничего: три человека
получат три разных ответа и каждый решит, что документ врёт.

**Правило — два требования, оба обязательны.**

1. **Число печатается командой.** Источник — `check_metrics.py`;
   в тексте стоит ссылка на команду, а не значение.
2. **У метрики назван ОДИН способ счёта**, и он записан рядом с числом
   в самой команде. Где ответов несколько — печатаются все, и один
   помечен опорным.

```bash
py check_metrics.py          # все метрики со способами счёта
py check_metrics.py --ряд    # только ряд девяти проверок §6.0.2
```

**Что печатает:** ряд девяти проверок (первые шесть — теми же грепами,
что записаны в §6.0.2, не второй реализацией; последние три — кодами
возврата), правила `:hover`, долг дневника из задачи 96, опись эндпоинтов.

**Чем это НЕ является.** `check_metrics.py` — срез, а не проверка: у него
нет понятия «правильно» и код возврата всегда 0. Проверки, у которых оно
есть, — `check_docs`, `check_ids`, `check_backlog`, `check_endpoints`, —
и их код читается отдельно (§6.0.1).

**Что в тексте остаётся числами и остаётся законно:** записи о прошлых
заходах («было 15, стало 16, потому что…»). Они рассказывают историю
и опорой не являются — по ним не сверяются. Опорное число в документе
теперь ровно одно: его нет.

### 6.1. Добавили таблицу с данными пользователя — три обязательных шага

Новая модель с `user_id` затрагивает не только схему. Забыть любой
из шагов легко, потому что все три живут в разных файлах.

**1. Каскад удаления.** Внести таблицу в `USER_TABLES` (или `CHILD_TABLES`,
если привязка идёт через родителя) в `database.py`. Иначе при удалении
аккаунта останутся сироты, а `id` в SQLite переиспользуются — данные
достанутся следующему пользователю. Проверка: `check_user_tables_complete()`,
её сам вызывает `cleanup_unverified.py` и останавливается при расхождении.

Тот же список ведёт **вторую сторону** — проверку «аккаунт пуст», по которой
ночная очистка решает, можно ли удалять. Разойтись они не могут по
конструкции: `user_data_counts()` вызывает `delete_user_cascade(dry_run=True)`
и считает то, что каскад удалил бы. Добавили таблицу в один список —
она попала в обе стороны сразу.

Почему проверка вообще появилась: очистка раньше опиралась на допущение
«неподтверждён — значит пуст», а оно неверно. Вход для неподтверждённых
открыт намеренно (гейт стоит на страницах инструментов, не на входе),
но API записи данных `is_verified` не проверяют — см. BACKLOG №24.

**Третье, что ведёт тот же список: «пусто по умолчанию».** Если строка
в новой таблице появляется САМА при регистрации, её надо внести
в `ПУСТЫЕ_ПО_УМОЛЧАНИЮ` (`database.py`) вместе с условием, что считать
пустотой. Иначе проверка сочтёт заготовку данными, и очистка перестанет
удалять ботов вовсе.

Это не теория: при регистрации каждому заводится пустое резюме, и первый
же прогон новой проверки пропустил 60 аккаунтов вместо одного. Список
лежит в одном месте — рядом с `user_data_counts`, которая его и применяет;
дублировать его где-либо нельзя.

Итого один список таблиц ведёт три вещи: **что удалять**, **что считать
данными**, **что считать заготовкой**.

**2. Политика конфиденциальности.** Назвать категорию в тексте
(`STATIC_PAGES["privacy"]` в `main.py`) и добавить строку
в `PRIVACY_MENTIONS` в `database.py`. Полный перечень обрабатываемых
данных — требование закона, а не стилистика. Проверка:

```bash
py check_privacy.py     # 27 таблиц против текста, код 1 при расхождениях
# ИМЕННО py. python на этой машине — заглушка Store: печатает текст,
# возвращает 9009 и не запускает скрипт. Прогнано 2026-08-08:
# 27 таблиц, 26 категорий, расхождений 0, код 0.
```

Так однажды выпал целый инструмент: трекер Enshrouded не упоминался
в политике вовсе, хотя данные по нему хранились. Проверка ловит три
случая — незаявленную таблицу, исчезнувшую из текста категорию
и оставшуюся в списке удалённую таблицу.

**3. Файлы вне базы.** Если таблица ссылается на файлы на томе — удалять
их в `delete_user_cascade` (образец: `_delete_avatar_file`, вызывается
после `commit` и с учётом `dry_run`). Имя файла лучше не привязывать
к `id` пользователя: `AUTOINCREMENT` на `users` наследование закрывает,
но опираться на одну эту защиту не стоит.

### 6.2. Правка кода, после которой документация правится в том же коммите

**Правило:** если правка меняет то, о чём `design-system.md` или `CLAUDE.md`
делает утверждение, документ правится **в том же коммите**, а не «потом».
Не «не забывать» — ниже таблица-триггер и команда, которая проверяет.

Почему правилом. За три дня документ разошёлся с кодом четыре раза, и ни
разу это не было опечаткой: `.modal` описан сутки после удаления класса,
`--max-w` назван примером системного токена, которого не существовало
никогда, breadcrumbs обещаны на четырёх страницах при одной, аватар
описан 32×32 при коде 36×36. Каждое утверждение было верным в день, когда
его писали. **Устаревает не документ — устаревает код под ним, молча.**

#### СВОДКА БЭКЛОГА ЧИТАЕТСЯ ПО КОДУ, А НЕ ПО ЗАГОЛОВКУ

Отдельным пунктом, потому что на этом уже споткнулись. 2026-08-11 сводка
перечислила одиннадцать «открытых» задач, взяв статусы из шапок, и три
из одиннадцати оказались неверны: задача 20 сделана целиком два дня
назад, 13 закрыта коммитом с её же номером в заголовке, 3 сделана
наполовину. В отчёте при этом стояло «каждое подтверждено чтением кода».

**Правило: строка сводки — это утверждение о коде, и основание у неё
должно быть в коде.** По каждой задаче называется, на чём стоит статус:
файл и функция, либо коммит. Не нашлось основания — так и писать
«не проверено», а не переписывать шапку.

Половину этого закрывает **проверка 9** (`py check_backlog.py`): задача
со статусом «не начата», в которую ведут коммиты с кодом. Вторую половину
не закрывает ничто — из девяти расхождений той сводки проверка нашла бы
три. Остальные шесть закрывали походя, не называя номер задачи в теме
коммита, и машине они невидимы.

Ритм: сводка нужна перед крупной задачей, а не по расписанию. Но раз она
делается — делается по коду.

#### Как это проверяется при ревью

Половину таблицы закрывает машина, половину — один вопрос себе.

**1. Машина.** Первые пять строк, девятая и десятая проверяются
`check_docs.py` (проверка 7, §6.0.2): имена классов и токенов, значения
токенов из `:root`, размеры вида `36×36` рядом с именем класса, имена
файлов. Читается **код возврата**, не вывод (§6.0.1):

```bash
py check_docs.py; echo "код=$?"     # 0 — сверено, не 0 — разбираться
```

**2. Глазами — по диффу, а не по памяти.** Строки про интерфейсные тексты
и про охват машина не берёт принципиально, и почему — названо в шапке
`check_docs.py`. Вопрос при ревью ровно один, и задаётся он к **диффу**:

> В этом диффе есть строка, которую увидит пользователь, или утверждение
> «везде / всегда / только»? Если да — где оно записано словами?

Найденное место правится сейчас. Не нашлось — так и сказать вслух:
«утверждений в документе про это нет», — а не промолчать. Молчание
и «проверил» выглядят одинаково, и это тот же класс отказа, что
`|| true` в §6.0.1.

**3. Коммит.** Правка кода и правка документа — **один коммит**. Разные
коммиты разъезжаются при откате: откатили код, документ остался описывать
откаченное. Именно поэтому компонент, заводимый в `style.css`, и его
описание в `design-system.md` не разделяются никогда.

#### Чего это правило не обещает

Оно ловит расхождения, **вносимые правкой**. Расхождение, накопленное
раньше, оно не найдёт: никто не открывает документ, если код не трогали.
Для накопленного есть только чтение целиком, и оно стоит захода —
2026-08-06 такой заход дал семь находок за раз (`BACKLOG.md`, задача 41).
Разумный ритм — раз в несколько месяцев или после крупной миграции,
а не по расписанию.

## 8. Диагностика на проде

> **Логи Fly пишутся в UTC, Денис живёт в GMT+3.** Чтобы сверить событие
> в логе со своим временем, **прибавьте три часа**: запись `23:54:08` в логе
> соответствует `02:54:08` по московскому времени. Это регулярно сбивает
> с толку — сначала кажется, что в логах «нет» только что сделанного
> действия, хотя оно там есть.

**Логи приложения:**

```bash
flyctl logs -a energydess-tools --no-tail          # последние записи
flyctl logs -a energydess-tools                    # живой поток
flyctl logs -a energydess-tools --no-tail | grep "\[login\]"
```

Префиксы в логах: `[login]` — срабатывания защиты входа, `[email]` — сбои
отправки писем, `[analyze]` — сбои анализа вакансии.

**Готовые скрипты** (только чтение, ничего не меняют):

```bash
flyctl ssh console -a energydess-tools -C "python /app/check_analysis.py"
flyctl ssh console -a energydess-tools -C "python /app/check_emails.py"
```

Первый показывает, у скольких писем анализ вакансии отработал и по каким
кодам падал. Второй — журнал отправок писем с `resend_id` и причинами сбоев.

**Фактическое значение переменной окружения** (секрет перекрывает `fly.toml`,
а `flyctl secrets list` значений не показывает):

```bash
flyctl ssh console -a energydess-tools -C "python -c \"import os;print(os.getenv('LETTER_MODEL'))\""
```

первый: **состояние, созданное однажды руками, невоспроизводимо**.
Проверить гейт без непроверенного аккаунта нечем, а «нечем проверить»
на практике означает «проверено рассуждением», то есть не проверено
(§6.0.1). Оба заводятся одной командой — аккаунт, который надо
не забыть создать, это аккаунт, которого не будет.

Заводятся и сбрасываются скриптом, **только в локальной базе**:

```bash
py make_local_user.py            # завести или сбросить пароль
py make_local_user.py --seed     # плюс данные: резюме, досье, 3 письма, 19 продуктов,
                                 # анкета питания, 17 позиций съеденного за сегодня,
                                 # 66 записанных дней за 95 прошлых (29 пропущено),
                                 # 2 запланированных дня вперёд и 22 взвешивания
py make_local_user.py --drop     # удалить вместе со всеми данными
```

Зачем отдельный аккаунт. Пароль хранится хэшем bcrypt и не восстанавливается
по построению, поэтому каждый заход, которому нужен авторизованный экран,
ломал пароль существующему — `test-admin@local.dev` был переписан дважды
за два дня. То есть съёмка скриншотов портила данные, на которых кто-то
мог работать дальше.

**На проде такого аккаунта быть не должно** — это вход с правами
администратора и с паролем, лежащим открытым текстом в этом файле.
Скрипт проверяет сам и останавливается с кодом 1, если база не локальная:
смотрит `FLY_APP_NAME` и путь `/data`. Проверено на проде отдельно —
2026-08-11 ответ **0**, ни одного адреса на `@local.dev`:

```bash
flyctl ssh console -a energydess-tools -C "python -c \"import sqlite3;c=sqlite3.connect('/data/app.db');print(c.execute(\\\"SELECT COUNT(*) FROM users WHERE email LIKE '%@local.dev'\\\").fetchone()[0])\""
```

`Error: The handle is invalid.` в конце вывода — артефакт закрытия SSH
на Windows, а не сбой запроса (§8.1, последнее замечание).

Ключ `--seed` наполняет аккаунт длинным содержимым намеренно: дефекты
вложенной прокрутки и схлопнутых колонок видны **только** на длинном
тексте и длинных названиях. На пустых экранах и то и другое выглядит
исправным — так эти два дефекта и прожили до 2026-08-11.

**Экран, которого seed не наполняет, не проверяется вовсе.** До 2026-08-11
seed заводил 19 продуктов в справочник, но ни одной записи в `food_logs` —
а дневник рисует карточки приёмов пищи из второй таблицы. Дневник
снимался пустым, и окно 90px на списке съеденного дожило до задачи 52
именно поэтому. Заодно добавлена анкета питания: без неё `/nutrition`
открывается экраном «Личные данные», то есть снять дневник нельзя
в принципе, сколько еды ни записывай.

Правило на будущее: **добавили экран — добавьте ему данные в seed**,
и не в соседнюю таблицу, а ровно в ту, из которой он читает.

**И не только в ту таблицу, но и в тот ДИАПАЗОН, который экран
показывает — 2026-08-17.** Тот же класс упущения, только по второй оси:
seed заводил еду ровно за сегодня, а вкладка «История» — про прошлое.
Календарь месяца, сводка «записано дней из прошедших» и предел листания
вперёд не проявляются вообще ни на чём, кроме данных, разбросанных
по нескольким месяцам с пропусками. Теперь seed кладёт 66 записанных
дней за 95 прошлых (каждый четвёртый плюс случайные — пропущены) и два
запланированных дня вперёд. Разброс детерминированный (`Random(20260817)`),
потому что числа в отчётах о замерах должны воспроизводиться.

**И это была не последняя таблица, о которой seed молчал — 2026-08-17,
второй заход.** `weight_logs` у аккаунта съёмки было **ноль строк**:
вкладка «Вес» — график, полоса прогресса к цели, три замера — не
снималась ни разу ни одним заходом за всё время. Пустой график при этом
выглядит не сломанным, а просто пустым, поэтому ни один обход экранов
на него не среагировал. Теперь seed кладёт **22 взвешивания за 106 дней**;
талия записана у каждого третьего, ягодицы и грудь — ни разу, чтобы
на экране были видны сразу оба случая: значение и «не записан».

**РОВНЫЙ ШАГ ТОЖЕ НЕ ПРОВЕРЯЕТ — 2026-08-17, вторая правка того же
места.** Первая версия ставила четырнадцать взвешиваний ровно через семь
дней, и на таком ряде график выглядит исправным при любой ошибке
в раскладке точек: равные промежутки не показывают ни сгущения подписей,
ни разрыва. Замер: на периоде «Месяц» ряд давал ровно четыре точки через
равные интервалы — то есть ни один из случаев, ради которых график
и рисуют, не проверялся.

Теперь ряд неровный и покрывает четыре месяца: два прогона по три дня
подряд (плотный участок — подписи дат обязаны не наезжать друг
на друга), разрыв в 19 дней между 24 мая и 12 июня (разреженный —
линия обязана идти прямо), промежутки внутри месяцев от 1 до 7 дней
и два подъёма веса против общего снижения. Замер после правки: «Месяц»
даёт 8 записей, «Всё время» — 22.

Правило то же, что и про таблицу с диапазоном, но по третьей оси:
**данные обязаны быть не только В ТОЙ таблице и В ТОМ диапазоне,
но и НЕРОВНЫМИ.** Идеально ровный ряд — это одно состояние экрана,
показанное двадцать раз.

Правило то же и повторяется третий раз: **экран, которого seed
не наполняет, не проверяется вовсе.** Проверять после правки надо
не только «есть ли данные в той таблице», но и «есть ли они в том
разбросе и той полноте, на которых экран показывает свои состояния».

### 8.1. Защита формы входа — как устроена

Сделана в BACKLOG №1 (2026-07-27). Вся логика в `main.py` рядом с роутом
`POST /login`, `auth.py` намеренно не тронут.

**Аккаунт не блокируется никогда.** Блокировка по аккаунту дала бы любому,
кто знает адрес, возможность держать чужой вход запертым постоянно —
достаточно вводить неверный пароль. Адрес пользователя знают как минимум
он сам и его почтовый провайдер, так что «знает адрес» — не редкость.
Ограничение только по адресу подключения.

| Неудач за 15 минут | Что происходит |
|---|---|
| 1-2 | ничего |
| 3+ | на форме появляется Turnstile |
| 15+ | отказ, код 429, на 15 минут |

Плюс прогрессивная задержка ответа: с 3-й неудачи 1 с, с 5-й 2 с, с 8-й 4 с
(потолок). Только `await asyncio.sleep` — `time.sleep` заморозил бы весь
event loop и сайт встал бы для всех сразу. Задержка не зависит от Cloudflare
и вместе с лимитом несёт основную нагрузку защиты.

**Успешный вход обнуляет счётчик** этого адреса.

**Ключ счётчика:** для IPv4 — полный адрес, для IPv6 — **префикс `/64`**.
Провайдер выдаёт клиенту целую подсеть `/64`, поэтому счёт по полному адресу
обходился бы бесплатно переключением адреса внутри своей подсети. В логах
печатается именно ключ (`2a00:1fa0:4705:1937::/64`), а не отдельный адрес —
чтобы при разборе инцидента было видно, по чему сработал лимит.

**Реальный IP** берётся из `Fly-Client-IP` → `X-Forwarded-For` →
`request.client.host`. Последнее без прокси-заголовков бесполезно: приложение
за прокси Fly и видит `172.16.13.90` у всех подряд.

**Turnstile работает в режиме fail-open.** Пустой токен (виджет не загрузился
либо проверку не прошли — серверно эти случаи неразличимы) и недоступность
`siteverify` пропускают вход. Отказ только на явное «нет» от Cloudflare.
Следствие принято осознанно: бот, не отправляющий поле капчи, проходит её
насквозь — капча тут дополнительный слой, а не барьер.

**Счётчик живёт в памяти процесса** (`_login_fails`), при рестарте обнуляется —
для защиты от перебора это допустимо. Протухшие записи вычищаются на ходу,
чтобы словарь не рос бесконечно.

Строки в логах: `включена капча`, `отказ на 15 мин`, `капча не отработала
(пустой токен)`, `Cloudflare недоступен с сервера`, `капча не пройдена`.
Каждая попытка не логируется — только моменты срабатывания. Email в логи
не пишется намеренно.

**Аварийное отключение защиты входа** — если лимит сработал против владельца.
Действует мгновенно, без передеплоя:

```bash
flyctl ssh console -a energydess-tools -C "touch /data/ratelimit_off"   # выключить
flyctl ssh console -a energydess-tools -C "rm /data/ratelimit_off"      # включить обратно
```

Файл лежит на volume и **переживает рестарт** — забыть его удалить значит
оставить вход без защиты навсегда. Пока файл существует, каждая попытка входа
пишет в лог строку об этом. Запасной путь, если SSH не отвечает:
`flyctl apps restart energydess-tools` (счётчики живут в памяти процесса).

**Замечание про вывод `flyctl ssh console` на Windows:** в конце команды
регулярно появляется `Error: The handle is invalid.` Это артефакт закрытия
SSH-сессии, а не ошибка скрипта — вывод до этого момента полный и корректный.

## 9. Бэкап базы и восстановление

> Снимки тома Fly (ежедневные, хранятся 30 дней — см. §10) остаются как
> были — это первая линия. Выгрузка в Telegram нужна на случай, когда
> тридцать дней уже прошли или требуется достать одну таблицу, а не
> разворачивать образ тома.

### Как устроено

`.github/workflows/backup.yml` раз в сутки: снимает согласованную копию базы
внутри контейнера (`make_backup.py`), скачивает её, сжимает, шифрует GPG
и отправляет в Telegram.

**Копия снимается через `sqlite3.Connection.backup()`**, а не копированием
файла: копировать `app.db` под нагрузкой нельзя — можно получить копию
посреди транзакции, которая выглядит целой, но не открывается. После снятия
прогоняется `PRAGMA integrity_check`; не прошёл — бэкап не отправляется.

Секреты в GitHub: `BACKUP_PASSPHRASE`, `TELEGRAM_BOT_TOKEN`,
`TELEGRAM_CHAT_ID`. Пароль шифрования **не хранится на Fly** — иначе он лежал
бы там же, где данные.

Размер проверяется до отправки: лимит Telegram Bot API 50 МБ на документ.
Перерастём — workflow упадёт с внятной ошибкой, а не отправит молча обрезанное.

### Восстановление: скачать и открыть

Всё делается **локально**, на боевую базу ничего не заливается.

```bash
# 1. Скачать файл из Telegram, например app-2026-07-27.db.gz.gpg

# 2. Расшифровать (пароль спросит интерактивно)
gpg -d app-2026-07-27.db.gz.gpg > app-2026-07-27.db.gz

# 3. Распаковать
gunzip app-2026-07-27.db.gz

# 4. Проверить целостность и счётчики
py -c "import sqlite3; c=sqlite3.connect('app-2026-07-27.db'); \
print(c.execute('PRAGMA integrity_check').fetchone()[0]); \
print('users:', c.execute('SELECT COUNT(*) FROM users').fetchone()[0])"
```

`gpg` уже установлен вместе с Git for Windows (`/usr/bin/gpg`), отдельно
Gpg4win ставить не нужно. Пароль — тот, что лежит в `BACKUP_PASSPHRASE`
и в менеджере паролей.

Счётчики сверяются с подписью к файлу в Telegram: она содержит число записей
по ключевым таблицам на момент снятия.

### Восстановление: залить базу обратно на Fly

> Инструкция на будущее. **Выполнять только осознанно** — заливка затирает
> боевую базу. Перед этим обязательно снять свежий бэкап текущего состояния.

```bash
# 1. Сохранить то, что есть сейчас, — на случай если восстановление ошибочно
flyctl ssh console -a energydess-tools -C "python /app/make_backup.py"
flyctl ssh sftp get /data/backup/app-СЕГОДНЯ.db ./на-всякий-случай.db -a energydess-tools

# 2. Остановить приложение, чтобы оно не писало в базу во время подмены
flyctl scale count 0 -a energydess-tools

# 3. Залить восстановленный файл
flyctl ssh sftp shell -a energydess-tools
# в открывшейся сессии:
#   put app-2026-07-27.db /data/app.db.new

# 4. Подменить и поднять приложение
flyctl ssh console -a energydess-tools -C "sh -c 'mv /data/app.db /data/app.db.old && mv /data/app.db.new /data/app.db'"
flyctl scale count 1 -a energydess-tools

# 5. Убедиться, что поднялось, и только потом убирать старую
flyctl ssh console -a energydess-tools -C "python /app/check_analysis.py"
flyctl ssh console -a energydess-tools -C "rm /data/app.db.old"
```

Шаг 2 обязателен: подменять файл базы под работающим приложением нельзя —
открытые соединения продолжат писать в старый inode, и часть данных уйдёт
в никуда.

### Запуск вручную

```bash
gh workflow run backup.yml
gh run watch
```

## 10. Восстановление файлов из снапшота тома

> Вторая линия, отдельная от выгрузки в Telegram. Туда уезжает **только
> база**, а файлы на томе — аватары и вложения переписки — в архив
> не попадают. Их единственная защита это снапшоты Fly.
>
> **Retention поднят до 30 дней** (2026-07-31, было 5). Снапшоты
> инкрементальные, у Fly первые 10 ГБ бесплатны, а все наши пять снимков
> занимают 144 МиБ — то есть 30 дней ничего не стоят. Потолок Fly — 60.

### МЕНЯЕТЕ RETENTION — ПРАВЬТЕ ПОЛИТИКУ

Срок хранения снимков лежит в двух источниках сразу: в настройке Fly
и в тексте, который читает пользователь. Поменять один и забыть про
второй — значит молча превратить политику конфиденциальности в неправду,
без единого сигнала о том, что что-то разъехалось.

Проверить командой:

```bash
flyctl volumes list -a energydess-tools --json | grep snapshot_retention
```

Места, где та же цифра записана словами, — все три править вместе
с настройкой:

| Файл | Где именно | Что там |
|---|---|---|
| `main.py` | `STATIC_PAGES["privacy"]`, таблица «Сколько мы храним данные», строка «Снимки состояния сервера у хостинга» | срок в таблице |
| `main.py` | `STATIC_PAGES["privacy"]`, блок `.doc-callout` про данные о здоровье, абзац про хранение фото | срок в тексте абзаца |
| `CLAUDE.md` | §9, врезка в начале раздела | срок для разработчика |

Проверка после правки:

```bash
grep -n "дней" main.py | grep -i "снимк\|хостинг"
```

### Главное: базу откатывать не нужно

Снапшот разворачивается **в отдельный том и монтируется в отдельную
машину**, параллельно работающему приложению. Боевой том при этом
не затрагивается вообще. То есть достать один файл недельной давности
можно, не трогая ни базу, ни чужие данные.

Проверено 2026-07-31 живым восстановлением: файл достали, sha256 совпал
с боевым побайтово, картинка открылась.

### Процедура

```bash
# 1. Выбрать снапшот — колонка CREATED AT показывает возраст
flyctl volumes snapshots list vol_4ql97qxo2lyodj8r

# 2. Создать из него отдельный том (боевой не трогается)
flyctl volumes create restore_test --snapshot-id vs_ВЫБРАННЫЙ \
  --region fra --size 1 -a energydess-tools --yes

# 3. Узнать id нового тома и текущий образ приложения
flyctl volumes list -a energydess-tools
flyctl image show -a energydess-tools

# 4. Поднять временную машину с этим томом. Образ берём свой же —
#    в нём есть python, которым удобно проверять базу
flyctl machine run registry.fly.io/energydess-tools:ТЕГ_ОБРАЗА \
  --volume vol_НОВЫЙ:/mnt/restore \
  --region fra -a energydess-tools --name restore-check \
  --vm-memory 256 --restart no \
  sleep 900

# 5. Посмотреть, что внутри
flyctl ssh console -a energydess-tools --machine ID_МАШИНЫ \
  -C "sh -c 'ls -la /mnt/restore /mnt/restore/avatars'"

# 6. Забрать файл к себе. MSYS_NO_PATHCONV=1 обязателен в Git Bash:
#    без него /mnt/... превращается в C:/Program Files/Git/mnt/...
MSYS_NO_PATHCONV=1 flyctl ssh sftp get /mnt/restore/avatars/1.png ./restored.png \
  -a energydess-tools

# 7. УБРАТЬ ЗА СОБОЙ — иначе машина и том капают в счёт
flyctl machine stop ID_МАШИНЫ -a energydess-tools
flyctl machine destroy ID_МАШИНЫ -a energydess-tools --force
flyctl volumes destroy vol_НОВЫЙ --yes
```

Проверить, что убрано:

```bash
flyctl volumes list -a energydess-tools    # должен остаться один том data
flyctl machine list -a energydess-tools    # одна машина приложения
```

### Что можно посмотреть в базе из снапшота, не разворачивая её

База на восстановленном томе открывается только на чтение — этого хватает,
чтобы сверить состояние на дату или вытащить одну запись:

```bash
flyctl ssh console -a energydess-tools --machine ID_МАШИНЫ -C "python -c \"
import sqlite3
c=sqlite3.connect('file:/mnt/restore/app.db?mode=ro', uri=True)
print(c.execute('PRAGMA integrity_check').fetchone()[0])
print('users:', c.execute('SELECT COUNT(*) FROM users').fetchone()[0])
\""
```

### Что где лежит

| Файл | Роль | `youtube_id` |
|---|---|---|
| `exercises_seed.json` (корень) | семя для первичного наполнения пустой базы | нет ни одного |
| `backups/exercises/exercises-ГГГГ-ММ-ДД.json` | снимок живого справочника | 852 из 873 |

Перепутать их нельзя по конструкции: seed — голый список, снимок — объект
с полем `формат`. `--restore` на seed отвечает «ОСТАНОВЛЕНО» и объясняет
разницу. Раньше seed назывался `exercises_data.json` — переименован ровно
затем, чтобы имя говорило о роли.

`backups/` исключён из образа: восстановление идёт с локальной машины,
а лишняя копия рядом с seed — та самая путаница.

### Снять снимок

```bash
flyctl ssh console -a energydess-tools -C "sh -c 'cd /app && python dump_exercises.py --dump'"
MSYS_NO_PATHCONV=1 flyctl ssh sftp get /app/backups/exercises/exercises-ГГГГ-ММ-ДД.json \
  ./backups/exercises/exercises-ГГГГ-ММ-ДД.json -a energydess-tools
flyctl ssh console -a energydess-tools -C "rm -rf /app/backups"
git add backups/exercises/ && git commit -m "backup: снимок справочника" && git push
```

`MSYS_NO_PATHCONV=1` обязателен в Git Bash: без него `/app/...` превращается
в `C:/Program Files/Git/app/...`.

### Восстановить

Сначала всегда `--dry-run` — он показывает, что изменится, и ничего не пишет:

```bash
py dump_exercises.py --restore backups/exercises/exercises-ГГГГ-ММ-ДД.json --dry-run
py dump_exercises.py --restore backups/exercises/exercises-ГГГГ-ММ-ДД.json
```

Импорт только добавляет и обновляет; записи, которых нет в файле, из базы
не удаляются. Всё одной транзакцией: полусобранный справочник хуже старого.

На проде — с `DB_PATH=/data/app.db` через `flyctl ssh console`, но сначала
убедиться, что снимок свежий, иначе откатятся результаты последней модерации.

### Когда снимать

После пополнения видео или ручной модерации в админке (на сегодня
модерации не было ни одной: `approved` и `wrong` пусты). Ежедневно
не нужно: справочник
меняется редко, снимок весит ~4 МБ и остаётся в истории git навсегда.

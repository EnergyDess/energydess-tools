## 2. Стек

**Бэкенд:** Python 3.12, FastAPI + Uvicorn, Jinja2 (HTML-шаблоны), SQLAlchemy + SQLite, bcrypt + python-jose, httpx для внешних API.

**Фронтенд:** Ванильный JS + чистый CSS в шаблонах. Никакого React, Node.js, сборщиков. Это не SPA.

**Иконки:** Lucide через CDN (`https://unpkg.com/lucide@latest`). Эмодзи в UI-элементах запрещены — см. `design-system.md`, раздел 8.

**ИИ (через OpenRouter API).**

Приоритет источников, от слабого к сильному: **дефолт в коде → `fly.toml [env]` → секрет Fly**. Секрет перекрывает всё, и `flyctl secrets list` показывает только имена, не значения — поэтому фактическое значение проверяется на машине:

```bash
flyctl ssh console -a energydess-tools -C "python -c \"import os;print(os.getenv('LETTER_MODEL'))\""
```

| Переменная | Дефолт в коде | `fly.toml [env]` | Секрет | **Работает на проде** |
|---|---|---|---|---|
| `LETTER_MODEL` | `opus-4-5` | — | `opus-4-8` | **`opus-4-8`** |
| `ANALYZE_MODEL` | `sonnet-4-5` | — | — | **`sonnet-4-5`** |
| `PARSER_MODEL` | `sonnet-4-5` | — | — | **`sonnet-4-5`** |
| `MODEL` | `haiku-4-5` | `haiku-4-5` | — | **`haiku-4-5`** |

Назначение: `LETTER_MODEL` — генерация сопроводительных писем; `ANALYZE_MODEL` — анализ вакансии и оценка релевантности; `PARSER_MODEL` — парсинг резюме в досье; `MODEL` — лёгкие задачи (нутриция, простые классификации).

**Правило:** одну переменную задавать в ОДНОМ месте. `LETTER_MODEL` намеренно убран из `fly.toml`: там лежало `sonnet-4-5`, тогда как секрет давал `opus-4-8` — файл противоречил реальности, и любой, кто прочитал бы его, ошибся бы в выводах.

### 2.1. Потолки ответа: все с именем, все замерены

**Правило: числа `max_tokens` на месте вызова в проекте нет ни одного.** Каждый
потолок — именованная константа в шапке `main.py` с переопределением из
окружения. Число на месте невидимо: его нельзя грепнуть, нельзя сверить
с расходом и нельзя поднять без передеплоя. Ровно так `/api/analyze-vacancy`
жил с захардкоженными `700`, пока таблица здесь утверждала, что лимит поднят
до 2000.

| Константа | Потолок | Что генерирует | Фактический расход (замер 2026-08-11) | Запас |
|---|---:|---|---:|---:|
| `ANALYZE_MAX_TOKENS` | 2000 | анализ вакансии, JSON из 9 полей | 552–958 | **2,1×** |
| `LETTER_MAX_TOKENS` | 3000 | письмо, 200–450 слов | 793 (письмо 2049 симв.) | **3,8×** |
| `PARSER_MAX_TOKENS` | 4000 | резюме → досье, JSON со всем опытом | 402 | **10×** |
| `PROGRAM_MAX_TOKENS` | 6000 | программа тренировок, 3–6 дней | не замерен | — |
| `CHAT_MAX_TOKENS` | 1000 | реплика ассистента (дневник, тренер) | ~110 (270 симв. в базе) | **9×** |
| `VISION_MAX_TOKENS` | 800 | разбор фото еды, распознавание тренажёра | не замерен | — |
| `FOOD_MAX_TOKENS` | 300 | КБЖУ продукта, JSON из 5 чисел | не замерен | — |

Замеры сняты настоящими вызовами через локальное приложение. Отношение
русского текста к токенам **уточнено 2026-08-11 на четырнадцати письмах
с прода**: 2,37–2,53 символа на токен, среднее **2,45**. Прежняя цифра
2,58 стояла по одному замеру (2049 / 793) и завышала запас на 5%.
Считались настоящим вызовом: текст уходит промптом с `max_tokens=1`,
читается `prompt_tokens`.
По нему считается худший разрешённый промптом случай: письмо в 450 слов —
это ~3150 символов, то есть ~1220 токенов. **Прежний потолок письма был 1500**,
и в худшем случае оставалось 19% запаса — а при структурированном ответе
на вопросы работодателя (промпт это разрешает) его не оставалось вовсе.
Обрыв письма при этом не диагностировался никак: `finish_reason` там
не читался, оборванное на середине фразы письмо отдавалось пользователю
и уезжало в историю как готовое.

Четыре потолка помечены «не замерен» честно: живого вызова с полными
входными данными для них в этот заход не было. Строка расхода в логе
(ниже) закрывает это без отдельной работы — первый же вызов на проде
напечатает число.

**`finish_reason` разбирается во всех девяти точках вызова, через один
`_model_output`.** Он же печатает расход **всегда**, а не только при обрыве:

```
[letter] finish=stop токенов=793 из 3000
[analyze] finish=length токенов=60 из 60   ← обрыв, наружу уходит 502 с внятным текстом
[parser] finish=stop токенов=1900 из 2000  ← ЗАПАС КОНЧАЕТСЯ (порог 80%)
```

Это единственный способ узнать фактический расход на проде: `usage`
нигде не сохраняется, и без строки в логе запас у потолка проверяется
рассуждением, а не замером. Метки: `analyze`, `letter`, `parser`,
`program`, `nut-chat`, `wk-chat`, `vision`, `food`.

Отрицательный тест проведён, а не только положительный: приложение поднято
с `ANALYZE_MAX_TOKENS=60 LETTER_MAX_TOKENS=60`, оба эндпоинта вернули 502
с человеческим текстом, в логе `finish=length` и число. Разбор самого
`_model_output` — `tests/test_model_output.py`, 9 тестов.

**Анализ вакансии живёт в ДВУХ местах, и правка одного не доезжает до второго.** Внутри `/api/generate-letter` (первый этап генерации) и отдельным эндпоинтом `/api/analyze-vacancy` за кнопкой «Проверить совпадение с резюме». Задача 8 подняла лимит и завела разбор `finish_reason` только в первом; второй до 2026-08-11 ходил в `LETTER_MODEL` с захардкоженными `max_tokens: 700` — то есть таблица выше про него **врала**, а пользователь получал `Unterminated string at line 22 column 5`. Замер: ответ анализа на живой вакансии занимает 958 токенов, при 700 модель обрывается на середине строки. Лимит поднимать не пришлось — 2000 хватает вдвое, чинить надо было второе место.

Правило на будущее: **меняете параметр вызова модели — грепните имя переменной по всему `main.py`, а не правьте то место, куда привёл стектрейс.** Обе команды ниже обязаны давать пусто:

```bash
grep -nE '"max_tokens":\s*[0-9]' main.py          # число на месте вызова
grep -n 'json()\["choices"\]' main.py             # разбор ответа мимо _model_output
```

**Деплой:** Fly.io, автодеплой через GitHub Actions на push в `main`.

## 4. Темы разделов

Каждый раздел объявляет класс темы **на `<body>`** — не на `<main>`
и не на обёртке контента. Тема объявляет **четыре** токена и больше
ничего: `--tool-accent`, `--tool-accent-dim`, `--tool-accent-hover`
и `--tool-accent-ink` (цвет надписи на акцентной заливке). Вся остальная
механика — лесенка поверхностей, типографика, отступы, состояния —
наследуется из `:root`.

Четыре, а не два, с 2026-08-09: `BACKLOG.md`, задача 43. Акцент
не объявляется в одиночку — разделить заливку и надпись значит получить
белый текст на янтаре, 2.15. По той же причине классы `.theme-*` и `.tool-*`
объявлены в `style.css` **одним правилом на пару**.

| Раздел | Класс темы | Акцент | Иконка Lucide | Mono-label | Применён |
|---|---|---|---|---|---|
| HH-ассистент | `.theme-hh` | electric blue #4F8FFF | `Briefcase` | `КАРЬЕРА` | да, `<body>` |
| Дневник питания | `.theme-nutrition` | emerald #10B981 | `Salad` | `ПИТАНИЕ` | да, `<body>`, с 2026-08-09 |
| Тренировки | `.theme-workout` | amber #F59E0B | `Dumbbell` | `ТРЕНИРОВКИ` | да, `<body>`, обе страницы |
| Enshrouded | `.theme-enshrouded` | copper #D97706 | `Shield` | `ИГРЫ · ENSHROUDED` | **нет**, свои хардкоды |

Последняя колонка — не украшение. Тема, объявленная в таблице и
не применённая в коде, читается как «акцент раздела работает», а он
не разрешается ни во что, и отказ немой: свойство просто не применяется,
консоль чистая. Замерено 2026-08-06 на живом дереве. Дневник переведён
2026-08-09 (замер по шестнадцати элементам, включая все двенадцать
модалок, тост и меню вложений — везде `#10B981`). Enshrouded остаётся:
`BACKLOG.md`, задача 38, вторая половина.

**Замер переменной ≠ замер пикселя.** Тот же заход показал, что
`--tool-accent` у `.site-header` разрешался с 2026-08-06, а фокус-кольцо
поля поиска всё это время оставалось синим: правило
`.header-search .input:focus` в `style.css` било компонент по специфичности.
Документ полтора месяца утверждал обратное, потому что вывод сделали
из замера переменной и не проверили. Подробности — `design-system.md` §7.7.

**Почему именно `<body>`, а не `<main>`:** переменные наследуются вниз
по дереву, и объявление на `<main>` обрезает акцент по границе главного
блока — всё, что лежит рядом (оверлеи, лайтбоксы, тултипы, тосты,
припаркованные в конце `<body>`), темы не видит. Подробнее и с замерами —
`design-system.md`, раздел 7.7.

## 5. Важные архитектурные нюансы

- **Резюме пользователя** живёт в HH-ассистенте (`/hh` → вкладка «Резюме»), НЕ в профиле (`/profile`). Это архитектурное решение: резюме — данные для HH-модуля, а не общий профильный атрибут.
- **Профиль** содержит: аватар, отображаемое имя, email + смена email, смена пароля, часовой пояс, уведомления, удаление аккаунта. См. `design-system.md`, раздел 10.1.
- **Аватар пользователя** — реализован: кругляшка 36×36 в верхней шапке справа (`templates/_avatar.html`), клик открывает dropdown с ссылками (Профиль, Админ, Выйти). Отдельные текстовые ссылки в шапке НЕ используются. Само изображение пока не грузится — показывается буква-инициал, загрузка файла в BACKLOG.md, задача 3.
- **Sticky-навигация** — верхняя шапка всегда прикреплена при скролле. См. `design-system.md`, раздел 4.
- **Глобальный поиск** в шапке — сделан целиком (`static/header-search.js`), задача 5b закрыта 2026-07-27. Инструменты фильтруются локально и без сети (их мало, они стабильны); письма и пользовательские продукты приходят с `/api/search`, и только когда человек начал печатать. Паттерн WAI-ARIA combobox с виртуальным фокусом через `aria-activedescendant`. Плейсхолдер — «Найти инструмент, письмо, продукт…»: узкий вариант «Найти инструмент…» стоял только на время, пока поиск умел одну навигацию.
- **TRAINER_PROMPT.md** исключён из `.dockerignore` намеренно — он нужен в проде.
- **SQLite база** — `app.db`, volume `/data` на Fly.io.

### 5.0. Вакансия hh берётся из JSON, а не из разметки

**Правило:** `/api/fetch-url` сначала пробует `_extract_hh_vacancy` — разбор
`<template id="HH-Lux-InitialState">`, — и только при неудаче откатывается
на общий обход тегов `_extract_text`. Порядок не менять, обход тегов
для hh не восстанавливать.

Причина. hh.ru — React-приложение: описание вакансии в отдаваемой сервером
разметке **не рендерится вовсе**, оно приезжает полем `vacancyView.description`
в JSON начального состояния. Общий обход тегов давал заголовок, куки-баннер
дважды и плашки «Опыт работы 1–3 года» — ни требований, ни обязанностей.

Отказ был немой и **выглядел как успех**: страница загрузилась, текст
извлёкся, счётчик показал «5 748 символов», зелёная галочка. Письма при
этом выходили приемлемые — модель домысливала по названию должности, —
то есть инструмент работал вопреки входным данным, и заметить это можно
было только прочитав, что именно уехало в модель.

| Что | Где | Замер 2026-08-11 |
|---|---|---|
| описание в DOM | `data-qa="vacancy-description"` | **отсутствует** |
| описание в JSON | `vacancyView.description`, экранировано дважды | есть, 5035 символов |
| старый разбор на архивной вакансии | `_extract_text` | 960 символов, описания ноль |
| новый разбор там же | `_extract_hh_vacancy` | 1139 символов, описание на месте |

Проверено на восьми вакансиях hh и rabota.by — все восемь идут по ветке
JSON. Клоны (`rabota.by`, `belarus.hh.ru`) отличать не надо: структура
одна, разбор берёт их тем же кодом.

**Вторая половина правила — проверка того, что разобралось.**
`_vacancy_quality` возвращает причину, по которой текст не похож на
описание (короткий; нет ни требований, ни обязанностей, ни одного длинного
абзаца), и она показывается **до** генерации отдельной плашкой
`.alert-warn`. Без неё любой следующий отказ разбора снова стал бы
«вроде что-то загрузилось»: единственный способ поймать немой отказ —
сверять содержимое, а не длину. Тесты — `tests/test_vacancy_parse.py`.

Чего проверка не ловит намеренно: вакансию, написанную прозой без слов
«требования» и «обязанности», она пропускает по длине абзаца — служебные
плашки всегда короткие. Ложная тревога здесь дороже пропуска: человек
перестанет читать плашку на третий раз.

### 5.1. Отдача чужих файлов: исключений для админа нет

`/avatar/{user_id}` и будущий `/media/{kind}/{token}` отдают файл **только
владельцу**. Ветки «а администратору можно» там нет и появляться не должна.

Причина не в паранойе, а в согласованности с документом: политика
конфиденциальности прямо говорит, что письма, дневники, измерения,
фотографии и переписка с ассистентами в служебном интерфейсе
не отображаются. Появится обход по `is_admin` — политика станет неверной
в ту же секунду и молча, потому что читать её никто заново не станет.

Проверка при code review одна: в обработчике отдачи медиа сравнивается
`запись.user_id == user.id`, и больше ничего. Не совпало — **404**, а не
403: отказ по правам подтверждает, что файл существует.

Понадобится служебный экран с чужими файлами — сначала правка политики,
потом код, а не наоборот.

## 6. Правила работы с кодом

- Разбивать работу по фазам, отчёт после каждой, всегда показывать реальный код (не summary).
- Перед добавлением UI-элемента — проверить, есть ли уже такой в `design-system.md`, раздел 2 «Компонентная база». Если есть — использовать существующий класс. Если нет — сначала обсудить, что за компонент, и добавить в дизайн-систему.
- CSS-переменные — только из `design-system.md`, раздел 13. Никаких новых токенов без обсуждения.
- Хардкод-цвета в HTML/CSS — запрещены. Всё через переменные.
- Хардкод-размеры шрифтов и отступов — запрещены. Всё через шкалу (`--text-*`, `--space-*`) или `clamp()`.
- Inline `<style>` в шаблонах Jinja2 — по возможности избегать. Общее — в `style.css`. Если нужен uniquely-page стиль — оформлять в отдельный `<style>`-блок в начале шаблона с комментарием «TODO: перенести в модульный CSS».

### 6.0. Кириллица ломает shell и jq. Латиница в машинном слое

**Правило:** всё, что читает не Python, — только ASCII. Имена переменных
bash, ключи JSON, которые разбирает `jq`, имена файлов в командах.
Комментарии и текст для человека остаются русскими.

Почему это отдельный раздел, а не строка в шапке workflow: там
предупреждение уже висело, и за одну сессию я наступил на те же грабли
**пять раз** — в тесте, в диагностике, в отпечатке справочника. Значит
место было выбрано неудачно. Здесь оно попадается при написании кода,
а не при чтении файла целиком.

| Где | Что ломается | Симптом |
|---|---|---|
| имя переменной bash | `вывод=$(...)` | `вывод=Connecting: command not found`, код 127 |
| ключ JSON под `jq` | `.хеш` | `jq: error: syntax error, unexpected INVALID_CHARACTER` |
| `jq` с кириллицей всё же нужен | — | только через `.["хеш"]`, но лучше переименовать |
| `bytes`-литерал в Python | `b"текст"` | `SyntaxError: bytes can only contain ASCII` |

Правило простое: **если строка попадёт в shell, `jq` или имя файла —
латиница.** Значения внутри могут быть любыми, ограничение только
на имена и ключи.

Живой пример разделения: `dump_exercises.py` печатает отпечаток
с ключами `total`, `with_video`, `hash` — его читает `jq` в workflow.
А внутри самого снимка ключи русские (`формат`, `упражнения`,
`счётчики`), потому что тот файл читает человек.

### 6.0.2. Страница не переопределяет систему. Девять проверок и один ручной пункт

**Правило:** страничный CSS не объявляет селекторы из компонентной базы,
не переопределяет токены и не выносит статические стили в атрибут `style=`.

Почему правилом, а не уборкой. Специфичность всплывала четыре раза, и один
раз мы уже чинили этот файл — коммит `d387c67` убрал хардкоды из медиазапроса
`nutrition`, но **причина осталась**: `.card` и `--border` там переопределены
до сих пор. Уборка без правила даёт возврат через полгода, потому что
архитектура переопределение разрешает: стили страницы грузятся после
`style.css` и выигрывают при равной специфичности, а `style=` бьёт вообще
любой файловый селектор.

| Что нельзя | Почему | Что вместо |
|---|---|---|
| `.card`, `.btn-primary`, `.input`… в шаблоне или в `hh.css`/`profile.css` | компонент ломается везде, где окажется на странице | системный компонент как есть — либо **новый вариант в системе** |
| `--border`, `--surface-1`… вне `:root` в `style.css` | меняет всю страницу молча; правка в `style.css` до неё не дойдёт | добавить вариант токена в систему |
| `style="margin-bottom:8px"` в разметке | бьёт любой селектор, в грепы по классам не попадает | класс в CSS |

**Префикс страницы (`.nut-card`) — не путь по умолчанию, а исключение.**
Если странице нужна карточка, отличная от системной, это почти всегда значит,
что в системе не хватает варианта: правильный ход — добавить его туда.
Префикс допустим только для того, чего в системе нет и быть не должно
(например, раскладка конкретного экрана). Иначе через полгода получим три
системы вместо одной: `.nut-card`, `.work-card`, `.hh-card`.

**Девять проверок** — шесть грепов и три скрипта. Скрипт там, где грепом
честно не выходит: у седьмой надо разбирать кодовые блоки документации,
у восьмой — сверять CSS с разметкой, у девятой — историю git со статусами
задач. Все три читаются по коду возврата.
Грепы ходят и по шаблонам, и по CSS-файлам (класс уже переехал

он не переопределение и не инлайн — синтаксис разметки, а не стиль.

в отличие от ручного пункта ниже.

Три замечания по самому грепу:

| Что | Почему так |
|---|---|
| `-P`, а не `-E` | нужна обратная ссылка `\1` — «тот же атрибут второй раз». В POSIX ERE её нет |
| `[^>]*` между атрибутами | ограничивает поиск ОДНИМ тегом: без этого `<div class="a"><span class="b">` в одной строке считалось бы дублем |
| `-i` | в HTML имя атрибута регистронезависимо: `<img SRC="1" src="2">` — дубль. Без `-i` обратная ссылка требует совпадения регистра и такой тег проходит мимо |
| `-z` в 6b | тег, разорванный переносом, построчный греп пропускает. `-z` читает файл одной строкой, и `[^>]*` начинает захватывать переводы строки. Раньше это сверялось руками «на глаз»; теперь это команда |

#### Проверка 8: id весит больше класса, и первая проверка его не видит

Заведена 2026-08-11. Форма была названа накануне при разборе задачи 45
(`#resume-textarea` в `hh.css` менял компоненту кегль) и отложена
до замера масштаба. Замерили.

Проверка 1 ищет системный класс **субъектом**: `.hero .btn-primary { … }`.
Правило `#hero-cta { … }` на том же элементе она не видит вовсе — а весит
оно больше: id это (1,0,0), любой класс (0,1,0). **Форма и невидимая,
и более сильная разом.**

Отказ немой в обе стороны:

| Сторона | Что происходит |
|---|---|
| компонент рисуется не по системе | разметка верная, класс на месте, консоль чистая — по коду не увидеть |
| компонент чинят в `style.css` | до такого элемента правка не доедет: id выигрывает и у медиазапроса, и у нового варианта |

**Почему скрипт, а не восьмой греп.** Разницы между долгом и законной
строкой в самом правиле нет. `#job-input { min-height: 300px }` законно
(высота экземпляра), `#job-input { font-size: … }` — долг (кегль
принадлежит компоненту). Отличают их две вещи сразу: какие свойства
объявлены **и носит ли элемент с этим id системный класс**. Второе лежит
в разметке, а не в CSS.

Замер на живом дереве: правил по id в проекте **48**, на элементе
с системным классом — **3**. Греп без разбора разметки печатал бы
48 строк, из которых 45 чужие: 94% ложных. Проверка, которая врёт,

**Список компонентов проверка не дублирует** — читает строку `names='…'`

проходит с пустым списком: whitelist, который молча опустел, печатает
«чисто» про всё на свете.

Свойства делятся по тому же критерию, что первое число: раскладка
экземпляра (`width`, `height`, `min-*`, `flex`, `margin`, `position`…) —
законна и в код возврата не идёт; вид компонента (`font-*`, `color`,

потому что список префиксов требовал имя сразу после `--`, а там стоит `tool`.
`.modal h3` прошёл мимо проверки 1, потому что это селектор потомка, а греп
искал имя в начале строки перед `{`, `,` или `:`. Мёртвый `.modal` в `style.css`
никакая проверка не искала вовсе. Причина у всех трёх одна: **регулярка
писалась под тот случай, который был перед глазами в момент написания.**

Поэтому проверки пересмотрены не вопросом «что она ловит», а вопросом
«какая форма нарушения проходит мимо». Ниже — что изменилось и что
осталось непокрытым **осознанно**.

**Проверка 1.** Было: `^\s*\.имя\s*[,{:]` — только имя в начале строки.
Проходили мимо: селектор потомка (`.modal h3`), соседа (`.card + .card`),
составной (`main.container`, `.card.active`), имя внутри
`:is()`/`:where()`/`:not()`, имя не первым в списке (`.foo, .card {`),
имя внутри `@media { .card {` на одной строке. Стало: имя класса **где угодно
на строке**, лишь бы на той же строке была `{`. Требование `{` — единственное,
что отделяет CSS-правило от прозы и от `closest('.card')` в скрипте;
без него проверка выдавала полтора десятка ложных срабатываний на
комментариях, где классы просто упомянуты.

Что это дало сразу: находок стало **16 вместо 1**. Пятнадцать новых —
не регресс, а долг, который проверка не показывала (`BACKLOG.md`, задача 37;
закрыта 2026-08-06, долговых строк не осталось).

**Правка 2026-08-06: «где угодно на строке» оказалось слишком широко.**
Под это попадал предок — `.tool-card .eyebrow` — где системный класс
вообще не оформляется, а только задаёт контекст своему. Такие строки
пишутся при нормальной работе, и число росло бы от неё же. Уточнение:
системный класс обязан быть **субъектом** селектора, то есть последним
в своей связке (дальше только `:псевдокласс`, `.класс`, `[атрибут]`,
потом сразу `,` или `{`). Пробел перед скобкой означает, что субъект
другой. Формы, на которых это проверено, — таблица выше.

Проверялась и обратная гипотеза: не ловит ли проверка сам `style.css`.
Не ловит и не может — его нет в `$pages` и не было ни разу. Если бы
был, дал бы 36 находок одной только системой, описывающей саму себя.
`main.container { max-width: 1600px }`, из-за которого вопрос и возник,
живёт в `static/hh.css:8` — то есть это страничный файл, меняющий
системный контейнер, и находка настоящая.

**Проверка 2.** Было: список префиксов имён. Список — это whitelist, и всё,
что в него не попало, невидимо: `--shadow-lg`, `--warning`, `--error`,
`--radius-xl`, `--ease-out`. `--tool-accent` был не единственной дырой,
а первой замеченной. (Здесь до 2026-08-06 стояло `--max-w` — токена
с таким именем в системе нет и не было, то есть пример был выдуман.
Нашла его проверка 7, см. ниже.) Стало: **список токенов берётся из самого `style.css`** прямо
перед прогоном — 63 имени на сегодня. Пятно закрыто не расширением списка,
а тем, что списка больше нет: имя, которого нет в системе, и не может быть
её переопределением, а любое системное имя проверяется по факту.
Плюс снят якорь `^\s*`, поэтому ловятся `.x { --border: red }` в одну строку
и `style="--border: red"` в разметке. Последнее важно: проверка 3 считает
инлайновый стиль из одних CSS-переменных **законным** и пропускает его —
через эту дверь системный токен переопределялся молча.

**Проверка 3.** Добавлены `static/*.js` в область (разметку собирает не только
Jinja) и отдельный проход 3a под `style='…'` в одинарных кавычках: HTML их
допускает, а прежний греп искал только двойные. Разбирать одинарные тем же
конвейером не стали — четыре звена исключений пришлось бы переписать
с экранированием кавычек внутри кавычек, а форм таких в проекте ноль;
дешевле называть их целиком и разбирать глазами, если появятся.

**Проверка 4.** Было: страница **упоминает** партиал шапки. Форма, проходившая
мимо: страница партиал подключила и **вдобавок** нарисовала свою шапку —
ровно то, чем была `<nav class="nav">`. Добавлена 4b: прямой поиск
`class="nav"` и `class="site-header"` в разметке страниц.

**Проверка 6.** Добавлены `-i` (в HTML имя атрибута регистронезависимо)
и поддержка одинарных кавычек; сверка многострочных тегов перестала быть
ручной — это 6b.

#### Признанные пробелы: что не ловится и проверяется глазами

Проверка с честно названной границей полезнее той, про которую думают,
что она видит всё. Ниже — формы, которые **остаются** непокрытыми, и почему
их не стали автоматизировать.

| Проверка | Что проходит мимо | Почему не закрыто |
|---|---|---|
| 1 | селектор, разорванный переносом: `.foo,`↵`.card`↵`{` — на строке с именем нет `{` | построчный греп такого не видит; вариант с `-z` даёт ложные срабатывания на каждом упоминании класса в комментарии, а комментариев в этих файлах много |
| 1 | имя класса, собранное в скрипте: `'.' + вид + '-card'` | не существует в исходнике как строка |
| 1 | **ложное** срабатывание: проза, где рядом стоят имя класса и `{` | лечится не грепом, а формулировкой комментария — см. `nutrition.css`, где пришлось убрать скобки из пояснения |
| 1 | системный класс как СУБЪЕКТ, но со свойством раскладки: `.save-bar .btn-primary { width: 100% }` | попадает в вывод, хотя законно: `width`, `flex`, `min-width` принадлежат родителю, а не компоненту. Отличить грепом нельзя — надо читать объявления. Поэтому первое число, как и пятое, разбирается по таблице в задаче 37, а не считается долгом целиком |
| 7 | утверждение о смысле: охват («на всех страницах»), потребитель, технология, строка интерфейса | буквального представления в коде нет — сверять не с чем. Полный список и разбор каждого — таблица «ГРАНИЦА» выше. Размер `36×36` сюда больше не входит: с 2026-08-09 его берёт проход C |
| 2 | токен, переопределённый анимацией или `@property` | форм в проекте нет; появятся — добавить звено |
| 3 | `элемент.style.свойство = …` в скрипте (146 мест) | подавляющее большинство законно рантаймовые; регулярка не отличит их от статики, а проверка, которая врёт в половине случаев, перестаёт читаться целиком |
| 3 | атрибут `style`, разорванный переносом строки | то же, что у проверки 1 |
| 3 | `style="{{ весь_стиль }}"` — атрибут целиком из переменной | попадает в вывод как долг, хотя может быть законным. Оставлено намеренно: ложная тревога здесь безопаснее пропуска |
| 4, 5 | партиал **упомянут в комментарии**, но не подключён; `include` под условием, которое никогда не истинно | греп проверяет наличие строки, а не факт вывода. Отличить может только рендер |
| 6 | дубль, разнесённый по веткам Jinja: `{% if %}class="a"{% else %}class="b"{% endif %}` | в файле это не дубль, а в выводе — дубль. Ловится только рендером |
| 6 | атрибут без кавычек: `<div class=a class=b>` | форм в проекте ноль; регулярка без кавычек цепляет слишком многое |
| 8 | класс, навешенный скриптом (`el.classList.add('card')`); id, собранный в рантайме | в разметке такой строки нет, а исполнять скрипт проверка не может |
| 8 | `!important` на правиле по КЛАССУ, бьющий систему тем же способом | другая форма: её видит проверка 1, если имя в `names`. Экземпляр в проекте один и он назван — `.spinner`, задача 45 |
| 9 | задача, у которой устарел не статус, а **содержание**: названы файлы, которых нет, план разошёлся с решением | буквального представления в коде нет. Лечится пунктом в §6.2 — сводка бэклога читается по коду, а не по заголовку |
| 9 | работа без номера задачи в теме коммита; «ЧАСТИЧНО», под которым сделано всё; «ВЫПОЛНЕНА» после отката | пропуски, а не ложь. Шесть из девяти расхождений сводки 2026-08-11 проверка бы не нашла — их закрывали походя |
| все | **самодельный компонент** — кнопка, поле, модалка, алерт под своим именем | ручной пункт ниже, автоматизировать нечем |

Четвёртый и пятый греп — про ту же болезнь, что первые три, только на этаж
выше: страница не переопределяет систему **и не пересобирает её заново**.
Своя `<nav class="nav">` на шести страницах входа была именно этим: копия
шапки, которая жила отдельной жизнью и молча расходилась с общей — на
`verify_required` она успела отрастить пару текстовых ссылок «Профиль /
Выйти», прямо запрещённых в `design-system.md`, разделе 4.

Обе проверки печатают **имена файлов**, а не строки, и молчание означает
«чисто». `grep -L` — это «файлы БЕЗ совпадения»; `grep -v '/_'` убирает
сами partials, у которых include самих себя быть и не должно. В четвёртом
грепе `_admin_nav.html` перечислен рядом с `_header.html` не для красоты:
админка подключает шапку через него, и без этого альтернатива дала бы
четыре ложных срабатывания подряд — а проверка, которая врёт, перестаёт
читаться на третий раз.

**Законные исключения на сегодня** — их видно в выводе пятого грепа, и это
не долг:

| Файл | Почему без футера |
|---|---|
| `verify_pending.html` | условия приняты шагом раньше, на регистрации |
| `verify_required.html` | то же: человек уже зарегистрирован и вошёл |

Всё остальное в выводе — долг, он расписан в `BACKLOG.md`, задачи 27 и 28.

#### Ручной пункт: компонентная база

Греп ловит переопределения и самодельные шапки, но не ловит **самодельные
кнопки, поля, модалки и алерты**: `<button class="verify-resend-btn">` —
это ни системный класс (значит, греп 1 молчит), ни инлайн (греп 3 молчит),
а просто новый компонент, которого в системе нет.

Поэтому пункт ручной и остаётся ручным: **кнопки, поля, модалки и алерты
на странице взяты из компонентной базы; каждое исключение названо вслух —
что это и почему не системный класс.** Автоматизировать его нечем. Регулярка
не отличит «кнопку с другим оформлением, потому что так надо» от «кнопку
с другим оформлением, потому что автор не посмотрел в дизайн-систему», и
проверка, которая врёт в половине случаев, перестаёт читаться целиком —
ровно как это случилось бы с грепом 4 без `_admin_nav.html`.

Третий греп написан именно так, потому что первая его версия имела слепое
пятно того самого класса, за которым мы гоняемся: она отсеивала строку
целиком, если в ней встречалось `{{`. То есть `style="width: {{ x }}%"`
пропускался законно, а `style="width: {{ x }}%; border: 1px solid red"` —
незаконно, и проверка рапортовала «чисто». Теперь исключается только то,
что законно **целиком**: смесь законного и статики ловится.

**Пятое звено — `${...}` — добавлено 2026-08-04.** Разметку у нас собирает
не только Jinja: в `nutrition.html` и `workout.html` куски HTML строит
скрипт шаблонными строками, и `style="height:${h}%"` — такое же рантаймовое
значение, как `{{ }}`, записать его в CSS точно так же нечем. Пока звена
не было, эти строки попадали в вывод как долг, которого нет. Форма у звена
намеренно та же, что у Jinja-звена: пропускается ОДНО свойство, значение
которого целиком выражение. Смесь выражения со статикой ловится по-прежнему.

Проверять изменения этого грепа надо на шести примерах сразу:

| Пример | Ожидание |
|---|---|
| `style="--n: 3"` | пропустить |
| `style="--n: 3; margin-top: 8px"` | **поймать** |
| `style="width: {{ x }}%"` | пропустить |
| `style="width: {{ x }}%; border: 1px solid red"` | **поймать** |
| `style="height:${h}%"` | пропустить |
| `style="height:${h}%; color: red"` | **поймать** |

#### Где инлайн допустим осознанно

| Случай | Пример | Почему |
|---|---|---|
| значение считается в рантайме | `style="width: {{ процент }}%"` | в CSS его записать нечем |
| переключатель видимости для JS | `style="display:none"` | начальное состояние элемента, которым управляет скрипт |
| CSS-переменная как параметр | `style="--задержка: .3s"` | это данные для стиля, а не сам стиль |

Всё остальное — необёрнутый CSS. `style="margin-bottom:8px"` и
`style="color:var(--text-2);font-size:0.95rem"` относятся ко второй
категории: токен внутри не делает инлайн законным.

### 6.0.1. Подавлять сбой нельзя. Список конструкций для ревью

**Правило:** нельзя подавлять вывод или код возврата у команды, которая
может сработать частично. Отказ, о котором никто не узнал, — дороже отказа:
он выглядит как успех и обнаруживается в тот единственный день, когда
на него положились.

За две сессии этот класс всплывал четыре раза, каждый раз в новом месте:
`except: pass` в анализе вакансии (письма молча выходили без разбора),
`|| true` в уведомлении о сбое бэкапа (полтора месяца немого 404),
`curl` без проверки ответа (404 считался успехом), `2>/dev/null` поверх
упавшего `git add` (в коммит уехала половина работы). Поэтому — не урок,
а список, по которому можно грепнуть.

| Конструкция | Чем плоха | Что вместо |
|---|---|---|
| `except:` без типа | ловит и `KeyboardInterrupt` с `SystemExit` | назвать конкретные исключения |
| `except X: pass` | сбой исчезает бесследно | `print(f"[метка] что не вышло: {e}")` или запись причины в поле |
| `except X: return []` / `return None` | вызывающий не отличит «пусто» от «сломалось» | вернуть признак ошибки либо залогировать |
| `\|\| true` в shell | шаг зеленеет при неудаче | `if ! cmd; then echo "::error::…"; exit 1; fi` |
| `2>/dev/null` | глушит и настоящую причину | убрать; если шумно — фильтровать конкретный текст |
| `curl` без `-f` и без чтения кода | HTTP 404 и 500 — «успех» | `-w '%{http_code}'` и явная проверка, как в `telegram.sh` |
| `set +e`, `continue-on-error: true` | отключает проверки оптом | точечная обработка нужной команды |
| `git add … 2>/dev/null` | частично применённая команда молчит | без подавления, потом `git status` |
| **проверка, чей результат читают глазами** | интерпретатора нет — заглушка печатает текст и «проходит» | читать **код возврата**, а не вывод |

#### Команда, которая проверяет код, сама проверяется по коду возврата

Последняя строка таблицы — не гипотеза. `python check_docs.py` (проверка 7
в §6.0.2) на этой машине **не запускалась ни разу**: `python` в `PATH` —
заглушка Microsoft Store из `WindowsApps`, она печатает
«Python was not found…» и возвращает 9009. Опорное число «проверка 7 — 0»
получено командой, которая не прочитала ни строки, и мы полгода считали
документацию сверенной. Обнаружено 2026-08-08, когда вывод показался
подозрительно коротким.

Родство с `curl` без `-f` прямое: **успехом объявлен ответ, который
успехом не является.** curl считает удачей HTTP 404, заглушка — ненайденный
интерпретатор. В обоих случаях сигнал есть и он верный (код 404, код 9009),
просто его никто не смотрит.

Правило: **у проверки читается код возврата.** Вывод — для человека, код —
для решения. Если проверка вызывается вручную, а не из workflow, кодом
надо интересоваться так же:

```bash
py check_docs.py;    echo "код=$?"     # 0 — сверено, не 0 — разбираться
py check_privacy.py; echo "код=$?"
```

Три признака, по которым такой отказ узнаётся, пока он не стоил полугода:

| Признак | Пример |
|---|---|
| вывод короче обычного и без чисел | вместо «0 расхождений» — одно слово `Python` |
| результат не меняется от правок в проверяемом | сколько ни ломай документ, всё те же «0» |
| код возврата не 0 при «успешном» на вид выводе | 9009 в PowerShell, 49 в Git Bash (те же 9009 по модулю 256) |

**Проверить грепом:**

```bash
grep -rn "except:" --include="*.py" .
grep -rn -A1 "except" --include="*.py" . | grep "pass$"
grep -rn "|| true\|2>/dev/null\|set +e\|continue-on-error" .github/
grep -rn "curl " .github/ | grep -v "http_code"
# локальный вызов python вместо py — заглушка Store молча ничего не сделает.
# Внутри flyctl ssh console python ЗАКОННЫЙ: там Linux и /usr/local/bin/python
grep -n "^\s*python[ 3]" CLAUDE.md *.md
```

#### Где подавление осознанно — и почему

Эти места **не** являются нарушением правила, у каждого своя причина.
Список нужен, чтобы правило не обходили «по аналогии»: аналогия
допустима только с той же причиной, а не с той же конструкцией.

| Место | Конструкция | Почему допустимо |
|---|---|---|
| `backup.yml`, шифрование | `shred \|\| rm` | `shred` может отсутствовать в образе; раннер эфемерный, пароль исчезнет с ним |
| `backup.yml`, уборка дампа | шаг не роняет прогон | идёт под `always()`; упав, перекрыл бы настоящую причину сбоя выше. Молчания при этом нет: `::warning::` плюс сообщение в Telegram |
| `database.py`, миграции | `except Exception: pass` | `ALTER TABLE` на уже применённой миграции обязан падать, это и есть признак «уже сделано» |
| `auth.py`, разбор токена | `return None` | битый токен — это «не авторизован», нормальный ход событий, а не сбой |
| `main.py`, Turnstile | `return False, False` | различает «не прошли» и «проверить не смогли»; решение fail-open принято осознанно, см. §8.1 |
| `make_backup.py`, счётчики | `счётчики[т] = None` | таблицы может не быть на старой базе; None и означает «не посчитано» |

### 6.1. Добавили таблицу с данными пользователя — три обязательных шага

Новая модель с `user_id` затрагивает не только схему. Забыть любой
из шагов легко, потому что все три живут в разных файлах.

**1. Каскад удаления.** Внести таблицу в `USER_TABLES` (или `CHILD_TABLES`,
если привязка идёт через родителя) в `database.py`. Иначе при удалении
аккаунта останутся сироты, а `id` в SQLite переиспользуются — данные
достанутся следующему пользователю. Проверка: `check_user_tables_complete()`,
её сам вызывает `cleanup_unverified.py` и останавливается при расхождении.

Тот же список ведёт **вторую сторону** — проверку «аккаунт пуст», по которой
ночная очистка решает, можно ли удалять. Разойтись они не могут по
конструкции: `user_data_counts()` вызывает `delete_user_cascade(dry_run=True)`
и считает то, что каскад удалил бы. Добавили таблицу в один список —
она попала в обе стороны сразу.

Почему проверка вообще появилась: очистка раньше опиралась на допущение
«неподтверждён — значит пуст», а оно неверно. Вход для неподтверждённых
открыт намеренно (гейт стоит на страницах инструментов, не на входе),
но API записи данных `is_verified` не проверяют — см. BACKLOG №24.

**Третье, что ведёт тот же список: «пусто по умолчанию».** Если строка
в новой таблице появляется САМА при регистрации, её надо внести
в `ПУСТЫЕ_ПО_УМОЛЧАНИЮ` (`database.py`) вместе с условием, что считать
пустотой. Иначе проверка сочтёт заготовку данными, и очистка перестанет
удалять ботов вовсе.

Это не теория: при регистрации каждому заводится пустое резюме, и первый
же прогон новой проверки пропустил 60 аккаунтов вместо одного. Список
лежит в одном месте — рядом с `user_data_counts`, которая его и применяет;
дублировать его где-либо нельзя.

Итого один список таблиц ведёт три вещи: **что удалять**, **что считать
данными**, **что считать заготовкой**.

**2. Политика конфиденциальности.** Назвать категорию в тексте
(`STATIC_PAGES["privacy"]` в `main.py`) и добавить строку
в `PRIVACY_MENTIONS` в `database.py`. Полный перечень обрабатываемых
данных — требование закона, а не стилистика. Проверка:

```bash
py check_privacy.py     # 27 таблиц против текста, код 1 при расхождениях
# ИМЕННО py. python на этой машине — заглушка Store: печатает текст,
# возвращает 9009 и не запускает скрипт. Прогнано 2026-08-08:
# 27 таблиц, 26 категорий, расхождений 0, код 0.
```

Так однажды выпал целый инструмент: трекер Enshrouded не упоминался
в политике вовсе, хотя данные по нему хранились. Проверка ловит три
случая — незаявленную таблицу, исчезнувшую из текста категорию
и оставшуюся в списке удалённую таблицу.

**3. Файлы вне базы.** Если таблица ссылается на файлы на томе — удалять
их в `delete_user_cascade` (образец: `_delete_avatar_file`, вызывается
после `commit` и с учётом `dry_run`). Имя файла лучше не привязывать
к `id` пользователя: `AUTOINCREMENT` на `users` наследование закрывает,
но опираться на одну эту защиту не стоит.

### 6.2. Правка кода, после которой документация правится в том же коммите

**Правило:** если правка меняет то, о чём `design-system.md` или `CLAUDE.md`
делает утверждение, документ правится **в том же коммите**, а не «потом».
Не «не забывать» — ниже таблица-триггер и команда, которая проверяет.

Почему правилом. За три дня документ разошёлся с кодом четыре раза, и ни
разу это не было опечаткой: `.modal` описан сутки после удаления класса,
`--max-w` назван примером системного токена, которого не существовало
никогда, breadcrumbs обещаны на четырёх страницах при одной, аватар
описан 32×32 при коде 36×36. Каждое утверждение было верным в день, когда
его писали. **Устаревает не документ — устаревает код под ним, молча.**

#### СВОДКА БЭКЛОГА ЧИТАЕТСЯ ПО КОДУ, А НЕ ПО ЗАГОЛОВКУ

Отдельным пунктом, потому что на этом уже споткнулись. 2026-08-11 сводка
перечислила одиннадцать «открытых» задач, взяв статусы из шапок, и три
из одиннадцати оказались неверны: задача 20 сделана целиком два дня
назад, 13 закрыта коммитом с её же номером в заголовке, 3 сделана
наполовину. В отчёте при этом стояло «каждое подтверждено чтением кода».

**Правило: строка сводки — это утверждение о коде, и основание у неё
должно быть в коде.** По каждой задаче называется, на чём стоит статус:
файл и функция, либо коммит. Не нашлось основания — так и писать
«не проверено», а не переписывать шапку.

Половину этого закрывает **проверка 9** (`py check_backlog.py`): задача
со статусом «не начата», в которую ведут коммиты с кодом. Вторую половину
не закрывает ничто — из девяти расхождений той сводки проверка нашла бы
три. Остальные шесть закрывали походя, не называя номер задачи в теме
коммита, и машине они невидимы.

Ритм: сводка нужна перед крупной задачей, а не по расписанию. Но раз она
делается — делается по коду.

#### Как это проверяется при ревью

Половину таблицы закрывает машина, половину — один вопрос себе.

**1. Машина.** Первые пять строк, девятая и десятая проверяются
`check_docs.py` (проверка 7, §6.0.2): имена классов и токенов, значения
токенов из `:root`, размеры вида `36×36` рядом с именем класса, имена
файлов. Читается **код возврата**, не вывод (§6.0.1):

```bash
py check_docs.py; echo "код=$?"     # 0 — сверено, не 0 — разбираться
```

**2. Глазами — по диффу, а не по памяти.** Строки про интерфейсные тексты
и про охват машина не берёт принципиально, и почему — названо в шапке
`check_docs.py`. Вопрос при ревью ровно один, и задаётся он к **диффу**:

> В этом диффе есть строка, которую увидит пользователь, или утверждение
> «везде / всегда / только»? Если да — где оно записано словами?

Найденное место правится сейчас. Не нашлось — так и сказать вслух:
«утверждений в документе про это нет», — а не промолчать. Молчание
и «проверил» выглядят одинаково, и это тот же класс отказа, что
`|| true` в §6.0.1.

**3. Коммит.** Правка кода и правка документа — **один коммит**. Разные
коммиты разъезжаются при откате: откатили код, документ остался описывать
откаченное. Именно поэтому компонент, заводимый в `style.css`, и его
описание в `design-system.md` не разделяются никогда.

#### Чего это правило не обещает

Оно ловит расхождения, **вносимые правкой**. Расхождение, накопленное
раньше, оно не найдёт: никто не открывает документ, если код не трогали.
Для накопленного есть только чтение целиком, и оно стоит захода —
2026-08-06 такой заход дал семь находок за раз (`BACKLOG.md`, задача 41).
Разумный ритм — раз в несколько месяцев или после крупной миграции,
а не по расписанию.

### 8.0. Аккаунт для съёмки авторизованных экранов

**Логин `screenshot@local.dev`, пароль `Screenshot-Local-2026`.**
Заводится и сбрасывается скриптом, **только в локальной базе**:

```bash
py make_local_user.py            # завести или сбросить пароль
py make_local_user.py --seed     # плюс данные: резюме, досье, 3 письма, 19 продуктов,
                                 # анкета питания и 17 позиций съеденного за сегодня
py make_local_user.py --drop     # удалить вместе со всеми данными
```

Зачем отдельный аккаунт. Пароль хранится хэшем bcrypt и не восстанавливается
по построению, поэтому каждый заход, которому нужен авторизованный экран,
ломал пароль существующему — `test-admin@local.dev` был переписан дважды
за два дня. То есть съёмка скриншотов портила данные, на которых кто-то
мог работать дальше.

**На проде такого аккаунта быть не должно** — это вход с правами
администратора и с паролем, лежащим открытым текстом в этом файле.
Скрипт проверяет сам и останавливается с кодом 1, если база не локальная:
смотрит `FLY_APP_NAME` и путь `/data`. Проверено на проде отдельно —
2026-08-11 ответ **0**, ни одного адреса на `@local.dev`:

```bash
flyctl ssh console -a energydess-tools -C "python -c \"import sqlite3;c=sqlite3.connect('/data/app.db');print(c.execute(\\\"SELECT COUNT(*) FROM users WHERE email LIKE '%@local.dev'\\\").fetchone()[0])\""
```

`Error: The handle is invalid.` в конце вывода — артефакт закрытия SSH
на Windows, а не сбой запроса (§8.1, последнее замечание).

Ключ `--seed` наполняет аккаунт длинным содержимым намеренно: дефекты
вложенной прокрутки и схлопнутых колонок видны **только** на длинном
тексте и длинных названиях. На пустых экранах и то и другое выглядит
исправным — так эти два дефекта и прожили до 2026-08-11.

**Экран, которого seed не наполняет, не проверяется вовсе.** До 2026-08-11
seed заводил 19 продуктов в справочник, но ни одной записи в `food_logs` —
а дневник рисует карточки приёмов пищи из второй таблицы. Дневник
снимался пустым, и окно 90px на списке съеденного дожило до задачи 52
именно поэтому. Заодно добавлена анкета питания: без неё `/nutrition`
открывается экраном «Личные данные», то есть снять дневник нельзя
в принципе, сколько еды ни записывай.

Правило на будущее: **добавили экран — добавьте ему данные в seed**,
и не в соседнюю таблицу, а ровно в ту, из которой он читает.

### 8.1. Защита формы входа — как устроена

Сделана в BACKLOG №1 (2026-07-27). Вся логика в `main.py` рядом с роутом
`POST /login`, `auth.py` намеренно не тронут.

**Аккаунт не блокируется никогда.** Блокировка по аккаунту дала бы любому,
кто знает адрес, возможность держать чужой вход запертым постоянно —
достаточно вводить неверный пароль. Адрес пользователя знают как минимум
он сам и его почтовый провайдер, так что «знает адрес» — не редкость.
Ограничение только по адресу подключения.

| Неудач за 15 минут | Что происходит |
|---|---|
| 1-2 | ничего |
| 3+ | на форме появляется Turnstile |
| 15+ | отказ, код 429, на 15 минут |

Плюс прогрессивная задержка ответа: с 3-й неудачи 1 с, с 5-й 2 с, с 8-й 4 с
(потолок). Только `await asyncio.sleep` — `time.sleep` заморозил бы весь
event loop и сайт встал бы для всех сразу. Задержка не зависит от Cloudflare
и вместе с лимитом несёт основную нагрузку защиты.

**Успешный вход обнуляет счётчик** этого адреса.

**Ключ счётчика:** для IPv4 — полный адрес, для IPv6 — **префикс `/64`**.
Провайдер выдаёт клиенту целую подсеть `/64`, поэтому счёт по полному адресу
обходился бы бесплатно переключением адреса внутри своей подсети. В логах
печатается именно ключ (`2a00:1fa0:4705:1937::/64`), а не отдельный адрес —
чтобы при разборе инцидента было видно, по чему сработал лимит.

**Реальный IP** берётся из `Fly-Client-IP` → `X-Forwarded-For` →
`request.client.host`. Последнее без прокси-заголовков бесполезно: приложение
за прокси Fly и видит `172.16.13.90` у всех подряд.

**Turnstile работает в режиме fail-open.** Пустой токен (виджет не загрузился
либо проверку не прошли — серверно эти случаи неразличимы) и недоступность
`siteverify` пропускают вход. Отказ только на явное «нет» от Cloudflare.
Следствие принято осознанно: бот, не отправляющий поле капчи, проходит её
насквозь — капча тут дополнительный слой, а не барьер.

**Счётчик живёт в памяти процесса** (`_login_fails`), при рестарте обнуляется —
для защиты от перебора это допустимо. Протухшие записи вычищаются на ходу,
чтобы словарь не рос бесконечно.

Строки в логах: `включена капча`, `отказ на 15 мин`, `капча не отработала
(пустой токен)`, `Cloudflare недоступен с сервера`, `капча не пройдена`.
Каждая попытка не логируется — только моменты срабатывания. Email в логи
не пишется намеренно.

**Аварийное отключение защиты входа** — если лимит сработал против владельца.
Действует мгновенно, без передеплоя:

```bash
flyctl ssh console -a energydess-tools -C "touch /data/ratelimit_off"   # выключить
flyctl ssh console -a energydess-tools -C "rm /data/ratelimit_off"      # включить обратно
```

Файл лежит на volume и **переживает рестарт** — забыть его удалить значит
оставить вход без защиты навсегда. Пока файл существует, каждая попытка входа
пишет в лог строку об этом. Запасной путь, если SSH не отвечает:
`flyctl apps restart energydess-tools` (счётчики живут в памяти процесса).

**Замечание про вывод `flyctl ssh console` на Windows:** в конце команды
регулярно появляется `Error: The handle is invalid.` Это артефакт закрытия
SSH-сессии, а не ошибка скрипта — вывод до этого момента полный и корректный.

## 9. Бэкап базы и восстановление

> Снимки тома Fly (ежедневные, хранятся 30 дней — см. §10) остаются как
> были — это первая линия. Выгрузка в Telegram нужна на случай, когда
> тридцать дней уже прошли или требуется достать одну таблицу, а не
> разворачивать образ тома.

### Как устроено

`.github/workflows/backup.yml` раз в сутки: снимает согласованную копию базы
внутри контейнера (`make_backup.py`), скачивает её, сжимает, шифрует GPG
и отправляет в Telegram.

**Копия снимается через `sqlite3.Connection.backup()`**, а не копированием
файла: копировать `app.db` под нагрузкой нельзя — можно получить копию
посреди транзакции, которая выглядит целой, но не открывается. После снятия
прогоняется `PRAGMA integrity_check`; не прошёл — бэкап не отправляется.

Секреты в GitHub: `BACKUP_PASSPHRASE`, `TELEGRAM_BOT_TOKEN`,
`TELEGRAM_CHAT_ID`. Пароль шифрования **не хранится на Fly** — иначе он лежал
бы там же, где данные.

Размер проверяется до отправки: лимит Telegram Bot API 50 МБ на документ.
Перерастём — workflow упадёт с внятной ошибкой, а не отправит молча обрезанное.

### Восстановление: скачать и открыть

Всё делается **локально**, на боевую базу ничего не заливается.

```bash
# 1. Скачать файл из Telegram, например app-2026-07-27.db.gz.gpg

# 2. Расшифровать (пароль спросит интерактивно)
gpg -d app-2026-07-27.db.gz.gpg > app-2026-07-27.db.gz

# 3. Распаковать
gunzip app-2026-07-27.db.gz

# 4. Проверить целостность и счётчики
py -c "import sqlite3; c=sqlite3.connect('app-2026-07-27.db'); \
print(c.execute('PRAGMA integrity_check').fetchone()[0]); \
print('users:', c.execute('SELECT COUNT(*) FROM users').fetchone()[0])"
```

`gpg` уже установлен вместе с Git for Windows (`/usr/bin/gpg`), отдельно
Gpg4win ставить не нужно. Пароль — тот, что лежит в `BACKUP_PASSPHRASE`
и в менеджере паролей.

Счётчики сверяются с подписью к файлу в Telegram: она содержит число записей
по ключевым таблицам на момент снятия.

### Восстановление: залить базу обратно на Fly

> Инструкция на будущее. **Выполнять только осознанно** — заливка затирает
> боевую базу. Перед этим обязательно снять свежий бэкап текущего состояния.

```bash
# 1. Сохранить то, что есть сейчас, — на случай если восстановление ошибочно
flyctl ssh console -a energydess-tools -C "python /app/make_backup.py"
flyctl ssh sftp get /data/backup/app-СЕГОДНЯ.db ./на-всякий-случай.db -a energydess-tools

# 2. Остановить приложение, чтобы оно не писало в базу во время подмены
flyctl scale count 0 -a energydess-tools

# 3. Залить восстановленный файл
flyctl ssh sftp shell -a energydess-tools
# в открывшейся сессии:
#   put app-2026-07-27.db /data/app.db.new

# 4. Подменить и поднять приложение
flyctl ssh console -a energydess-tools -C "sh -c 'mv /data/app.db /data/app.db.old && mv /data/app.db.new /data/app.db'"
flyctl scale count 1 -a energydess-tools

# 5. Убедиться, что поднялось, и только потом убирать старую
flyctl ssh console -a energydess-tools -C "python /app/check_analysis.py"
flyctl ssh console -a energydess-tools -C "rm /data/app.db.old"
```

Шаг 2 обязателен: подменять файл базы под работающим приложением нельзя —
открытые соединения продолжат писать в старый inode, и часть данных уйдёт
в никуда.

### Запуск вручную

```bash
gh workflow run backup.yml
gh run watch
```

## 10. Восстановление файлов из снапшота тома

> Вторая линия, отдельная от выгрузки в Telegram. Туда уезжает **только
> база**, а файлы на томе — аватары и вложения переписки — в архив
> не попадают. Их единственная защита это снапшоты Fly.
>
> **Retention поднят до 30 дней** (2026-07-31, было 5). Снапшоты
> инкрементальные, у Fly первые 10 ГБ бесплатны, а все наши пять снимков
> занимают 144 МиБ — то есть 30 дней ничего не стоят. Потолок Fly — 60.

### МЕНЯЕТЕ RETENTION — ПРАВЬТЕ ПОЛИТИКУ

Срок хранения снимков лежит в двух источниках сразу: в настройке Fly
и в тексте, который читает пользователь. Поменять один и забыть про
второй — значит молча превратить политику конфиденциальности в неправду,
без единого сигнала о том, что что-то разъехалось.

Проверить командой:

```bash
flyctl volumes list -a energydess-tools --json | grep snapshot_retention
```

Места, где та же цифра записана словами, — все три править вместе
с настройкой:

| Файл | Где именно | Что там |
|---|---|---|
| `main.py` | `STATIC_PAGES["privacy"]`, таблица «Сколько мы храним данные», строка «Снимки состояния сервера у хостинга» | срок в таблице |
| `main.py` | `STATIC_PAGES["privacy"]`, блок `.doc-callout` про данные о здоровье, абзац про хранение фото | срок в тексте абзаца |
| `CLAUDE.md` | §9, врезка в начале раздела | срок для разработчика |

Проверка после правки:

```bash
grep -n "дней" main.py | grep -i "снимк\|хостинг"
```

### Главное: базу откатывать не нужно

Снапшот разворачивается **в отдельный том и монтируется в отдельную
машину**, параллельно работающему приложению. Боевой том при этом
не затрагивается вообще. То есть достать один файл недельной давности
можно, не трогая ни базу, ни чужие данные.

Проверено 2026-07-31 живым восстановлением: файл достали, sha256 совпал
с боевым побайтово, картинка открылась.

### Процедура

```bash
# 1. Выбрать снапшот — колонка CREATED AT показывает возраст
flyctl volumes snapshots list vol_4ql97qxo2lyodj8r

# 2. Создать из него отдельный том (боевой не трогается)
flyctl volumes create restore_test --snapshot-id vs_ВЫБРАННЫЙ \
  --region fra --size 1 -a energydess-tools --yes

# 3. Узнать id нового тома и текущий образ приложения
flyctl volumes list -a energydess-tools
flyctl image show -a energydess-tools

# 4. Поднять временную машину с этим томом. Образ берём свой же —
#    в нём есть python, которым удобно проверять базу
flyctl machine run registry.fly.io/energydess-tools:ТЕГ_ОБРАЗА \
  --volume vol_НОВЫЙ:/mnt/restore \
  --region fra -a energydess-tools --name restore-check \
  --vm-memory 256 --restart no \
  sleep 900

# 5. Посмотреть, что внутри
flyctl ssh console -a energydess-tools --machine ID_МАШИНЫ \
  -C "sh -c 'ls -la /mnt/restore /mnt/restore/avatars'"

# 6. Забрать файл к себе. MSYS_NO_PATHCONV=1 обязателен в Git Bash:
#    без него /mnt/... превращается в C:/Program Files/Git/mnt/...
MSYS_NO_PATHCONV=1 flyctl ssh sftp get /mnt/restore/avatars/1.png ./restored.png \
  -a energydess-tools

# 7. УБРАТЬ ЗА СОБОЙ — иначе машина и том капают в счёт
flyctl machine stop ID_МАШИНЫ -a energydess-tools
flyctl machine destroy ID_МАШИНЫ -a energydess-tools --force
flyctl volumes destroy vol_НОВЫЙ --yes
```

Проверить, что убрано:

```bash
flyctl volumes list -a energydess-tools    # должен остаться один том data
flyctl machine list -a energydess-tools    # одна машина приложения
```

### Что можно посмотреть в базе из снапшота, не разворачивая её

База на восстановленном томе открывается только на чтение — этого хватает,
чтобы сверить состояние на дату или вытащить одну запись:

```bash
flyctl ssh console -a energydess-tools --machine ID_МАШИНЫ -C "python -c \"
import sqlite3
c=sqlite3.connect('file:/mnt/restore/app.db?mode=ro', uri=True)
print(c.execute('PRAGMA integrity_check').fetchone()[0])
print('users:', c.execute('SELECT COUNT(*) FROM users').fetchone()[0])
\""
```

с полем `формат`. `--restore` на seed отвечает «ОСТАНОВЛЕНО» и объясняет
разницу. Раньше seed назывался `exercises_data.json` — переименован ровно
затем, чтобы имя говорило о роли.

`backups/` исключён из образа: восстановление идёт с локальной машины,
а лишняя копия рядом с seed — та самая путаница.

### Снять снимок

```bash
flyctl ssh console -a energydess-tools -C "sh -c 'cd /app && python dump_exercises.py --dump'"
MSYS_NO_PATHCONV=1 flyctl ssh sftp get /app/backups/exercises/exercises-ГГГГ-ММ-ДД.json \
  ./backups/exercises/exercises-ГГГГ-ММ-ДД.json -a energydess-tools
flyctl ssh console -a energydess-tools -C "rm -rf /app/backups"
git add backups/exercises/ && git commit -m "backup: снимок справочника" && git push
```

`MSYS_NO_PATHCONV=1` обязателен в Git Bash: без него `/app/...` превращается
в `C:/Program Files/Git/app/...`.

### Восстановить

Сначала всегда `--dry-run` — он показывает, что изменится, и ничего не пишет:

```bash
py dump_exercises.py --restore backups/exercises/exercises-ГГГГ-ММ-ДД.json --dry-run
py dump_exercises.py --restore backups/exercises/exercises-ГГГГ-ММ-ДД.json
```

Импорт только добавляет и обновляет; записи, которых нет в файле, из базы
не удаляются. Всё одной транзакцией: полусобранный справочник хуже старого.

На проде — с `DB_PATH=/data/app.db` через `flyctl ssh console`, но сначала
убедиться, что снимок свежий, иначе откатятся результаты последней модерации.

### Когда снимать

После пополнения видео или ручной модерации в админке (на сегодня
модерации не было ни одной: `approved` и `wrong` пусты). Ежедневно
не нужно: справочник
меняется редко, снимок весит ~4 МБ и остаётся в истории git навсегда.

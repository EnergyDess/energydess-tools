## 0. Философия и принципы

**Позиционирование:** премиальный SaaS-инструментарий 2026. Референсы направления — Linear, Vercel, Raycast, Штруцель. Ощущение — сдержанная уверенность, «инструмент профессионала», а не «домашний проект с эффектами».

**Пять принципов, из которых выводится всё остальное:**

1. **Тёмный — не значит чёрный.** Плоский `#000` читается как «мы не подумали». Наш фон — двухслойный нейтральный с ощутимой (но не крикливой) разницей между уровнями. Глубина возникает из этой лесенки, а не из градиентов.
2. **Типографика — герой сцены.** Крупные, жирные, чистые заголовки. Никаких градиентных заливок букв, никаких decorative-шрифтов с «характером». Читаемость важнее выразительности.
3. **Цветовая дисциплина.** База — нейтральная. Акцент — один на инструмент, применяется в 3-7% пикселей интерфейса. Всё, что цветное без причины — визуальный шум.
4. **Движение — микро, не макро.** Никаких плавающих блобов, интерактивных частиц, аврор-эффектов. Только тонкие ambient-эффекты на лендинге и осмысленные микроинтеракции (ховеры, появление секций).
5. **Сдержанность.** Декоративных эффектов нет. Здесь стоял пункт «один
   signature-элемент — бегущая обводка secondary-CTA»; обводка удалена
   2026-08-11 (см. §3), и точка, в которую тратилась «дерзость», теперь
   не занята ничем. Заводить новую — отдельное решение, а не свободное место.

**Что мы НЕ делаем (список запретов):**

- ❌ Aurora blobs, плавающие блобы, интерактивные частицы за мышкой
- ❌ Градиентные заливки заголовков (`background-clip: text` с цветным градиентом)
- ❌ Градиентные кнопки (`linear-gradient` как fill CTA)
- ❌ Эмодзи как иконки UI-элементов (💪 🥗 🎮 📝 в шапках карточек, метках, категориях)
- ❌ Разноцветные метки категорий (розовый КАРЬЕРА + жёлтый ФИТНЕС + голубой ПИТАНИЕ)
- ❌ Decorative-шрифты с характером (Syne, Playfair, Fraunces) для UI
- ❌ Микроскопический вторичный текст, невидимая навигация, «исчезающая» шапка при скролле
- ❌ Радужные подсветки, неоновые свечения (кроме одного тонкого glow на H1)
- ❌ Переключатель светлой/тёмной темы (до отдельного решения)

## 1. Токены — базовые

### 1.1. Поверхности (лесенка)

```css
:root {
  /* Фоновая лесенка — шаги ощутимы глазом */
  --surface-0: #0A0B0D;   /* фон страницы (база) */
  --surface-1: #141520;   /* карточки, панели */
  --surface-2: #1E2030;   /* вложенные блоки: инпуты, textarea, под-карточки */
  --surface-3: #2A2C45;   /* активные/выделенные вложенные элементы */

  /* Углубление — единственный уровень НИЖЕ карточки */
  --surface-sunken: #0e0f16;  /* дорожки прогресса, утопленные области */

  /* Границы — обязательны на карточках */
  --border:        rgba(255,255,255,0.08);   /* стандартная граница */
  --border-strong: rgba(255,255,255,0.14);   /* hover, акцентные блоки */
  --border-hairline: rgba(255,255,255,0.06); /* разделители секций */
}
```

**Железные правила:**
- Любая `.card` — фон `--surface-1` + `border: 1px solid var(--border)`.
- Инпут/textarea/под-блок внутри карточки — фон `--surface-2`.
- Активный/выделенный элемент — `--surface-3` или акцентная рамка.
- Никогда два соседних по вложенности элемента в один и тот же `--surface-*`.

**Про `--surface-sunken` — две оси, а не одна лесенка.**

Ряд `--surface-0..3` описывает **всплытие вверх**: чем выше уровень, тем
«ближе к пользователю» элемент. Но в тёмном UI есть и обратное движение —
**углубление**: элемент выглядит утопленным в поверхность, на которой лежит.
Классический случай — дорожка прогресс-бара: она не «поверх» карточки, она
вырезана в ней.

Для этого и введён `--surface-sunken` — он намеренно **не входит в числовой
ряд**, потому что означает другое направление, а не ещё один уровень вверх.

| | Направление | Токены |
|---|---|---|
| Всплытие | элемент поверх основы | `--surface-1` → `--surface-2` → `--surface-3` |
| Углубление | элемент утоплен в основу | `--surface-sunken` |

Применять `--surface-sunken`:
- дорожки прогресса — линейные полосы и `stroke` круговых индикаторов;
- утопленные пассивные области внутри карточки.

**НЕ применять к интерактивным контролам.** Дорожка тумблера
(`.toggle-track`) остаётся на `--surface-3`: это не пассивный контейнер,
а орган управления, и его дорожка должна быть заметна сама по себе как
affordance. На углублении выключенный тумблер стал бы полуневидимым.

Заполненная часть прогресс-бара красится акцентом (`--tool-accent` или
семантическим цветом) — основную работу по читаемости делает контраст
«заполнение ↔ дорожка», а не «дорожка ↔ карточка». Если дорожка всё же
читается вяло, добирать нужно тонкой внутренней границей (1px `--border`),
а не затемнением: `--surface-sunken` подходит близко к `--surface-0`, и
дальнейшее затемнение превратит углубление в «прореху» насквозь.

### 1.2. Текст

```css
:root {
  --font:      'Manrope', -apple-system, BlinkMacSystemFont, sans-serif;
  --font-mono: 'JetBrains Mono', 'DM Mono', monospace;

  --text:       #E8ECF8;   /* основной */
  --text-2:     #AEB8D4;   /* вторичный — ЕДИНЫЙ токен */
  --text-faint: #7A83A0;   /* приглушённый, используется редко */
  --text-strong: #FFFFFF;  /* максимальный контраст, для H1 hero */
}
```

**Правила:**
- Один шрифт для всего UI — **Manrope**. `Syne` удаляется.
- `JetBrains Mono` — для меток, кода, чисел (обзоры данных).
- Вторичный текст — только `--text-2`. Хардкод-серые (`#c7d3ea`, `#81899b`, `#5a6888`) удалить из всех шаблонов.
- Минимальный `font-weight` — **400**. Веса 300 и тоньше запрещены.
- Заголовки — **600-800**.

### 1.3. Типографическая шкала

```css
:root {
  /* Все размеры в rem/clamp, никаких px для текста */
  --text-display: clamp(2.5rem, 5vw, 4.5rem);   /* H1 hero (40→72px), weight 800 */
  --text-h1:      clamp(1.75rem, 4vw, 3rem);    /* H1 обычный (28→48px), weight 700 */
  --text-h2:      clamp(1.375rem, 3vw, 2rem);   /* H2 (22→32px), weight 700 */
  --text-h3:      clamp(1.125rem, 2vw, 1.5rem); /* H3 (18→24px), weight 600 */
  --text-body-lg: 1.0625rem;                    /* 17px — крупный body, weight 400 */
  --text-body:    1rem;                         /* 16px — стандартный body, weight 400 */
  --text-body-sm: 0.9375rem;                    /* 15px — вторичный body, weight 400 */
  --text-nav:     0.9375rem;                    /* 15px — навигация, weight 500 */
  --text-caption: 0.8125rem;                    /* 13px — метки, weight 500 */
  --text-mono:    0.75rem;                      /* 12px — uppercase mono-labels, weight 500, tracking +0.1em */
}
```

**Правила:**
- Hero-заголовок H1 (главная страница) получает `--text-strong` (белый) + тонкий glow: `text-shadow: 0 0 40px rgba(255,255,255,0.15);`
- Никаких градиентных заливок текста (`background-clip: text` с color-gradient).
- Uppercase mono-labels (типа `PERSONAL AI TOOLS`) — `--font-mono`, tracking `+0.1em`, `--text-2` или акцент.
- Line-height: заголовки — `1.1`, body — `1.6`, caption — `1.4`.

### 1.4. Акценты (per-tool identity)

```css
:root {
  /* Универсальный акцент — используется на лендинге и в общих CTA */
  --accent-brand: #4F8FFF;      /* electric blue, primary CTA */
  --accent-brand-hover: #146AFF; /* ТЕМНЕЕ базового, см. правило ниже */
  --accent-brand-dim: rgba(79,143,255,0.15); /* фон акцентных чипов */

  /* Инструменты — каждый со своим акцентом. Три значения у каждого:
     цвет, приглушённый фон, наведение. Подробности ниже. */
  --accent-hh:         #4F8FFF;  /* HH-ассистент: electric blue */
  --accent-hh-dim:     rgba(79,143,255,0.15);
  --accent-hh-hover:   #146AFF;
  --accent-nutrition:  #10B981;  /* Дневник питания: emerald */
  --accent-nutrition-dim: rgba(16,185,129,0.15);
  --accent-nutrition-hover: #12D595;
  --accent-workout:    #F59E0B;  /* Программа тренировок: amber */
  --accent-workout-dim: rgba(245,158,11,0.15);
  --accent-workout-hover: #F6AA28;
  --accent-enshrouded: #D97706;  /* Enshrouded: copper */
  --accent-enshrouded-dim: rgba(217,119,6,0.15);
  --accent-enshrouded-hover: #A25904;

  /* Семантические */
  --success: #10B981;
  --warning: #F59E0B;
  --error:   #EF4444;
}
```

**Правило акцентного контроля:** акцент применяется ТОЛЬКО в этих местах:
1. Primary CTA-кнопка внутри инструмента
2. Иконка инструмента в шапке карточки/страницы
3. Активная вкладка в под-навигации
4. Progress-indicators, графики, круг калорий
5. Focus-ring на активном инпуте

Всё остальное — нейтральная база.

#### ГЛАВНАЯ КНОПКА — АКЦЕНТА РАЗДЕЛА, А НЕ БРЕНДА

Пункт 1 списка выше говорит «внутри инструмента», и это ответ на вопрос
«брендовая везде или своя в каждом разделе»: **своя**. Вопрос был решён
в этом документе давно, а код его не выполнял — `.btn-primary` читала
`--accent-brand` жёстко, до 2026-08-09.

Цена расхождения видна на любой странице инструмента: поля, чипы, вкладки,
focus-ring и плитка иконки читали `var(--tool-accent, …)`, а кнопка нет.
На превью дневника это доходило до карикатуры — зелёная иконка, зелёная
метка «ПИТАНИЕ», зелёная ссылка внизу и **синяя** кнопка «Войти» посередине.
Единственное синее пятно на экране приходилось ровно на тот элемент, который
по списку обязан быть акцентным.

Замер до правки (1280×800, живое дерево, вычисленные значения):

| Страница | что давала `.btn-primary` | что раздел рисовал сам |
|---|---|---|
| `/hh` | `#4F8FFF`, белый, 3.13 | она же — совпадало |
| `/nutrition` | `#4F8FFF`, белый — синяя на зелёной странице | `.save-btn` `#10B981` + `--surface-0`, 7.76 |
| `/workout` | `#4F8FFF`, белый — синяя на янтарной | `.wk-btn-primary` `#F59E0B` + `--surface-0`, 9.17 |
| `/enshrouded` | `#4F8FFF`, белый — синяя на медной | заливки нет, кнопка контурная |

Третья колонка — главный довод, и он не теоретический. Два раздела из
четырёх уже решили этот вопрос сами, **независимо друг от друга, и пришли
к одному ответу**: заливка акцентом, надпись `--surface-0`. Система
не изобретает здесь принцип, а догоняет практику, которая сложилась
без неё. Ровно поэтому сведение `.wk-btn-primary` к старой `.btn-primary`
было бы регрессом: страница не мусорила, она закрывала пробел.

Вне раздела `--tool-accent` не объявлен, и кнопка падает на бренд —
на лендинге, входе, в профиле и админке она синяя, как была.

#### Цвет текста на акцентной заливке

Акценты у нас разной светлоты, и «белым по акценту» одинаково хорошо
не выходит. Замеры белого и `--surface-0` на каждой заливке:

| Токен | hex | белый | `--surface-0` | текст |
|---|---|---|---|---|
| `--accent-workout` | `#F59E0B` | **2.15** | **9.17** | тёмный |
| `--accent-nutrition` | `#10B981` | **2.54** | **7.76** | тёмный |
| `--accent-brand` | `#4F8FFF` | 3.13 | 6.29 | белый |
| `--accent-enshrouded` | `#D97706` | 3.19 | 6.18 | белый |

**Граница — 3.0.** Ниже — текст `var(--surface-0)`, выше — белый.

Порог WCAG 4.5 здесь сознательно не применяется: это норматив, а не
граница читаемости. 3.13 на синем читается нормально, а 2.15 белым по
янтарю — нет, и дело уже не в цифре. Формального соответствия AA по
`--accent-brand` и `--accent-enshrouded` нет, решение отложено —
`BACKLOG.md`, задача 33.

Тёмный текст задаётся токеном `var(--surface-0)`, а не подобранным на
глаз тёмным оттенком акцента. Хардкоды вроде `#06251f` и `#06150c`
(они у нас были) тянут за собой чужой тон, проигрывают по контрасту
и не проверяются грепом.

**Отсюда следует, что цвет надписи — не константа компонента, а часть
комплекта акцента.** Он объявляется рядом с самим акцентом токеном
`--tool-accent-ink`:

| Тема | `--tool-accent` | `--tool-accent-ink` | контраст |
|---|---|---|---|
| вне раздела (бренд) | `#4F8FFF` | `var(--text-strong)` | 3.13 |
| `.theme-hh` | `#4F8FFF` | `var(--text-strong)` | 3.13 |
| `.theme-nutrition` | `#10B981` | `var(--surface-0)` | 7.76 |
| `.theme-workout` | `#F59E0B` | `var(--surface-0)` | 9.17 |
| `.theme-enshrouded` | `#D97706` | `var(--text-strong)` | 3.19 |

**АКЦЕНТ НЕ ОБЪЯВЛЯЕТСЯ В ОДИНОЧКУ.** Заливка, приглушённый фон,
наведение и надпись — комплект из четырёх, и объявляются они одним
правилом. Разделить их — это и есть исходный дефект: фон брался из акцента,
а надпись оставалась белой константой, и на янтаре выходило 2.15.

Практическое следствие: `.theme-*` (страница раздела) и `.tool-*` (карточка
инструмента, а на превью инструмента — весь `<body>`) объявлены в `style.css`
**одним правилом на пару**. Два списка в разных местах файла уже разъезжались:
второй знал про акцент, но не знал про надпись, и кнопка «Войти» на превью
дневника получила бы белый текст на зелёном.

#### Наведение уводит заливку ПРОЧЬ ОТ ЦВЕТА НАДПИСИ

**Правило одно, а направлений два, и задаёт его надпись:**

> На кнопке с белой надписью заливка при наведении **темнеет**.
> На кнопке с тёмной — **светлеет**.

Проверяемое условие тоже одно: контраст надписи при наведении обязан
**вырасти**, а не упасть. Это и есть смысл правила, а «темнеет» — лишь
его половина, та, что была видна, пока все кнопки были синими.

Замеры, покой → наведение:

| Акцент | надпись | наведение | контраст |
|---|---|---|---|
| `#4F8FFF` бренд и HH | белая | `#146AFF` темнее | 3.13 → **4.63** |
| `#D97706` enshrouded | белая | `#A25904` темнее | 3.19 → **5.29** |
| `#10B981` nutrition | тёмная | `#12D595` светлее | 7.76 → **10.29** |
| `#F59E0B` workout | тёмная | `#F6AA28` светлее | 9.17 → **10.03** |

Рецепт значения один на все четыре: тот же тон и та же насыщенность,
сдвинута только светлота. Размер шага — работа, которую шагу поручено
сделать. У белых надписей контраст в покое стоит впритык к границе 3.0,
поэтому шаг большой, **11 пунктов**, и он заодно чинит: 4.63 и 5.29 —
это уже с запасом. У тёмных надписей чинить нечего (7.76 и 9.17), шагу
остаётся быть замеченным — хватает **6 пунктов**. Те же 11 дали бы
эмеральду `#16EBA4`, неоновую мяту, прямо запрещённую настроением
раздела (§7.3).

Осветление белой надписи — интуитивный ход и неверный: старый
`--accent-brand-hover: #6BA0FF` давал белому 2.59 против 3.13 у базового
состояния, то есть кнопка теряла читаемость ровно в тот момент, когда
на неё смотрят.

Второй вариант — оставить цвет светлым, а текст на hover сделать тёмным —
отвергнут: надпись мигала бы с белой на тёмную при каждом наведении,
а состояние всё равно осталось бы светлее базового.

**Почему не `filter: brightness()`.** Соблазн очевидный: одна строка вместо
токена на каждый акцент, и раздел тренировок так и сделал. Но `filter`
красит элемент целиком — вместе с надписью, — и на кнопках с белым текстом
это отменяет собственную же цель:

| Акцент | покой | `filter: brightness(0.88)` | итог |
|---|---|---|---|
| `#4F8FFF` | 3.13 | заливка `#467EE0`, надпись `#E0E0E0` | **2.99 — упал** |
| `#D97706` | 3.19 | заливка `#BF6905`, надпись `#E0E0E0` | **3.04 — упал** |

Оба ушли ниже собственного состояния покоя, а первый — ещё и ниже границы
3.0. На тёмных надписях фильтр работает (у янтаря `brightness(1.08)` даёт
10.33) только потому, что почти чёрный текст светлеть ему почти некуда.
Правило, верное в половине случаев, хуже отсутствия правила, поэтому
наведение — токен, а не фильтр.

**Для текста это правило зеркальное.** Ссылка или кнопка-текст на тёмном
фоне при наведении, наоборот, **светлеет** — там фон тёмный, и затемнение
уронило бы контраст. `--accent-brand-hover` для текста не годится по
построению: он описывает наведение на заливку. Текст осветляют до
`--text-strong`.

### 1.5. Радиусы

```css
:root {
  --radius-sm:  8px;   /* кнопки, инпуты, чипы */
  --radius-md:  12px;  /* small cards, dropdowns */
  --radius-lg:  16px;  /* стандартные карточки */
  --radius-xl:  24px;  /* модалки, hero-блоки */
}
```

### 1.6. Тени

```css
:root {
  --shadow-sm:  0 1px 2px rgba(0,0,0,0.3);
  --shadow-md:  0 4px 12px rgba(0,0,0,0.4);
  --shadow-lg:  0 12px 32px rgba(0,0,0,0.5);
  --shadow-glow-brand: 0 0 24px rgba(79,143,255,0.25);
}
```

**Правила:**
- Карточка в покое — `--shadow-sm` или без тени.
- Карточка на hover — `--shadow-md`.
- Модалка, dropdown, всплывающие меню — `--shadow-lg`.
- Focused-элементы (только CTA hero-секции) — `--shadow-glow-brand`.

### 1.7. Отступы (шкала)

```css
:root {
  --space-1: 4px;
  --space-2: 8px;
  --space-3: 12px;
  --space-4: 16px;
  --space-5: 24px;
  --space-6: 32px;
  --space-7: 48px;
  --space-8: 72px;
  --space-9: 96px;
  --space-10: 128px;
}
```

> **ИМЯ — ПОРЯДКОВЫЙ НОМЕР, А НЕ МНОЖИТЕЛЬ.**
>
> Первые четыре шага выглядят как умножение на 4: `-1` → 4, `-2` → 8,
> `-3` → 12, `-4` → 16. Дальше правило ломается: `-5` даёт **24**, а не 20,
> `-8` даёт **72**, а не 32.
>
> Ловушка в том, что расхождение молчит. Написав `--space-5` в расчёте
> на 20px, получишь 24px — без ошибки, без предупреждения, просто вёрстка
> на четыре пикселя не та, что задумана.
>
> | Токен | Значение | Что могли ожидать по «×4» |
> |---|---:|---:|
> | `--space-1` | 4px | 4 ✓ |
> | `--space-2` | 8px | 8 ✓ |
> | `--space-3` | 12px | 12 ✓ |
> | `--space-4` | 16px | 16 ✓ |
> | `--space-5` | **24px** | ~~20~~ |
> | `--space-6` | **32px** | ~~24~~ |
> | `--space-7` | **48px** | ~~28~~ |
> | `--space-8` | **72px** | ~~32~~ |
> | `--space-9` | **96px** | ~~36~~ |
> | `--space-10` | **128px** | ~~40~~ |
>
> Шкала не арифметическая, а типографическая: шаг растёт вместе с размером,
> потому что на крупных отступах разница в 4px незаметна, а на мелких
> заметна. Смотреть в таблицу, а не считать в уме.

**Правила:**
- Отступ между секциями страницы (desktop) — `--space-9` (96px) или `--space-10` (128px).
- Отступ между секциями (mobile) — `--space-7` (48px).
- Внутри карточки padding — `--space-5` (24px) или `--space-6` (32px).
- Gap в grid/flex — из шкалы. Никаких `gap: 20px` в inline-стилях.

### 1.8. Motion

```css
:root {
  --ease:       cubic-bezier(0.4, 0, 0.2, 1);
  --ease-out:   cubic-bezier(0, 0, 0.2, 1);
  --dur-fast:   150ms;   /* микро — ховеры кнопок */
  --dur-base:   200ms;   /* стандарт — большинство транзиций */
  --dur-slow:   400ms;   /* появление секций при скролле */
}
```

**Правила:**
- Все `transition` — только через переменные, единый easing.
- Ховер карточки: граница → `--border-strong`, `translateY(-2px)`, тень → `--shadow-md`.
- Ховер CTA-кнопки: `scale(1.02)`, лёгкое затемнение цвета акцента.
- Появление секций при скролле: fade + `translateY(20px → 0)`, длительность `--dur-slow`.
- Respect `prefers-reduced-motion: reduce` — все анимации отключаются.

Три свойства из трёх едут комплектом акцента: заливка, надпись, наведение

не объявлен и каждый `var()` падает на брендовое значение — идиом ровно
тот же, что у полей, чипов и вкладок, нового здесь нет.

Рамка прозрачная, а не `none`: у `.btn-secondary` и `.btn-danger` она
видимая, и без этой строки primary оказывалась на 2px ниже в общем ряду.

**Secondary (outline):**
```css
.btn-secondary {
  background: transparent;
  color: var(--text);
  border: 1px solid var(--border-strong);
  padding: var(--space-3) var(--space-5);
  border-radius: var(--radius-sm);

  transition: border-color var(--dur-fast) var(--ease), background var(--dur-fast) var(--ease);
```

Наведение тоже в акценте раздела — иначе на янтарной странице получалось бы
две главные кнопки разного цвета: primary янтарная, а стоящая рядом
secondary синеет под курсором. Пары стоят рядом реально, а не гипотетически:
`tool_preview.html` ставит «Войти» и «Создать аккаунт» в один ряд. Заливки
у secondary нет, поэтому `--tool-accent-ink` ей не нужен.

**Ghost/text:**
```css
.btn-ghost {

  color: var(--text-2);
  border: none;
  padding: var(--space-2) var(--space-3);
  cursor: pointer;
}
.btn-ghost:hover {
  color: var(--text);
}
```

**Третичная ссылка-кнопка `.btn-signature` (см. раздел 3).** Бегущей обводки у неё больше нет — удалена 2026-08-11.

**Два модификатора: размер и свечение.** Заведены 2026-08-06 при закрытии
задачи 37 — до этого оба свойства лежали в `landing.css` правилами
`.hero .btn-primary` и `.cta .btn-primary`, то есть страница переопределяла
компонент.

```css
.btn-lg   { padding: var(--space-4) var(--space-7); font-size: var(--text-body-lg); }
.btn-glow { box-shadow: var(--shadow-glow-brand); }
```

Разделены намеренно, а не собраны в один «промо-вариант»: на лендинге
они нужны в разных сочетаниях. Кнопке в hero положено свечение,
но **не** увеличенный размер — рядом стоит `.btn-signature` высотой 40px,
и выросшая кнопка сломала бы ряд. Финальному CTA нужно и то и другое.
Один класс на оба свойства заставил бы hero снова писать своё правило.

**Третий модификатор — ширина.**

```css
.btn-block { width: 100%; }
```

Ширину кнопки задаёт **место**, куда её поставили: форма входа растягивает
на всю колонку, панель действий нет. Поэтому модификатор, а не свойство
компонента. Заведён 2026-08-09 при сведении `.auth-btn-primary` —
из трёх отличий той копии от системной кнопки законным было ровно это
(`BACKLOG.md`, задача 42).

**Иконочная кнопка** — кнопка, у которой всё содержимое один значок:
показать пароль, закрыть, свернуть.

```css
.btn-icon { width: 40px; height: 40px; background: none; border: none; color: var(--text-faint); }
.btn-icon:hover { color: var(--text-2); }
.btn-icon svg { width: 18px; height: 18px; stroke-width: 1.5; }
.btn-icon-solid { background: var(--surface-sunken); color: var(--text-2); }
.btn-icon-round { border-radius: 50%; }
```

Квадрат 40×40 — та же минимальная высота, что у `.btn-primary`, поэтому
ряд с обычными кнопками не съезжает. Где нужен полный тач-таргет 44px,
размер задаёт место установки: у кнопки-глаза он приходит от высоты поля.

Фона и рамки в базовом виде нет — значок стоит внутри чужой поверхности
(поля, шапки окна), и своя подложка спорила бы с ней. Кнопка стоит сама
по себе — `.btn-icon-solid`. Крестик закрытия — плюс `.btn-icon-round`:
круг читается как «убрать», квадрат в шапке окна спорит с прямоугольником
самого окна.

**Значок внутри кнопки не сжимается.** Заведено 2026-08-11.

```css
:is(.btn-primary, .btn-secondary, .btn-ghost, .btn-danger) > :is(svg, i, .spinner) {
  flex-shrink: 0;
}
```

Все кнопки базы — `inline-flex`. У элемента флекса минимальная ширина
по умолчанию берётся из содержимого только у текста; у `<svg>` она равна
нулю, поэтому при нехватке места браузер сжимает **именно значок**,
а не подпись.

Это и было «интерфейс дёргается при нажатии кнопок». Покадровый замер
на живой странице: нажатие «Копировать» меняло подпись на «Скопировано»
(+13px), кнопка держала свою ширину (`flex: 1` в ряду действий), и лишнее
забиралось у значка — **22px → 10px** на 1280 и **1px → 0** на 390,
то есть значок исчезал совсем. У соседней «Редактировать» то же самое
в обратную сторону: 0 → 24px при переключении подписи на «Готово».

Правило системное, а не страничное: свойство принадлежит кнопке базы,
и та же форма отказа ждала любую кнопку со значком в тесном ряду.

**Подпись кнопки при этом менять всё равно не стоит.** Правило спасает
значок, но ряд всё равно перекомпонуется. Подтверждение действия —
тост (`position: fixed`, не двигает ничего), а не текст на самой кнопке.
Замер после правки: нажатие «Копировать» меняет **два** элемента, и оба —
появление тоста; высота документа не меняется вовсе. Исключение —
подпись, которая сообщает **новое состояние** («Редактировать» → «Готово»,
«Завершить» → «Завершена»): она обязана меняться, это и есть её работа.

### 2.3. Inputs

```css
.input, .textarea, .select {
  background: var(--surface-2);
  border: 1px solid var(--border);
  border-radius: var(--radius-sm);
  padding: var(--space-3) var(--space-4);
  color: var(--text);
  font-family: var(--font);
  font-size: var(--text-body);
  transition: border-color var(--dur-fast) var(--ease), box-shadow var(--dur-fast) var(--ease);
}
.input:focus, .textarea:focus, .select:focus {
  outline: none;
  border-color: var(--accent-brand);
  box-shadow: 0 0 0 3px var(--accent-brand-dim);
}
.input::placeholder {
  color: var(--text-faint);
}
```

Внутри инструмента — заменить `--accent-brand` на акцент инструмента.

**Два варианта поля.** Оба заведены 2026-08-06 (задача 37): раньше это были
правила `.url-row .input` и `.dosie-item .input` в `hh.css`.

```css
.input-compact { height: 44px; padding-top: 0; padding-bottom: 0; }
.input-nested, .textarea-nested { background: var(--surface-1); }
```

`.input-compact` — поле в одну строку с кнопкой. Своей высоты у `.input` нет,
её задаёт содержимое: 12+12 паддинга плюс строка 1.6×16 даёт около 52px
против 40px у кнопки рядом, и ряд выглядит съехавшим. 44px — минимальный
тач-таргет из глобального `CLAUDE.md`. Вертикальные паддинги снимаются,
иначе спорят с `height`.

`.input-nested` — поле лежит не на карточке, а на вложенном блоке
(`--surface-2`): под-карточка досье, вложенная панель. Базовый фон поля
тоже `--surface-2`, и они сливаются, что запрещает лесенка (раздел 1.1).
Уходим на ступень **вниз**, а не вверх: `--surface-3` занят активным
состоянием, и поле в покое читалось бы как выделенное.

**Третий вариант — плотное.** Заведён 2026-08-09 (задача 42).

```css
.input-sm { padding: var(--space-2) var(--space-3); font-size: var(--text-caption); }
```

Поле в ячейке таблицы, где строк сотня и каждая лишняя пара пикселей
множится на сотню. До этого варианта таблица продуктов в админке держала
свою копию `.food-input`, и комментарий над ней прямо говорил: «`.input`
из базы, уменьшенный под ячейку». Копию делали осознанно — просто варианта
не существовало.

**Четвёртый вариант — компактное многострочное.** Заведён 2026-08-10
(задача 45), на месте `.dosie-item .textarea.sm` из `hh.css`.

```css
.textarea-compact { min-height: 0; }
```

Поле в под-карточке списка, где запись — две строки, а не абзац:
описание места работы, достижения, описание проекта. Системный минимум
96px растит каждую под-карточку, а их в досье до десятка.

**Числа в правиле нет намеренно, и это находка, а не стиль.** Прежнее
правило страницы объявляло `min-height: 58px`, и замер показал, что
эти 58px **не применялись ни разу**: собственная высота `<textarea>`
при `rows=2` равна 77.2px — 2×25.6 строки, 12+12 паддинга, 2 рамки, —
то есть больше минимума, и минимум не связывает. Любое значение
от 0 до 77 дало бы ровно ту же картинку. Единственное, что правило
делало на самом деле, — снимало системные 96px, что теперь и записано.

`rows="2"` проставлен в разметке явно: высоту задаёт он, а умолчание,
от которого зависит вид, обязано быть видно в коде.

**Почему `-compact`, а не `-sm`.** В этой системе суффиксы уже означают
разное, и путать их дороже, чем помнить:

| Суффикс | Что меняет | Примеры |
|---|---|---|
| `-sm` | плотность: паддинг и кегль | `.input-sm` |
| `-compact` | высоту поля, которая не подошла месту | `.input-compact` (44px в ряд с кнопкой), `.textarea-compact` |
| `-nested` | фон под лесенку поверхностей | `.input-nested`, `.textarea-nested` |

`BACKLOG.md` предлагал имя `.textarea-sm` — от него отказались именно
поэтому: правило не трогает ни паддинг, ни кегль, и один суффикс стал бы
значить две разные вещи в двух соседних строках файла.

**Второй потребитель нашёлся назавтра, и это подтвердило вариант.**
2026-08-11 разбор правил по id (задача 47) наткнулся на
`#custom-context { min-height: 60px }` в `hh.css` — «разовая настройка»
на вкладке письма. Замер: 60px **не связывали**, своя высота поля при
`rows=2` равна 74px. То есть правило снимало системные 96px и больше
ничего — ровно роль `.textarea-compact`. Правило удалено, поле получило
вариант и явный `rows`.

Отсюда общее наблюдение, которое стоит помнить при любом поле:
**у `<textarea>` есть собственная высота от `rows`, и `min-height` ниже
неё не значит ничего.** Оба раза за два дня число выглядело осмысленным
(58px, 60px) и не применялось ни разу.

**Пятый вариант — растущее под текст.** Заведён 2026-08-11.

```css
.textarea-grow { overflow-y: hidden; resize: vertical; }
```

Высоту поля задаёт содержимое, а не `rows`. Саму высоту проставляет
скрипт (`autosizeTextarea` в `hh.html`) — в CSS её записать нечем;
здесь объявлено то, что от неё зависит.

**Зачем, замером.** `rows="2"` с длинным текстом — это окошко на две
строки с собственной прокруткой внутри прокручиваемой страницы. Замер
на 390px: поле «что делал» в досье показывало **75px при содержимом
613** — восемь строк из шестидесяти пяти. Пальцем такое окно листается
плохо: жест уводит страницу, а не текст. На десктопе то же поле прятало
103px из 178, и там это выглядело мелочью — мышь колесом попадает
в окно точно.

**`resize` здесь был `none` первые сутки, и это пришлось пересмотреть.**
Довод был верный для той версии скрипта: `autosizeTextarea` пересчитывал
высоту на каждый введённый символ и затирал заданную мышью — ручка
обещала то, чего не делает. С 2026-08-11 (задача 57) высота считается
как `max(содержимое, ручная)`: заданное мышью работает **минимумом**
и ввод его не сбрасывает. Замер: поле 180px растянуто до 300px, после
набора текста — по-прежнему 300px.

Ручное растягивание ловится `ResizeObserver`, а не событием: события
«потянули за угол» у `<textarea>` в DOM нет вообще. Своя же правка
отличается от чужой меткой `dataset.своя`, которую скрипт ставит перед
тем, как назначить высоту, — без неё наблюдатель принял бы пересчёт
за движение мыши и защёлкнул бы высоту навсегда.

Чего вариант по-прежнему **не** позволяет: сделать поле КОРОЧЕ
содержимого. Оно вернётся к тексту, и это не недоделка — совмещать
«растёт под текст» с «прячет текст» было бы противоречием.

`overflow-y: hidden` обязателен: при высоте, посчитанной под содержимое,
собственная полоса поля не нужна, но браузер успевает нарисовать её
на кадр между вводом символа и пересчётом. `resize` снят по той же
причине: ручную высоту скрипт затрёт при следующем вводе, и ручка
обещала бы то, чего не делает.

Две ловушки, на которых пришлось споткнуться, — обе стоят замера:

| Ловушка | Симптом | Как правильно |
|---|---|---|
| `height = scrollHeight` при `box-sizing: border-box` | поле на 2px короче текста, последняя строка срезана пополам | прибавить рамку: `scrollHeight + borderTop + borderBottom` |
| пересчёт на скрытой вкладке | `scrollHeight` равен нулю, поле схлопывается в ноль | считать при показе вкладки, а не только при наполнении |

Потребители: описание и достижения места работы, описание проекта
(досье), «разовая настройка» на вкладке письма.

**Две вещи, без которых компонент неполон** — свойства поля, а не страницы:

```css
.input[type="number"] { -moz-appearance: textfield; }
.input[type="number"]::-webkit-outer-spin-button,
.input[type="number"]::-webkit-inner-spin-button { -webkit-appearance: none; margin: 0; }
.select option { background: var(--surface-2); color: var(--text); }
```

Нативные спиннеры наезжают на само число и обрезают его в узкой колонке;
выпадающий список `<select>` рисует ОС, и без явного фона пункты приезжают
белыми на белом в тёмной теме Windows. Оба правила жили копиями
на страницах — `.food-input[type="number"]` в админке
и `.wk-profile-input option` в профиле тренировок.

#### `class="input"` НА `<input type="text">` ДО 2026-08-09 НЕ РАБОТАЛ

Не «работал хуже» — **не применялся вовсе**, и знать об этом обязан
каждый, кто читает старый код или старый замер.

В `style.css` есть блок «Старые инпуты по тегам» для всего, что ещё
не переведено на компонент. Селектор там `input[type="text"]` — это
специфичность (0,1,1), а у `.input` (0,1,0). **Правило на теге выигрывало
у компонента.** Поле с правильным классом рисовалось объявлениями legacy,
вариант `.input-sm` не применялся никогда, и понять это по коду нельзя:
разметка верная, класс на месте, консоль чистая. Только замер вычисленного
значения в браузере.

Замер на живом дереве, 1280×800, `/workout/profile`:

| | было | стало |
|---|---|---|
| `font-size` | 15px (`--text-body-sm` из legacy) | 16px (`--text-body`, компонент) |
| `padding` | 13px 16px (число из legacy) | 12px 16px (`--space-3` / `--space-4`) |

Нашлось не чтением, а сведением `.wk-profile-input` к `.input`
(`BACKLOG.md`, задача 42): страница и компонент рисовали одинаково
не потому, что совпали, а потому что **оба проигрывали третьему**.
Пиксельная сверка до/после показала ноль, и это был не успех, а симптом.

Починено исключением на самом legacy-правиле:

```css
textarea:where(:not(.textarea)), input[type="text"]:where(:not(.input)),
input[type="email"]:where(:not(.input)), input[type="password"]:where(:not(.input)) { … }
```

**`:where(:not(…))`, а не `:not(…)`** — разница не стилистическая.
`:not()` считается в специфичность, и правило выросло бы до (0,2,1).
Страницы, которые компенсировали старую специфичность селектором потомка,
тут же проиграли бы: `.search-wrap .search-input-admin` — это (0,2,0),
и поиск в админке лишился бы левого паддинга под иконку. Замерено смоуком
на первой попытке: значок наехал на плейсхолдер, поле выросло с 34px
до 46px. `:where()` даёт нулевой вклад — правило остаётся ровно (0,1,1),
меняется только то, на что оно **не** распространяется.

**Подпись поля — `.field-label`, класс, а не тег.**

```css
.field-label {
  display: block;
  font-family: var(--font-mono);
  font-size: var(--text-caption);
  font-weight: 500;
  color: var(--text-2);
  margin-bottom: 8px;
  letter-spacing: 0.07em;
  text-transform: uppercase;
}
```

Ставится на элемент, который **является микрозаголовком над полем**:
«EMAIL», «ПАРОЛЬ», «ВОЗРАСТ». Обычно это `<label>`, но тег тут ни при чём —
класс можно повесить и на `<div>`, если подпись не привязана к контролу.
Страница вправе уточнить кегль, цвет и трекинг своим классом рядом
(`class="field-label dosie-label"`), но не гарнитуру и не регистр: по ним
подпись и узнаётся.

**Не ставится** на то, что `<label>` по смыслу, а подписью не является:
строка-переключатель с чекбоксом, кнопка выбора файла, коробка тумблера.
Там нужен обычный текст, и теперь он получается сам собой.

До 2026-08-08 то же правило висело на голом теге `label` и доставалось
всем 74 `<label>` проекта. Отказ был немой в обе стороны: автор строки
«Учитывать данные питания» капса не заказывал и в CSS его не искал —
получил моноширинный капс; а автор компонента-исключения был вынужден
гасить чужое правило пятью объявлениями подряд. Разбор всех 74 мест
и замеры — `BACKLOG.md`, задача 40.

### 2.4. Chips / labels

```css
.chip {
  display: inline-flex;
  align-items: center;
  gap: var(--space-2);
  padding: var(--space-1) var(--space-3);
  background: var(--surface-2);
  border: 1px solid var(--border);
  border-radius: 999px;
  color: var(--text-2);
  font-size: var(--text-caption);
  font-weight: 500;
}
.chip.active {
  background: var(--accent-brand-dim);
  color: var(--accent-brand);
  border-color: var(--accent-brand);
}
```

Базовый чип — **одна короткая подпись**, поэтому `white-space: nowrap`:
в узком ряду перенос сделал бы соседние чипы разновысокими.

**Вариант `.chip-wrap` — когда длину подписи задаём не мы.**

```css
.chip-wrap {
  white-space: normal;
  overflow-wrap: anywhere;
  max-width: 100%;
  align-items: flex-start;
  text-align: left;
  border-radius: var(--radius-md);
  line-height: 1.45;
}
```

Заведён 2026-08-11. Повод: карточка анализа вакансии в HH-ассистенте
наполняет чипы **ответом модели** — там не слово, а целая фраза вроде
«Опыт построения мультиагентного пайплайна генерации видео
с агентом-деконструктором, аналитиком и критиком». Замер до правки:
чип шириной **767px внутри карточки в 531** на 1280 и внутри **293**
на 390 — то есть он уезжал за край экрана и обрезался вместе с ним,
потому что `body` объявлен `overflow-x: clip` и прокрутить туда нельзя.

Радиус у варианта `--radius-md`, а не 999px: пилюля в три строки читается
как ошибка вёрстки. Всё остальное — фон, рамка, кегль, паддинги —
от базового, поэтому родство видно с одного взгляда.

**Правило выбора:** подпись пишем мы (фильтр, тег, состояние) — базовый
чип. Подпись приходит извне (модель, пользователь, чужой API) — `.chip-wrap`.
Ставить базовый на неизвестную длину нельзя: отказ будет молчаливым,
текст просто уедет за границу экрана.

```css
.eyebrow {

  font-size: var(--text-mono);
  font-weight: 500;

  text-transform: uppercase;
  color: var(--text-2);
```

### 2.5. Modals

Компонент из трёх частей, и все три обязательны:

| Часть | Где | Что делает |
|---|---|---|
| каркас | `templates/_modal.html` | макрос `modal()` — оверлей, лист, шапка, кнопка закрытия |
| оформление | `static/style.css`, блок `.modal-ov` | шторка снизу до 640px, окно по центру с 640px, варианты |
| поведение | `static/modal.js` | Escape, клик вне окна, кнопка, фокус, `inert`, блокировка фона, смахивание шторки |

Страница подключает `modal.js` и вызывает макрос. Ни `onclick`, ни своего
обработчика клавиш она не пишет:

```jinja
{% raw %}{% import '_modal.html' as m %}

{% call m.modal('modal-water', 'Добавить воду', icon='💧') %}
  …содержимое…
{% endcall %}{% endraw %}
```

Открыть и закрыть — `открыть_модалку('modal-water')` /
`закрыть_модалку('modal-water')`.

**Слот под значок в шапке (`icon`, `icon_tone`).** Значок передаётся отдельным
параметром, а не пишется в начало `title`. Причина не косметическая: `title`
принимает только текст, Jinja экранирует разметку, и `<i data-lucide>` туда
не вписать — значок неизбежно уезжает в тело окна. Ровно это и случилось
с предупреждением в модалке конфликтов HH: объяснение было техническим
(«макрос принимает только текст»), а результат — предупреждение без акцента
там, где акцент и нужен. **Различие по виду допустимо, когда обосновано
смыслом; здесь оно было обосновано ограничением компонента, а это повод
править компонент.**

| Параметр | Значение | Что рисуется |
|---|---|---|
| `icon='alert-triangle'` | имя иконки Lucide — ASCII из букв, цифр и дефисов | `<i data-lucide="…">`, 18×18, `stroke-width: 1.5` |
| `icon='💧'` | эмодзи | сам символ, кегль 1.05rem |
| `icon_tone=''` | по умолчанию | цвет `--text-2` |
| `icon_tone='warning'` | янтарь | `--warning`. Новый тон заводится в `style.css` рядом с `.modal-icon`, а не классом со страницы |

Lucide от эмодзи отличается по самой строке (`icon.isascii()` и
`.replace('-','').isalnum()`), поэтому отдельного параметра нет: перепутать
нечего, а вызов остаётся одинаковым до и после замены эмодзи на Lucide
(`BACKLOG.md`, задача 31).

Значок помечен `aria-hidden` и лежит **вне** элемента с `title_id`: доступное
имя диалога собирается по `aria-labelledby`, и значок в нём был бы шумом.
Для эмодзи это ещё и исправление — `'💧 Добавить воду'` программа чтения
объявляла как «капля воды Добавить воду».

**Имена кириллические намеренно, и переименовывать их обратно нельзя.**
Компонент назывался `openModal`/`closeModal` ровно до тех пор, пока
не выяснилось, что такую же пару объявляет у себя `profile.html` — с той
разницей, что его `closeModal` принимает **элемент**, а компонентный — **id**.
Подключение `modal.js` к профилю сломало бы обе его модалки молча: вызов ушёл
бы в компонентную функцию, `getElementById(элемент)` вернул бы `null`, она
вышла бы по первой проверке и не бросила бы ничего. Ни ошибки, ни следа.
Кириллица убирает не последствия ошибки, а её возможность: `openModal`
напишет любой, кто делает модалку и не заглядывал сюда, — `открыть_модалку`
не набирается случайно.

Своя уборка при закрытии (остановить камеру, сбросить флаг) вешается
на событие `modal:close`, а НЕ на отдельную кнопку: событие уходит из
единственной точки выхода, без единого `return` перед ним, поэтому приходит
от любого способа закрытия и на любой глубине стопки. Забыть один из способов
становится нельзя.

**Варианты** (класс на оверлей, параметр `variant`):

| Вариант | Что меняет | Зачем |
|---|---|---|
| — | лист снизу, шапка с «ручкой» | по умолчанию |
| `modal-ov-column` | высота листа фиксирована, тело — колонка | содержимое само себе скролл-контейнер (лента чата) |
| `modal-ov-viewer` + `chrome=false` | прозрачный лист, размытый фон, кнопка закрытия поверх содержимого | просмотр фото: рамка мешала бы картинке |

Новый вариант заводится здесь, а не подмешивается на странице
(`CLAUDE.md`, §6.0.2).

**Две раскладки одного компонента, порог 640px.** Вариантом это не является:
`variant` выбирает автор, а раскладку выбирает ширина окна.

| Ширина | Как выглядит | Как закрывается |
|---|---|---|
| до 640px | шторка снизу, скругление только сверху, «ручка» `.modal-drag` | крестик, Escape, клик по подложке, **смахивание вниз** |
| от 640px | окно по центру: `border-radius: var(--radius-lg)`, рамка, тень, отступы от краёв окна, «ручки» нет | крестик, Escape, клик по подложке |

До 2026-08-12 раскладка была одна — шторка, на любой ширине. Замер на трёх
разрешениях (1280×800, 1920×1080, 2560×1440) давал одно и то же:
`align-items: flex-end`, нижний край листа ровно на границе окна (отступ
снизу 0 на всех трёх) и «ручка» высотой 40px, за которую мышью тянуть
нечем. То есть мобильная шторка, отрисованная на десктопной ширине.

Три следствия, важные при правке этого блока:

- **«Ручка» на десктопе убрана, а не спрятана «за компанию».** Элемент,
  который заявляет жест и не выполняет его, — тот же немой отказ, только
  повёрнутый к пользователю (`CLAUDE.md`, §6.0.3).
- **Смахивание спрашивает раскладку, а не ширину.** `modal.js` перед началом
  жеста читает `align-items` оверлея и работает только при `flex-end`.
  Порог живёт в одном месте — в CSS; продублируй его числом в скрипте,
  и через полгода два числа разъедутся молча.
- **Потолок высоты считается от окна**, а не «примерно 92vh»:
  `max-height: calc(100vh - var(--space-6) * 2)`. Окно с кнопками обязано
  помещаться целиком, иначе кнопка подтверждения уезжает за край.

**Лист центрируется по рабочей области, а не по окну (с 2026-08-14).**
Оверлей по-прежнему растянут на всё окно — затемнять надо и боковую
колонку тоже, — а вот лист встаёт по центру той области, в которой
человек работает. Замер на дневнике до правки: центр листа 632 против
центра содержимого 752 при ширине 1280, расхождение **−120px**; на 1920
те же −120, на 2560 **−128**. Компонент вёл себя по спецификации,
и всё же окно выглядело уехавшим влево — потому что уехало оно
относительно того, что человек читает.

Смещение задаётся **привязкой, а не константой**: страница с боковой
колонкой объявляет `--app-aside` своей же величиной, страница без
колонки не объявляет ничего и получает `0px` из запасного значения.
Исключений в правиле нет — оно одно на все страницы.

| Что | Где |
|---|---|
| читает | `static/style.css`, `.modal-ov:not(.modal-ov-viewer)`, `padding-left: calc(var(--space-5) + var(--app-aside, 0px))` |
| объявляет | `static/nutrition.css`, `body` внутри `@media (min-width: 900px)` |
| одно число на два потребителя | `--nut-aside: 15rem` — им же задана ширина самой колонки |

Величина **в `rem`, и это не стилистика**: корневой кегль здесь
`clamp(16px, 13px + 0.15625vw, 19px)`, то есть `15rem` — это 240px
на 1280 и 255px на 2560. Константа в пикселях разошлась бы на те самые
15px, что и видно в замере «−128 вместо −120». После правки расхождение
центров **0** на всех трёх ширинах и на страницах обоих видов.

Токен намеренно **не объявлен** в `:root` — как `--assistant-top`
и `--undo-window`. Объявленный, он попал бы в список системных токенов
проверки 2 (`CLAUDE.md` §6.0.2), и страница, которая его задаёт, стала
бы там ложной находкой. Просмотр фото (`modal-ov-viewer`) смещения
не получает: картинка считает свои размеры от окна.

Подложка затемняется на обеих раскладках, `rgba(0,0,0,.75)`. Проверено
пикселями, а не чтением правила: средняя яркость области списка писем
24.74 при закрытой модалке против 5.81 при открытой, отношение 0.235 —
ровно то, что объявлено. Ощущение «фон читается в полную силу» даёт тёмная
тема: светлый текст на почти чёрном остаётся различим и после снятия трёх
четвертей яркости.

**Три поведения — не пожелание, а часть компонента.** До него каркас жил
двенадцатью копиями в дневнике питания, и замер показал, во что это обошлось:
Escape не закрывал ни одну из двенадцати (обработчика не существовало вовсе),
фокус после закрытия оставался на невидимом поле внутри спрятанного окна,
а 73 фокусируемых элемента из 142 на странице лежали в порядке табуляции
всегда — четырнадцать нажатий Tab с начала страницы попадали в закрытые
модалки все четырнадцать. Клавиатурой пройти по странице было нельзя.

Отсюда два неочевидных требования к разметке:

- **`inert` на закрытой модалке.** Она остаётся в DOM с `opacity: 0` ради
  перехода — то есть остаётся живой и фокусируемой. `display: none` убил бы
  анимацию, `inert` не мешает ей.
- **Фокус возвращается ДО снятия `inert`.** В обратном порядке `inert`
  на предке уводит фокус с потомка в никуда, и возвращать становится неоткуда.

Блокировка фона — классом `modal-open` на `<html>`, не `position: fixed`
на `body`: второй сбрасывает `scrollY`, и страница прыгает при закрытии.
Место под скроллбар зарезервировано всегда (`scrollbar-gutter: stable`),
поэтому вёрстка при блокировке не сдвигается.

**Второго варианта больше нет.** Здесь до 2026-08-04 стояла «центрированная
карточка» — `.modal` + `.modal-backdrop`, предшественник компонента, живший
в профиле. Профиль переведён на компонент (`BACKLOG.md`, задача 29), правила
удалены из `style.css`, и текст с их кодом удалён отсюда: описание мёртвого
класса в дизайн-системе — та же ловушка, что и само правило. Оно молча
сработает на первом же `class="modal"`, написанном в расчёте на компонент,
а компонент называется `.modal-ov`.

Нужен диалог — только макрос выше. Другого способа нет.

### 2.7. Toggle

Переключатель «вкл/выкл» для настроек. Единственный потребитель на сегодня —
таблица доступов в админке (`admin_users.html`). Уведомления в профиле,
под которые компонент задумывался, ещё не сделаны, и тумблера там нет.

```html
<label class="toggle">
  <input type="checkbox" checked>
  <span class="track"></span>
</label>
```

Дорожка называется `.track`, а не `.toggle-track`: второе имя было
у админской копии и умерло вместе с ней.

**`display: inline-block` на `.toggle` обязателен, и это не косметика.**
Компонент — это `<label>`, то есть строчный элемент, а на строчном
ширина и высота не применяются вовсе. Пока единственным местом был
флекс-ряд, отсутствие свойства не всплывало: флекс-элемент блокируется
сам. В ячейке таблицы блокировать некому — коробка схлопывается в ноль,
дорожка с `inset: 0` растягивается по нулю, и тумблер исчезает. Отказ
немой: разметка на месте, ошибок нет, элемента не видно.

Размер 40×22, бегунок 16×16. Дорожка выключенного состояния — `--surface-3`,
включённого — `--accent-brand-dim` с рамкой `--accent-brand`. Акцент здесь
брендовый, а не `--tool-accent`: тумблер живёт в служебных экранах, где темы
раздела нет.

**Дорожка намеренно на `--surface-3`, а не на `--surface-sunken`.** Углубление
предназначено для пассивных контейнеров — дорожек прогресса и утопленных
областей (раздел 1.1). Тумблер интерактивен, ему нужно читаться как элемент
управления, поэтому он остаётся на уровне выше.

Компонент завели здесь после того, как выяснилось, что его в системе нет
вовсе: тумблер писала у себя каждая страница, которой он понадобился, —
профиль 40×22, админка 38×22. Это не переопределение системного класса,
а его отсутствие, и греп из `CLAUDE.md` §6.0.2 такие случаи ловит вместе
с переопределениями, не различая. Различать должен читающий: переопределение
чинится удалением, отсутствие — переносом в систему.

Вторая половина — удаление копии — закрыта 2026-08-06 (`BACKLOG.md`,
задача 26). Замер до и после, на живом дереве: `38×22` с бегунком `14×14`
и сдвигом через `left` → `40×22` с бегунком `16×16` и сдвигом
`translateX(18px)`. Два пикселя — та самая разница, которую никто
не замечает глазом и которая доказывает, что копии разъезжаются сами.

### 2.8. Контейнер

```css
.container      { max-width: 1200px; margin: 0 auto; padding: 0 40px; }
.container-wide { max-width: 1600px; }
```

Вариант ставится **вместе** с базовым: `<main class="container container-wide">`.
Потребитель на сегодня один — HH-ассистент, и это не повод обойтись без
варианта. Ширина там нужна по существу: рабочая область делится на две
колонки, и при 1200px в каждой остаётся около 560px, отчего текст письма
ломается каждые ~55 знаков. Раньше та же величина лежала в `hh.css`
правилом `main.container` — то есть страница молча меняла системный
контейнер, и вторая страница, которой понадобилась бы широкая область,
скопировала бы строку вместо готового варианта.

Пока класс на странице один, соблазн «оставить как есть» велик — но
цена ошибки несимметрична: переопределение стоит правки в `style.css`,
которая не проявится, а вариант не стоит ничего.

### 2.9. Spinner

```css
.spinner    { display: inline-block; width: 18px; height: 18px;
              border: 2px solid rgba(255,255,255,0.15);
              border-top-color: var(--tool-accent, var(--accent-brand)); }
.spinner-sm { width: 14px; height: 14px; }
.spinner-lg { width: 32px; height: 32px; border-width: 3px; }
```

Базовый размер — 18px, рядом с текстом. `.spinner-sm` встаёт внутрь кнопки
на место значка, `.spinner-lg` — в пустую панель, где спиннер единственное
содержимое. Толщина кольца у мелкого та же, что у базового, поэтому
в варианте не объявляется. Цвет берётся из темы раздела автоматически.

**`display: inline-block` — не оформление, а условие работы компонента.**
Спиннер вешают и на `<div>` (в панели), и на `<span>` (внутри кнопки, на
место значка). У строчного элемента `width` и `height` игнорируются: от
кольца оставались одни рамки, и вместо него рисовалась неподвижная
вертикальная палка 4×26. Замерено 2026-08-11 на кнопках анализа вакансии
и генерации письма в HH-ассистенте — обе показывали палку, обе с рабочей
анимацией вращения, потому что крутить нечего было. Отказ немой в чистом
виде: разметка верная, класс на месте, анимация идёт, консоль пустая.

Признак при ревью тот же, что у темы раздела в §7.7: **замер свойства
не равен замеру пикселя.** `getAnimations().length` возвращал 1, то есть
по свойству спиннер «крутился». Читать надо `getBoundingClientRect()`.

**Второй индикатор на том же экране — лишний.** Если рядом уже крутится
`.spinner-lg` в панели результата, спиннер на кнопке не добавляет
информации: достаточно сменить подпись («Анализирую…»). В HH-ассистенте
так и сделано — на кнопке письма индикатора нет намеренно, а на кнопке
анализа он есть, потому что другого на экране нет.

### 2.10. Экран-результат пути входа

«Проверьте почту», «Пароль изменён», «Аккаунт удалён» — три экрана
с одинаковой разметкой: значок, заголовок, текст, действие, иногда сноска.

```html
<div class="auth-box">
  <div class="auth-result">
    <div class="auth-result-icon">📬</div>
    <h1>Проверьте почту</h1>
    <p class="auth-result-text">Если такой email зарегистрирован…</p>
    <a href="/login" class="auth-result-back">← Вернуться к входу</a>
  </div>
</div>
```

Части: `.auth-result-icon` — глиф-иллюстрация (кегль тут не текстовый,
правило минимума на него не распространяется); `.auth-result-text` —
основной абзац; `.auth-result-back` — возврат ссылкой; `.auth-result-note` —
сноска мелким под действием. Действие-кнопка — обычная `.btn-primary`
с `.btn-block`, своего класса у неё больше нет (см. 11).

**Шаблоны при этом в один не сводятся, и это выяснилось при попытке.**
У `forgot_password` и `reset_password` разные формы, разные роуты и разные
поля, а `account_deleted` к восстановлению пароля не относится вовсе —
общим у трёх был ровно результат-экран. Он и стал компонентом; пятнадцать
инлайновых `style=` ушли вместе с ним (`BACKLOG.md`, задача 34).

### 2.11. Вкладки раздела

Верхний уровень навигации **внутри** инструмента: «Написать письмо /
История / Досье / Резюме». Подчёркивание снизу, активная — в акценте
раздела.

```html
<div class="tab-bar tab-bar-sticky" role="tablist">
  <button class="tab-btn active"><i data-lucide="pen-line"></i> Написать письмо</button>
  <button class="tab-btn"><i data-lucide="history"></i> История писем</button>
</div>
```

```css
.tab-bar { display: flex; gap: var(--space-2); border-bottom: 1px solid var(--border-hairline); overflow-x: auto; }
.tab-btn { padding: var(--space-3) var(--space-4); border-bottom: 2px solid transparent; color: var(--text-2); font-size: var(--text-nav); font-weight: 500; }
.tab-btn.active { color: var(--text); border-bottom-color: var(--tool-accent, var(--accent-brand)); }
```

Прозрачная линия у неактивной вкладки, а не её отсутствие: иначе активная
подрастает на 2px и весь ряд дёргается при переключении.

**Вариант `.tab-bar-sticky`** — ряд остаётся под шапкой при прокрутке
длинного вида: `top: 64px` плюс полупрозрачный фон с `backdrop-filter`.
Это одно из четырёх мест, где высота шапки участвует в расчётах осознанно
(раздел 4.1). Размытие нужно, чтобы уходящее под ряд содержимое читалось
как уходящее, а не как обрезанное.

Адаптив (кегль и паддинг на ≤640px) живёт **в компоненте**, а не
на странице: иначе каждая страница с вкладками пишет свой медиазапрос
и они разъезжаются ровно так же, как разъехались сами вкладки.

**Имя `.tab-btn`, а не `.tab`.** `.tab` занят в `enshrouded.html`
собственным инлайновым `<style>` с шестью категорийными расцветками.
Раздел вне системы целиком (`BACKLOG.md`, задача 38), сводить его сейчас
нельзя, а системный `.tab` перекрывался бы там молча — как раз тот
немой отказ, от которого весь этот документ.

**Отбивка ряда от содержимого — не свойство компонента.** Её задаёт
страница своим классом: у `/hh` это `.hh-tabs { margin-bottom }`.

### 2.12. Сегментированный переключатель

Два-три взаимоисключающих режима **одного блока**: «Текст / Ссылка»
у источника вакансии, «Недавние / Частые / Рецепты» в поиске еды.

```html
<div class="segmented">
  <button class="segmented-btn active"><i data-lucide="clipboard-list"></i> Текст</button>
  <button class="segmented-btn"><i data-lucide="link"></i> Ссылка</button>
</div>
```

```css
.segmented { display: flex; gap: var(--space-1); padding: var(--space-1); background: var(--surface-2); border: 1px solid var(--border); border-radius: var(--radius-sm); }
.segmented-btn { flex: 1; border-radius: calc(var(--radius-sm) - 2px); color: var(--text-faint); font-size: var(--text-caption); font-weight: 600; }
.segmented-btn.active { background: var(--surface-3); color: var(--text); }
```

**От вкладок отличается не видом, а ролью.** Вкладки переключают экран
и живут в его верху; переключатель меняет содержимое одного блока и стоит
внутри него. Отсюда и разница оформления: у переключателя подложка —
он читается как один контрол, у вкладок линия — они читаются как
навигация.

Активный сегмент поднят на `--surface-3`, а **не** окрашен акцентом:
акцент в системе означает действие, а выбранный режим — состояние.

Радиус сегмента — `calc(var(--radius-sm) - 2px)`, минус паддинг
контейнера. Без вычитания угол сегмента не вписывается в угол подложки
и между ними видна светлая скобка.

### 2.13. Полоса отмены (`.undo-bar`)

Сообщение о только что сделанном действии **с кнопкой возврата**. Заведена
2026-08-12 под удаление письма из истории (`BACKLOG.md`, задача 61).

```html
<div class="undo-bar" id="undo-bar" role="status" aria-live="polite">
  <span class="undo-bar-text" id="undo-bar-text"></span>
  <button class="undo-bar-btn" type="button">Вернуть</button>
</div>
```

```css
.undo-bar { position: fixed; left: var(--space-5); bottom: var(--space-5); display: none; align-items: center; gap: var(--space-4); background: var(--surface-1); border: 1px solid var(--border-strong); border-radius: var(--radius-md); box-shadow: var(--shadow-md); overflow: hidden; }
.undo-bar.show { display: flex; opacity: 1; transform: translateY(0); }
.undo-bar-btn { border: 1px solid var(--tool-accent, var(--accent-brand)); color: var(--tool-accent, var(--accent-brand)); border-radius: var(--radius-sm); }
.undo-bar::after { content: ''; position: absolute; left: 0; right: 0; bottom: 0; height: 2px; background: var(--tool-accent, var(--accent-brand)); transform: scaleX(0); transform-origin: left center; }
.undo-bar.run::after { animation: undoDrain var(--undo-window, 5000ms) linear forwards; }
```

**Полоса обратного отсчёта по нижнему краю** (добавлена 2026-08-12). Сколько
ещё висит окно отмены — видно, а не угадывается. Цифрового счётчика нет
намеренно: он требует чтения, а нужен один взгляд.

| Что | Как сделано | Почему так |
|---|---|---|
| длительность | приходит из скрипта: `setProperty('--undo-window', ОКНО_ОТМЕНЫ_МС + 'ms')` | окно отмены задано константой в JS. Вторая копия числа в CSS разъехалась бы молча — полоса опустела бы не тогда, когда срабатывает таймер, то есть соврала бы ровно о том, ради чего заведена |
| перезапуск | класс `run` снять → `void bar.offsetWidth` → вернуть | без снятия класса CSS-анимация с тем же именем заново не начинается: при втором удалении подряд подпись стала бы счётчиком, а полоса продолжила бы утекать со старого места |
| пауза при наведении | **нет** | пауза означала бы, что запись висит удалённой неопределённо долго, пока курсор стоит на полосе |
| `prefers-reduced-motion` | полоса не рисуется вовсе | глобальное правило в конце `style.css` обнуляет длительность любой анимации, и полоса опустела бы на первом кадре — показала бы «время вышло» сразу |

Замер расхождения между опустошением полосы и фактическим срабатыванием
таймера — в отчёте по правке; порядок величины единицы миллисекунд, обе
стороны стартуют в одном кадре.

**От тоста отличается ролью, а не видом.** Тост — уведомление, в него
не тыкают, у него `pointer-events: none` и фиксированные 2,5 секунды.
Полоса — орган управления: в неё тыкают, и живёт она ровно столько,
сколько длится окно отмены.

**Одна на страницу — это часть компонента, а не деталь применения.**
Второе действие подряд не добавляет вторую полосу, а меняет подпись
на счётчик («Удалено писем: 2»), заводит отсчёт заново от последнего
действия и возвращает всю накопленную пачку. Стопка отдельных полос,
у каждой свой таймер, на 390px закрывает существенную часть экрана,
и по виду не сказать, какая кнопка что вернёт.

Угол — левый нижний, потому что правый нижний занят тостом: два блока
в одном углу перекрывают друг друга. На узком экране полоса растягивается
по ширине (`left` и `right` разом): 390px не хватает, чтобы подпись
и кнопка стояли рядом.

### 2.15. Сообщения (`.alert`)

Раздел заведён 2026-08-14 и закрывает давнее слепое пятно: сам компонент
живёт в `style.css` с самого начала, а описания у него не было ни строки.
Проверка 7 такое не ловит по построению — она ищет имена из документа
в коде, а не наоборот, — поэтому пятно и держалось.

Полоса-сообщение над содержимым или под ним. База `.alert` задаёт форму
(отступы, радиус, кегль подписи, флекс со значком), цвет приносит вариант.
Варианта четыре, и различаются они не оттенком, а тем, **что утверждают**:

| Класс | Что означает | Когда |
|---|---|---|
| `.alert-error` | операция не прошла | отказ, который надо исправить |
| `.alert-success` | операция прошла | подтверждение сделанного |
| `.alert-warn` | прошла, но с оговоркой | не ошибка и не успех |
| `.alert-accent` | **не про исход операции вовсе** | состояние, о котором надо знать сейчас |

Четвёртый заведён 2026-08-14 под подпись «запись пойдёт в такой-то день»
в дневнике питания. Три прежних ему не годились ни один: ничего не
случилось, ни хорошего, ни плохого, — сообщение говорит о состоянии,
в котором человек находится. `.alert-success` на таком месте утверждал бы
успех несделанного действия.

**Красится акцентом РАЗДЕЛА** (`--tool-accent`), а не общим брендом:
вариант всегда стоит внутри инструмента, и второй зелёный рядом
с зелёным дневника читался бы как другой смысл. На страницах без темы
раздела откатывается на `--accent-brand`.

Значок ставится первым потомком: `.alert svg` уже описан размером 18×18
и `stroke-width: 1.5`, отдельного правила писать не надо.

### 2.16. Панель вместо модалки на широком экране

Заведено 2026-08-14 на экране «Добавить» в дневнике питания (`.a-panel`).

**Правило: если окно открывается ПОВЕРХ списка, из которого выбирают,
и на широком экране рядом есть место — вместо окна ставится панель.**
На узкой ширине остаётся модалка: колонки там нет.

Причина не в моде на панели. Модалка порции закрывала собой список
находок — то есть ровно то, из чего человек выбирает. Сравнить две
записи по калорийности с открытым окном нельзя: чтобы посмотреть
на соседнюю, окно надо закрыть, а закрытие теряет введённую граммовку.

Три вещи, без которых панель хуже модалки:

| Что | Почему |
|---|---|
| колонка стоит ВСЕГДА, даже пустой | появляясь по выбору, панель сдвигает список ровно в момент нажатия по нему — и на широком экране дважды, потому что сетка находок перестраивается под новую ширину |
| пустая колонка говорит, чего ждать | «Выберите продукт слева» вместо пустоты: пустая рамка читается как поломка |
| панель липнет к верху (`position: sticky`) | список прокручивается, а кнопка записи обязана остаться на виду |

**Ветка выбора одна и порог у неё общий с раскладкой** (900px,
`matchMedia`). Второе число здесь разошлось бы с CSS молча: панель
объявлялась бы там, где колонки для неё нет, и не открылось бы ни окно,
ни панель.

**Функция записи — ОДНА на оба пути.** Панель и модалка отличаются двумя
вещами: откуда взять граммовку и что закрыть после записи. Второй
обработчик «то же самое, только поля называются иначе» разъезжается ровно
так же, как разъезжаются две копии текста, — правку внесут в ту, что была
перед глазами.

**Выбор, показанный в двух местах, ведёт одно значение.** Приём пищи
на этом экране выбирается и слева, и в панели; обе группы чипов красит
одна функция. Разъехавшись, они показали бы человеку выбранным один
приём, а записали бы в другой.

## 3. Третичная ссылка-кнопка (`.btn-signature`)

**Бегущей обводки в проекте больше нет.** Раздел описывал единственную
«фишку» сайта: тонкую рамку 1px, вокруг которой по периметру бежала
светящаяся дуга длиной 40px, цикл 4 секунды. Механика удалена 2026-08-11
(`BACKLOG.md`, задача 54) вместе с `.signature-border`, `@keyframes
run-border`, исключением в `prefers-reduced-motion` и расчётом периметра
в `ui.js`.

**Причина — замер, а не вкус.** Дуга 40px на периметре 432px занимает 9%
контура. В любой отдельный момент времени видна не рамка, а короткая
синяя чёрточка у случайного края кнопки: на скриншоте, в записи экрана
и на первом кадре загрузки страницы она читается как посторонний элемент,
а не как оформление. Анимация, которую можно опознать только досмотрев
её до конца, не работает — смотреть на кнопку четыре секунды никто
не станет.

Что осталось — сама ссылка-кнопка, третичный уровень рядом
с `.btn-primary`:

```css
.btn-signature {
  display: inline-flex;
  align-items: center;
  justify-content: center;
  gap: var(--space-2);
  padding: var(--space-3) var(--space-5);
  color: var(--text);
  font-weight: 500;
  text-decoration: none;
  background: transparent;
  border: none;
  border-radius: var(--radius-sm);
  min-height: 40px;
}
```

`min-height: 40px` — не украшение: кнопка стоит в одном ряду
с `.btn-primary` геройского блока, и ряд обязан быть ровным. Ровно поэтому
у соседней кнопки берётся `.btn-glow`, но не `.btn-lg` (см. §2, кнопки).

**Имя историческое.** «Signature» — от той самой обводки. Класс оставлен
как есть: потребитель у него один (`landing.html`), а переименование ради
имени переписало бы ссылки в трёх документах и в истории `BACKLOG.md`,
ничего не изменив на экране. Если компонент понадобится второй странице —
имя стоит поменять тем же коммитом.

**Правило использования:** третичное действие рядом с основным. Не primary
CTA, не кнопка внутри инструмента.

### 4.1. ВЫСОТА 64px УЧАСТВУЕТ В РАСЧЁТАХ РАСКЛАДКИ — но уже только там, где это по существу

**Меняете `height` у `.site-header` — правьте все места из таблицы ниже.**
Мест стало три вместо десяти.

Число жило не в одном месте. Страницы, которым нужна высота «весь экран
минус шапка» или прилипание под шапкой, вычитали и подставляли эти же 64px
руками, и разъехалось бы всё **молча**: ошибки нет, консоль чистая, просто
у одних страниц лишняя полоса внизу, у других контент под шапкой.

**2026-08-04 половина зависимости убрана, а не разложена аккуратнее.**
Шесть мест из десяти были одним и тем же: `min-height: calc(100vh - 64px)`
на главном блоке — «займи остаток экрана». Остаток умеет считать браузер,
если раскладку описать колонкой, и тогда высота шапки в расчёт не входит
вовсе. Токен `--header-h` эту зависимость бы сохранил, просто под одним
именем; вариант с раскладкой её **устраняет**.

```css
body.page-column { display: flex; flex-direction: column; min-height: 100dvh; }
.page-fill       { flex: 1 0 auto; }
```

Страница ставит `page-column` на `<body>` и `page-fill` на блок, который
должен вырасти. Два класса, а не селектор `body.page-column > main`:
у дневника питания главный блок — `<div class="nut-app">`, а `<main>`
получает `position: relative; z-index: 1` и вместе с ним свой stacking
context, из которого `position: fixed` вкладки ассистента уже не выбирается.
Менять тег ради раскладки нельзя.

`flex: 1 0 auto`, а не `flex: 1`. База `auto` означает «не меньше
содержимого»: короткий контент — блок дорастает до остатка экрана и футер
прижат к низу, длинный — блок растёт дальше и страница прокручивается.
С `flex: 1` (база 0) блок был бы ровно в остаток, а всё, что ниже, стало бы
недостижимым.

**Осталось три места, и в каждом вычитание осмысленно.** Общее у них одно:
элемент вырван из потока (`position: sticky` или `fixed`), браузеру считать
остаток не из чего, и отступ сверху обязан совпасть с высотой шапки числом.

Четвёртым было пятое: `.hh-tabs` держал `top: 64px` дважды — в десктопном
правиле и слово в слово в мобильном. Оба ушли 2026-08-09 вместе с самим
рядом вкладок, переехавшим в компонент `.tab-bar-sticky` (раздел 2.11).
Это и есть выигрыш от компонента, который обычно не называют: число,
записанное на странице, копируется вместе со страницей, а записанное
в компоненте — не копируется вообще.

| Файл | Место | Как участвует |
|---|---|---|
| `static/style.css` | `.site-header` | **источник**: `height: 64px` |
| `static/style.css` | `.tab-bar-sticky` | `top: 64px` — ряд вкладок прилипает под шапкой |
| `static/nutrition.css` | `#tab-assistant.active` | `top: calc(64px + var(--hdr-h))` — запасное значение, обычно его перекрывает `--assistant-top` от скрипта |
| `templates/enshrouded.html` | под-шапка раздела | `top: 64px` |

**Ушло шесть мест:**

| Файл | Было | Стало |
|---|---|---|
| `static/nutrition.css` | `.nut-app { min-height: calc(100dvh - 64px) }` | `.page-fill` |
| `static/nutrition.css` (≥900px) | `.nut-app { height: calc(100dvh - 64px) }` | `.nut-app { flex: 1 1 0; min-height: 0 }` — сужение `.page-fill` до «ровно остаток», см. ниже |
| `static/workout.css` | `.wk-page { min-height: calc(100vh - 64px) }` | `.page-fill` |
| `templates/404.html` | `.not-found { min-height: calc(100vh - 64px) }` | `.page-fill` |
| `templates/tool_preview.html` | `.tp-wrap { min-height: calc(100vh - 64px) }` | `.page-fill` |
| `templates/workout_profile.html` | `.theme-workout { min-height: calc(100vh - 64px) }` | `.page-fill`; сам селектор с 2026-08-06 называется `.wkp-page` и живёт в `static/workout_profile.css` |

Дневник на десктопе — единственное место, где нужен не «минимум остатка»,
а **ровно остаток**: это приложение в один экран, прокручиваются колонки
внутри, а сама страница не прокручивается никогда. Поэтому `.nut-app` там
сужает системное `flex: 1 0 auto` до `flex: 1 1 0` с `min-height: 0` —
база 0 означает, что высоту блока определяет свободное место, а не
содержимое. Замер после правки (1280×800): `.nut-app` 64…800, лента чата
94…715 при `scrollHeight` 1434, прокрутка страницы отсутствует —
`scrollHeight` документа равен `clientHeight`.

Проверить перечень:

```bash
grep -rn "64px" static/*.css templates/*.html | grep -E "calc\(|top: ?64px|height: 64px" | grep -v "grid-template\|padding"
```

**Почему оставшиеся четыре НЕ переводятся в rem.** Соблазн есть — файлы
страниц переведены на rem, и `64px` выглядит забытым. Но высота шапки задана
в px и не растёт с корневым кеглем, а `4rem` на 2K/4K вырастет до 76px.
Вычиталось бы то, чего нет. Правило: **чужая величина вычитается в тех
единицах, в которых объявлена.**

**Почему `100dvh`, а не `100vh`, в `page-column`.** `vh` на мобильных
считается по вьюпорту без адресной строки, то есть больше видимой области;
на коротком экране это давало бы полосу прокрутки ровно в высоту этой строки.
У дневника здесь уже стояло `100dvh` — теперь так на всех пяти страницах.

**НЕ используем:** горизонтальные ссылки «Главная / Профиль / Админ / Выйти» вразнобой в шапке. Всё уходит в аватар-дропдаун. Это освобождает шапку и делает её премиальной.

**Четыре состояния, и все четыре выводятся из данных.** Страница не задаёт
состояние вручную — она просто подключает `_header.html`:

| Состояние | Условие | Что в шапке | Где встречается |
|---|---|---|---|
| гость | `user` нет | логотип + Войти / Регистрация | `/login`, `/register`, `/forgot-password`, `/reset-password`, лендинг, витрина инструмента |
| регистрация начата | `user` нет, есть кука `pending_verify` | логотип + Войти | `/verify-pending` и любая страница в течение 30 минут после регистрации |
| без инструментов | `user` есть, `user.is_verified` ложно | логотип + аватар-дропдаун | `/verify-required` |
| полный | `user.is_verified` истинно | логотип + поиск + аватар-дропдаун | всё остальное |

Поиск рисуется по четвёртому состоянию, а не по факту авторизации: пока почта
не подтверждена, инструменты закрыты плашкой, и выпадашка вела бы обратно
в неё же. Проверка — прямая на истинность: `is_verified` в базе `nullable`,
и незаполненное значение обязано читаться как «доступа нет», иначе пустое
поле молча нарисует поиск.

**Второе состояние — про уместность, а не про права.** Человек, который
только что заполнил форму регистрации и ждёт письмо, технически гость: сессии
нет, `/register` её не открывает. Но кнопка «Регистрация» на экране «проверьте
почту» читается как «вы сделали что-то не то, начните заново». Поэтому она
убирается, а «Войти» остаётся — почту могли подтвердить в соседней вкладке.

Признак берётся из куки `pending_verify`, а не из адреса страницы: это то же
данное, по которому `/verify-pending` узнаёт человека (`main.py`,
`_pending_user`). Разбор пути превратил бы шапку в справочник роутов, который
разъедется при первом переименовании.

Класс `.site-header-edges` вешается на первые три состояния: содержимое по
краям, середина пуста. Он снимает растяжку крыльев, без которой логотип уезжал
бы к центру. Имя описывает раскладку, а не то, чего в шапке нет: «без поиска»
соврало бы в тот день, когда из середины уберут что-то ещё.

#### Четыре состояния — потолок

**Пятого не добавляем.** Не «стараемся не добавлять», а не добавляем: нужда
в пятом означает, что пересматривать надо не шапку, а задачу, которую на неё
вешают.

Причина в несоразмерности. Компонент рисует логотип, поле поиска и одну
кнопку. Четыре ветки на такой объём — уже верхняя граница читаемости: их
можно удержать в голове целиком и проверить перебором за минуту. Пятая
превращает шапку в место, где принимаются решения о продукте, и разбираться
в ней придётся каждому, кто пришёл поправить отступ у логотипа.

Признак, из которого выводится каждое состояние:

| Состояние | Признак | Откуда он берётся |
|---|---|---|
| гость | `user` отсутствует | сессии нет |
| регистрация начата | кука `pending_verify` | `/register`, живёт 30 минут |
| без инструментов | `user.is_verified` ложно | поле в базе |
| полный | `user.is_verified` истинно | поле в базе |

Ни один из четырёх не задаётся страницей и не читается из адреса. Это
и есть граница: **признак должен быть данным о человеке, а не о том, где
он сейчас находится.** Как только для нового состояния понадобится смотреть
на путь, имя роута или флаг из контекста шаблона — состояние заводить нельзя,
это уже не шапка.

Что делать вместо пятого состояния:

- **уместность конкретного экрана** (что-то лишнее на одной странице) —
  решается на самой странице, а не ветвлением в общем компоненте;
- **новый тип пользователя** — сначала проверить, не сводится ли он
  к `is_verified`-подобному признаку внутри существующих четырёх;
- **если не сводится** — это разговор о том, что шапка вообще должна делать,
  и он начинается с правки этого раздела, а не с `{% if %}` в `_header.html`.

### 7.6. Механика тем

```css
/* Общая механика (все токены) живёт в :root.
   Комплект из четырёх, и .theme-* с .tool-* — одно правило: акцент

.theme-hh, .tool-hh {

}
.theme-nutrition, .tool-nutrition {
  --tool-accent: var(--accent-nutrition);
  --tool-accent-dim: var(--accent-nutrition-dim);
  --tool-accent-hover: var(--accent-nutrition-hover);
  --tool-accent-ink: var(--surface-0);
}
.theme-workout, .tool-workout {

  --tool-accent-dim: var(--accent-enshrouded-dim);

  --tool-accent-ink: var(--text-strong);

```

**Правил вида `.theme-hh .btn-primary` в системе нет и быть не должно.**
Здесь до 2026-08-09 стоял именно такой пример — тема переопределяла
компонент, — и он был неверен дважды. Во-первых, это переопределение
компонента контекстом, то есть ровно то, за что мы ругаем страницы
(`CLAUDE.md` §6.0.2): фон переехал бы, а надпись осталась белой. Во-вторых,
`filter: brightness(0.88)` красит и надпись: на синем это давало 2.99
против 3.13 в покое — правило, отменяющее собственную цель (§1.4).

Компоненты читают `--tool-accent*` сами, поэтому тема объявляет только
токены. Ни одна строка вида `.theme-… .компонент` в `style.css` не нужна.

### 7.7. Тема объявляется на `<body>`

**Правило: класс темы вешается на `<body>`. Не на `<main>`, не на обёртку
контента.**

`--tool-accent` — это CSS-переменная, а переменные наследуются **вниз по
дереву**. Объявление на `<main>` делает акцент доступным только внутри
главного блока. Всё, что по разметке лежит рядом с `<main>`, а не внутри
него, темы не видит: оверлеи, модалки, лайтбоксы, тосты, тултипы, выпадашки,
припаркованные в конце `<body>`.

Отказ при этом **немой**. Нераскрытая переменная не роняет страницу и не
пишет ничего в консоль — свойство просто не применяется либо берёт
fallback. Элемент оказывается серым или бесцветным, и заметить это можно
только глазами и только открыв тот самый оверлей.

**Цена на живом примере — она же история правки.** До 2026-08-06
`workout.html` объявлял тему на `<main class="theme-workout wk-page">`.
Три элемента вынесены за `<main>` по требованиям позиционирования,
и каждому пришлось приписать класс темы руками:

| Элемент | Почему вне `<main>` |
|---|---|
| `#wkChartTooltip` | `position: fixed`, следует за курсором |
| `#wkLightbox` | полноэкранный просмотр фото |
| `#wkChatOverlay` | оверлей чата с тренером |

Три копии класса — это не «немного дублирования», это три места, где
следующий оверлей будет забыт. Проверить, что список полон, нельзя ничем,
кроме ручного обхода: греп по `theme-` покажет только те элементы, которым
класс УЖЕ приписали, а ищем мы как раз те, которым не приписали.

На `<body>` вопрос не возникает вовсе: `<body>` — предок всего, включая
элементы, которых ещё нет в разметке. Все три копии сняты, приписывать
класс новым оверлеям не нужно.

Замер после переноса (1280×800, живое дерево, вычисленное значение
`--tool-accent`):

| Элемент | Было (тема на `<main>`) | Стало (тема на `<body>`) |
|---|---|---|
| `<body>` | не разрешался | `#F59E0B` |
| `<main>` | `#F59E0B` | `#F59E0B` |
| `.site-header` | не разрешался | `#F59E0B` |
| `#wkChatOverlay`, `#wkLightbox`, `#wkChartTooltip` | `#F59E0B` — но только благодаря классу на самом элементе | `#F59E0B` по наследованию |

Строка «`.site-header`: было не разрешался, стало `#F59E0B`» — это
не побочный ущерб, а следствие правила. Шапка лежит внутри `<body>`,
значит внутри темы.

> **ЗДЕСЬ БЫЛА НЕПРАВДА, И ЭТО ПОУЧИТЕЛЬНО.** До 2026-08-09 абзац
> продолжался так: «её focus-ring на поле поиска на страницах тренировок
> теперь янтарный вместо синего». Замер выше — настоящий, но он мерил
> **другое**: что `--tool-accent` у `.site-header` разрешается. Про кольцо
> из этого был сделан **вывод**, и вывод не проверили.
>
> Замер самого кольца (2026-08-09, `getComputedStyle` у `#nav-search-input`
> после фокуса) дал синий на всех четырёх разделах. Мешало правило
> `.header-search .input:focus` в `style.css` — копия компонентного
> `.input:focus` с брендовым цветом и специфичностью (0,3,0) против (0,2,0).
> Родня задачи 44: разметка верная, токен верный, третье правило молча
> выигрывает.
>
> Правило переведено на `var(--tool-accent, …)`. Сегодня кольцо
> действительно зелёное на `/nutrition`, янтарное на обеих страницах
> тренировок и синее вне раздела — **замерено, а не выведено**.

Это соответствует 1.4: focus-ring — одно из пяти мест, где акцент
разрешён, а акцент внутри раздела — акцент раздела. На `/hh` разницы
не видно вовсе: `--accent-hh` и `--accent-brand` — один и тот же `#4F8FFF`.

**Мораль шире одного кольца.** Замер переменной подтверждает, что
переменная разрешается, и ровно это. Что её кто-то ЧИТАЕТ и что прочитанное
доходит до пикселя — отдельное утверждение и отдельный замер. Между ними
помещается вся специфичность CSS.

**Как проверить:** страницы инструментов объявляют тему на `<body>`;
`grep -n 'class="theme-' templates/*.html` не должен показывать
`<main class="theme-...`. Но греп проверяет только форму. Что переменная
действительно разрешается у оверлеев, проверяется замером на живом дереве —
`getComputedStyle(элемент).getPropertyValue('--tool-accent')` у самого
оверлея, а не у `<main>`. Пустая строка означает отказ.

```html
<!-- правильно -->
<body class="theme-workout has-site-header">
  {% include '_header.html' %}
  <main class="wk-page">…</main>
  <div class="wk-lightbox">…</div>   <!-- тему видит -->
</body>

<!-- неправильно: оверлей вне темы, --tool-accent не разрешится -->
<body class="has-site-header">
  <main class="theme-workout wk-page">…</main>
  <div class="wk-lightbox">…</div>   <!-- темы не видит, отказ немой -->
</body>
```

**Ловушка при переносе — развязка делается первой.** Просто перевесить
класс нельзя, если на селектор `.theme-*` навешана раскладка. Так было
в обеих страницах раздела тренировок: на `.theme-workout` висели
`background`, `color-scheme` и `padding`, а раньше и `min-height`.
На `<body>` они означают совсем другое — паддинг ушёл бы под общую шапку.

Тема объявляет **только** акцентные токены. Раскладка уезжает в свой
класс, и лишь потом переносится тема:

| Страница | Тема (`<body>`) | Раскладка (`<main>`) |
|---|---|---|
| `workout.html` | `.theme-workout` | `.wk-page` (в `workout.css`) |
| `workout_profile.html` | `.theme-workout` | `.wkp-page` (в `workout_profile.css`) |

Отдельно про медиазапросы: правило вида
`@media (max-width: 640px) { .theme-workout { padding: … } }` после переноса
уедет на весь документ. Такое было в `workout.css` и переписано
на `.wk-page` вместе с классом.

## 8. Иконочная система — Lucide

**Подключение (CDN):**
```html
<script src="https://unpkg.com/lucide@latest"></script>
<script>lucide.createIcons();</script>
```

**Использование в шаблонах:**
```html
<i data-lucide="briefcase" class="tool-icon"></i>
```

**Правила:**
- `stroke-width: 1.5` (единая толщина по всему сайту).
- Размеры: 16px (inline с текстом), 20px (в кнопках), 24px (в шапках карточек), 32px (в hero-блоках).
- Цвет: наследуется из `currentColor`.

**Размер задаётся ВСЕГДА и только правилом на контейнере.** Наследования
у иконки нет: `createIcons` пишет `width`/`height` атрибутами прямо на `svg`,
по умолчанию 24. Кегль родителя на неё не влияет никак — в отличие от эмодзи,
который был глифом шрифта и подчинялся `font-size` сам.

Отсюда исключение к списку размеров выше: **где значок стоит в строке
с текстом, ставим `1em`, а не 16px.** В разделах кегль строки разный —
подпись 0.75rem, кнопка 0.875rem, заголовок карточки 1.0625rem, — и одно
число подошло бы одной строке из трёх. Образец с разбором:
`static/workout.css`, самый верх файла.

**Иконки в разметке, собранной скриптом, дорисовываются сами.**
`lucide.createIcons()` страница зовёт один раз, последней строкой; всё,
что вставлено позже, этим вызовом не покрыто, и `<i data-lucide>` остаётся
пустым тегом — без ошибки и без следа в консоли. Наблюдатель
`initLucideAutoDraw` в `static/ui.js` дорисовывает такие значки сам,
поэтому звать `createIcons` после каждой вставки не нужно.
- В шапке карточки инструмента иконка — цвет акцента инструмента.
- В навигации и кнопках — цвет наследуется от текста.

**Список используемых иконок (обновляется по мере необходимости):**
- Инструменты: `Briefcase`, `Salad`, `Dumbbell`, `Shield`
- Действия: `ChevronDown`, `ChevronRight`, `X`, `Check`, `Plus`, `Trash2`, `Edit3`, `Copy`, `Save`
- Навигация: `Search`, `User`, `Settings`, `LogOut`, `Home`
- Состояния: `AlertCircle`, `Info`, `CheckCircle2`, `Loader2`

**Эмодзи разрешены ТОЛЬКО:**
- В описательном тексте уведомлений (`🎉 Программа готова!`)
- В UI-copy, где смысл эмодзи прямой (например, в welcome-сообщении «Привет 👋» — но и это лучше без)
- **НИКОГДА** — в иконках инструментов, метках категорий, заголовках карточек.

#### КРИТЕРИЙ: КРОШКИ ТАМ, ГДЕ РОДИТЕЛЬ НЕ ДОСТИЖИМ ИЗ ШАПКИ

Пересмотрено 2026-08-10 (`BACKLOG.md`, задача 39). Прежняя формулировка —
«единый паттерн на всех страницах внутри инструментов» — держалась
с самого начала и не выполнялась ни дня: крошки стояли на одной странице
из четырёх. Разбор показал, что виноват был не код.

Крошки нужны там, где **есть уровень, которого нет в шапке**. Логотип
в шапке ведёт в лаунчер, то есть родитель любой страницы инструмента
уже стоит на экране постоянно. Строка «Инструменты / HH-ассистент»
повторяла его ссылкой, а под ней шёл `<h1>HH-ассистент` — три элемента
подряд об одном и том же.

| Страница | Родитель | Достижим из шапки? | Крошки |
|---|---|---|---|
| `/hh`, `/nutrition`, `/workout`, `/enshrouded` | лаунчер `/` | **да** — логотип | нет |
| `/workout/profile` | `/workout` | **нет** — ничем | **да** |

То есть страниц с крошками в проекте одна, и это `/workout/profile` —
единственное место с настоящими двумя уровнями:

```
Инструменты / Тренировки / Профиль
```

Показывается **полный путь**, включая «Инструменты», хотя туда ведёт
и логотип: раз элемент поставлен, он показывает цепочку целиком, иначе
это не путь, а вторая кнопка «назад».

**Рассмотренная и отклонённая альтернатива — «страница-документ получает
крошки, экран-приложение нет».** По ней крошки достались бы `/hh`
и `/workout` (у обоих обычная раскладка `eyebrow / h1 / p`), а дневник
остался бы без них как экран со своим app shell. Отклонено потому, что
критерий получается про **вид** страницы, а не про её место: на `/workout`
крошка была бы ровно так же избыточна, как на `/hh`, — родитель тот же
логотип. Правило «где родитель не в шапке» проверяется вопросом, у которого
есть однозначный ответ, и даёт меньше интерфейса.

### 10.4. Правило «всегда есть путь назад»

С любой страницы должны работать:
- Клик по логотипу → главная
- Аватар → профиль/выйти
- Breadcrumb → любой уровень выше (там, где он есть; см. критерий в 10.3)
- Browser back button (не ломать history)

Никаких «вернуться» кнопок в отдельных местах — всё через единые механизмы
шапки и breadcrumb.

**Два исключения, и они разные по природе:**

| Где | Что | Почему не «вернуться»-кнопка вопреки правилу |
|---|---|---|
| дневник питания, `.nut-hdr-back` | стрелка в своей шапке приложения | она **не навигация, а состояние**: с любой вкладки ведёт на «Дневник», и только с «Дневника» — из инструмента. Крошками такое не выражается: путь один, а поведение разное |
| — | — | третьего исключения нет: стрелка `.wkp-back` на `/workout/profile` убрана 2026-08-10 и заменена крошками. Она вела туда же, но не называла куда |

### 10.5. UI-copy

Правила из frontend-design skill:
- Кнопки называют действие в активном залоге: «Сохранить резюме», не «Отправить».
- Одна и та же операция называется одинаково через весь флоу: кнопка «Опубликовать» → тост «Опубликовано» (не «Успешно опубликовано»).
- Никаких «Успешно», «Ошибка!» без содержания. Вместо «Ошибка!» — «Не удалось сохранить: сеть недоступна. Попробуйте ещё раз.»
- **Убрать метку «ДОСТУПЕН»** на карточках инструментов — она ничего не сообщает. Заменить на короткое описание того, ЧТО инструмент делает («Готовит письмо за 15 секунд»), или убрать вовсе.
- В пустых состояниях — не «Здесь пусто», а «Ещё не написано ни одного письма. Начните с вакансии →».
- Обращение к пользователю — **на «вы»** во всех UI-текстах: подсказках, плейсхолдерах, сообщениях об ошибках, модалках, ответах ассистентов. Исключение — админка (`/admin`, внутренний инструмент владельца).

**Описания инструментов живут в двух местах — это намеренно.** У лендинга и лаунчера разные задачи текста: гостю нужно короткое «зачем это», залогиненному — «что внутри». Единое поле дало бы формулировку, которая плохо работает в обоих местах.

| Где | Источник | Задача текста |
|---|---|---|
| Лендинг (`/`, гость) | захардкожено в `templates/landing.html` | короткое «зачем это» |
| Лаунчер (`/`, авторизован) | `TOOLS` в `main.py` | «что внутри инструмента» |

Правило: лендинговая версия может быть **короче**, но не должна **противоречить** по фактам — сроки, способы ввода, набор возможностей обязаны совпадать. При добавлении нового инструмента текст пишется в оба места.

#### Сообщение об отказе называет причину и следующий шаг — не имя исключения

Заведено 2026-08-11 разбором HH-ассистента. Кнопка «Проверить совпадение
с резюме» показывала строку `Unterminated string at line 22 column 5` —
это текст `json.JSONDecodeError`, вылетевший наружу через `str(e)`.

Такое сообщение нарушает сразу два правила выше: оно без содержания
(для читающего это шум) и не говорит, что делать. При этом оно **выглядит
информативным**, поэтому и живёт долго — в отличие от «Ошибка!», которое
режет глаз сразу.

| Плохо | Хорошо |
|---|---|
| `Unterminated string at line 22 column 5` | «Ответ анализа не поместился в лимит. Сократите текст вакансии — оставьте требования и задачи.» |
| `Ошибка OpenRouter: {"error":{"code":429…}}` | «Сервис анализа не ответил. Попробуйте ещё раз через минуту.» |
| «Не удалось извлечь текст» | «Похоже, описание не загрузилось. Откройте вакансию на сайте, скопируйте описание и вставьте на вкладке „Текст“.» |

Правило: **техническая причина уходит в лог целиком, пользователю
достаётся человеческая формулировка и действие.** Не наоборот и не то
и другое разом — префикс `parse:` перед понятной фразой возвращает
исходную болезнь.

Отдельно: **«загрузилось» — не то же самое, что «загрузилось нужное».**
Если операция формально прошла, но результат негоден (страница отдалась,
а описания в ней нет), это не успех и не ошибка — это `.alert-warn`
рядом с результатом, до того как человек нажмёт следующую кнопку.
Зелёная галочка с числом символов на куки-баннере — худший из трёх
исходов, потому что она гасит подозрение.

### 10.6. Длинный текст на узком экране: потолок высоты — это отказ

Заведено 2026-08-11 по трём находкам подряд, у которых форма одна:
**блок с потолком высоты и содержимым переменной длины.**

Потолок отказывает двумя разными способами, и оба немые:

| Форма | Что происходит | Как выглядит |
|---|---|---|
| `max-height` + `overflow: hidden` | всё выше потолка недоступно **никак** | текст просто кончается, будто там конец |
| `max-height` + `overflow: auto` | окошко с собственной прокруткой внутри прокручиваемой страницы | палец уводит страницу, содержимое остаётся обрезанным |

Замеры на 390px, до правки: открытое письмо в истории — содержимое
1764px при потолке 1200, **недоступно 564** (первая форма); поле «что
делал» в досье — 75px при содержимом 613 (вторая форма). На 1280 то же
письмо укладывалось в 898 из 1200, поэтому оба дефекта видел только
владелец телефона.

**Критерий — назначение блока, а не его форма:**

| Блок | Решение |
|---|---|
| текст, который **читают** (письмо, описание опыта, реплика) | разворачивается по высоте, потолка нет |
| **превью** — признак того, что операция прошла (загруженная вакансия) | потолок остаётся, но окно не мельче ~40vh плюс `overscroll-behavior: contain` |
| **лента** с собственной логикой прокрутки (чат, длинный список в модалке) | прокрутка своя, это её работа |

Критерий применён второй раз 2026-08-11, к дневнику питания (`BACKLOG.md`,
задача 52). `.meal-items` — список съеденного за день — держал
`max-height: 5.625rem`, то есть окно **90px**. Замер при четырёх позициях
на приём пищи: содержимое 311–369px, недоступно **222–280**. Потолок снят,
прокрутка поднялась на этаж выше — колонку `#tab-diary` прокручивает
браузер, вложенной ловушки нет.

Отдельно: дефект был **десктопный**, при `min-width: 900px`, где четыре
карточки приёмов пищи стоят в ряд. В задаче 49 он записан как «≤640px» —
ошибка, исправленная замером. На 390px потолка у этого списка не было
никогда.

Как разворачивать аккордеон без потолка — сеткой, а не `max-height`:

```css
.аккордеон      { display: grid; grid-template-rows: minmax(0, 0fr);
                  transition: grid-template-rows var(--dur-slow) var(--ease);
                  overflow: hidden; }
.аккордеон.open { grid-template-rows: minmax(0, 1fr); }
.аккордеон > *  { min-height: 0; }
```

Анимируется (в отличие от `height: auto`), а высота равна содержимому —
числа, до которого можно дорасти, в правиле просто нет.

Два подводных камня, оба замерены, оба не видны без проверки закрытого
состояния:

| Что | Симптом | Почему |
|---|---|---|
| голый `0fr` вместо `minmax(0, 0fr)` | закрытая секция 33px, а не 0 | `0fr` разворачивается в `minmax(auto, 0fr)`, и авто-минимум дорожки равен min-content элемента — паддинги и рамки в него входят |
| `overflow: hidden` только на внутреннем элементе | то же самое | `overflow` не обрезает собственный паддинг элемента; обрезать должен контейнер |

### 10.7. Масштаб раздела на широком мониторе: одна единица

Заведено 2026-08-14 для дневника питания и экрана «Добавить».

**Правило: если раздел растёт под широкий монитор, растёт он ЦЕЛИКОМ
и от одного числа.** Ширина содержимого, кегль, размеры элементов,
отступы и высоты карточек выражаются кратными одной величины,
объявленной на `body` страницы (`--nut-u` у дневника).

Почему не по отдельности. Растянуть ширину при прежнем кегле — это
не «крупнее», а «реже»: строка становится длиннее, текст остаётся
мелким, читать труднее, чем было. Поднять один кегль — то же наоборот.
Обе половины правки поодиночке делают хуже, и заметно это только
на реальном мониторе, а не в голове.

Почему не `html { font-size }`. Это самый короткий способ и самый
неверный: корневой кегль объявлен в системе (`clamp(16px, 13px +
0.15625vw, 19px)`), и переопределение его на одной странице утащило бы
за собой шапку, футер и всё остальное. Ровно то переопределение системы,
которое запрещает `CLAUDE.md` §6.0.2, и ни одна из девяти проверок его
не увидит.

**Системные компоненты внутри масштабу страницы НЕ подчиняются**, и это
решение, а не недоделка. `.chip`, `.input`, `.segmented-btn`, `.card`
сохраняют свои размеры: страница, которая красит систему под себя, —
это и есть переопределение. Свой рост у системы уже есть — все её токены
в `rem`, и корневой кегль поднимается с шириной окна.

Ступени выбираются так, чтобы каждая проверяемая ширина попадала в свою,
и значения по ним ЗАМЕРЯЮТСЯ, а не выводятся. Для дневника (замер
2026-08-14, окна 1440 / 1920 / 2560):

| Величина | 1440 | 1920 | 2560 |
|---|---:|---:|---:|
| единица `--nut-u` | 1rem | 1.1rem | 1.25rem |
| ширина содержимого | 1113* | 1540 | 1859 |
| левая колонка сводки | 288 | 317 | 383 |
| кольцо калорий | 168 | 185 | 223 |
| кегль остатка в кольце | 33.6 | 37.0 | 44.6 |
| кегль имени блюда | 14.4 | 15.8 | 19.1 |
| высота карточки приёма | 326 | 361 | 431 |
| поле справа от содержимого | 51 | 78 | 230 |

\* на 1440 потолок не достигается: содержимому остаётся 1113px после
боковой колонки и полей, и оно занимает их целиком.

Проверяется это одним числом на ширину, а не сорока: если хоть одна
величина отстала, отношение по ней разойдётся с остальными, и видно
это в той же таблице.

## 12. Чек-лист приёмки страницы

Перед тем как считать страницу готовой:

- [ ] Не осталось hardcode-цветов (grep `#[0-9a-fA-F]{3,6}` даёт 0)
- [ ] Не осталось inline-стилей `<style>` в шаблоне (всё в `style.css`)
- [ ] Все шрифты — Manrope (или JetBrains Mono для меток). Syne нет.
- [ ] Все размеры текста — из шкалы (`--text-*`) или через clamp. Никаких `font-size: 14px` в inline.
- [ ] Все отступы — из шкалы `--space-*`.
- [ ] Шапка sticky, не исчезает при скролле.
- [ ] Шапка — общий `_header.html`, своей `<nav>` на странице нет (проверка 4 в `CLAUDE.md`, §6.0.2).
- [ ] Кнопки, поля, модалки и алерты — из компонентной базы (раздел 2). Каждое исключение названо вслух: что это и почему не системный класс. Пункт ручной, грепом не ловится — самодельный компонент не является ни системным классом, ни инлайном.
- [ ] Крошки есть тогда и только тогда, когда родитель страницы **не достижим из шапки** (критерий и таблица — раздел 10.3). У страницы инструмента родитель — лаунчер, он стоит логотипом, и крошек там быть не должно.
- [ ] Есть футер — полный, гостевой (`{% set footer_guest = true %}`) или тонкий (`{% set footer_thin = true %}`), см. §6.1. Отсутствие футера — осознанное исключение, названное в §6.0.2 `CLAUDE.md`.
- [ ] Все иконки — Lucide. Эмодзи в UI-элементах нет.
- [ ] Focus-состояния видны (ring из `--tool-accent-dim`).
- [ ] Prefers-reduced-motion работает (анимации отключаются).
- [ ] На мобильном (390px) вёрстка не ломается, ничего не режется.
- [ ] Если применяется тема инструмента — класс `.theme-*` на body, primary-акцент = `--tool-accent`.

## 14. Финальное напоминание

**Мы не платим ни за одну фишку: тишина и дисциплина — это и есть стиль.**
(Здесь было «платим за одну фишку — running-border кнопка»; обводка удалена
2026-08-11, см. §3.) Если возникает соблазн добавить эффект / градиент / декоративный элемент — сначала спроси: «Это нужно для понимания или для украшения?» Если для украшения — не добавлять.

Референс восприятия: страница должна работать одинаково хорошо для человека, который увидит её на 4K-мониторе с идеальной цветопередачей, и для человека, который откроет её на телефоне под ярким солнцем. Если приём разрушается в одном из этих сценариев — он не проходит.
